# WM quirks

Confirmed sway/i3 behavioral findings that inform tuicc's provider code. Each section is a stable anchor other docs/docstrings can point to (`CLAUDE/NOTES/wm-quirks.md#anchor`).

## Focus-on-map stealing {#focus-on-map-stealing}

Most WMs give a newly-mapped window keyboard focus regardless of stacking order. tuicc is a floating window that stays visually on top of whatever workspace it's summoned into, so without an explicit reclaim, the moment something is spawned from the launcher, the next keystrokes silently go to the new window sitting hidden underneath tuicc — even though tuicc still *looks* focused on screen. This happens on the very first spawn, not as an edge case; it breaks the launcher's "spawn without losing your place" promise immediately.

`Provider.focus_self()` (`providers/base.py`) is the reactive fix: called once per resolved entry in `pending_moves.process()`, right after `move_window_to_region()`/`set_floating_geometry()`. `Provider.no_focus_next_window(pid)` is the proactive complement — see below.

## Fullscreen drop on sibling window map {#fullscreen-drop-on-map}

sway/i3 both drop a fullscreen container back to plain floating the instant its keyboard focus moves away to a new sibling window. This used to happen unavoidably on every spawn: new windows land wherever real WM focus currently is (typically tuicc's own workspace) and, by default, take focus themselves the moment they map.

`Provider.no_focus_next_window(pid)` prevents the focus move at the source — `for_window [pid=<spawned pid>] no_focus`, sent right after `spawn_detached()` returns, before the window has had a chance to map. Confirmed: preventing the auto-focus also prevents the fullscreen drop — the drop is not an independent side effect of a new window merely existing, it's specifically caused by focus leaving the fullscreen container.

Reasserting fullscreen alone (`focus_self(fullscreen=True)`) isn't enough to make a drop that does happen look clean: a floating container's underlying (non-fullscreen) geometry is whatever the WM defaults a new floating window to — usually a small centered box — so a visible "blink" would be a shrink-then-expand pop, not just a flicker, even once fullscreen is recovered within one poll cycle. `install.sh`'s generated `for_window` rules work around this by adding `move position 0 0` and `resize set 100 ppt 100 ppt` before `fullscreen enable`, pinning the floating container's geometry to the full output once, at window-creation time — confirmed on sway (swayfx 0.5.3, based on sway 1.11.0) that this combination against a 1920x1080 output produces a 1916x1048 floating rect; i3 shares the same `resize set <w> [px|ppt] <h> [px|ppt]` syntax.

## Fullscreen suppresses tiling layout for the workspace {#fullscreen-suppresses-layout}

A container with `fullscreen_mode=1` suppresses tiling-layout computation entirely for the rest of its workspace, so a sibling window that maps onto the *same* workspace as a persistently-fullscreen tuicc never gets a real rect computed for it — stuck at `{0,0,0,0}` — for as long as tuicc stays fullscreen without interruption. Confirmed live: `preview.py` (which draws windows from their rect) shows nothing for that window, indefinitely, until something forces sway to actually run a layout pass for that workspace (observed happening incidentally on a manual dismiss+resummon, which drops tuicc out of fullscreen entirely and back).

`Provider.focus_self(force_relayout=True)` works around this deliberately: it briefly toggles fullscreen off and back on to force a layout pass, right when a spawn/restore match resolves onto tuicc's own workspace, instead of leaving the window's rect broken until an unrelated dismiss/resummon fixes it as a side effect. Only meaningful combined with `fullscreen=True`; relies on the floating geometry pin above (`install.sh`'s `move position 0 0, resize set 100 ppt 100 ppt`) so the brief non-fullscreen instant it causes has no size to visibly blink through.

## `no_focus` uses pid criteria, and what that costs {#no-focus-pid-criteria}

`no_focus_next_window(pid)` is implemented via `for_window [pid=<pid>] no_focus` on sway/i3 (`no_focus` is i3-native; sway adopted the same directive and criteria syntax), deliberately keyed on `pid` rather than `class`/`app_id`. `class`/`app_id` would keep matching every *future* window of that same app for the rest of the WM session — open it again later, outside tuicc, and it silently won't auto-focus either. `pid` matches exactly the one process this call is about and, barring pid reuse, essentially never anything else again.

Cost: sway/i3 have no IPC command to remove a `for_window` rule once added (only a full WM restart clears them), so these rules accumulate one per spawn for the process's lifetime. At the kernel's modern default `pid_max` (4194304, e.g. NixOS/most current distros), a collision with a stale rule needs years of continuous uptime to become likely even under heavy process-creation load; only the old 32768 default makes this a realistic (if still rare-per-process) concern. A collision's actual damage, if it ever happens, is cosmetic — one unrelated future window silently doesn't auto-focus on creation (Tab/click fixes it), not data loss.

Also silently a no-op for apps that fork/exec into a child with a different pid than the one `spawn_detached()` returned — see `CLAUDE/NOTES/known-limitations.md#fork-exec-pid-mismatch`.

## Dismissed fullscreen window ghosts over a later fullscreen toggle (swayfx 0.5.3 / sway 1.11.0, fixed upstream) {#scratchpad-fullscreen-ghost}

Confirmed live, this session: dismiss tuicc (`fullscreen_only = true`, so it's still `fullscreen_mode: 1` at the moment `dismiss_self()` runs `move scratchpad` on it), then `fullscreen enable` (toggle) on *any* window on the workspace tuicc was last shown on — tuicc visibly renders on top of that window, alpha-blended with whatever `opacity` its own `for_window` rule sets, for a couple of seconds, even though `swaymsg -t get_tree` reports `visible: false` for it the entire time and real keyboard focus stays on the fullscreened window throughout (confirmed via a live 0.15s-interval tree-poll capture — the ghost is real on screen but invisible to sway's own IPC model). Only reproduces on the workspace tuicc was last associated with before being scratched; toggling fullscreen on an unrelated workspace does nothing.

This is not a tuicc bug — it's upstream sway [issue #8972](https://github.com/swaywm/sway/issues/8972) ("fullscreened window moved to scratchpad is displayed when a different window is fullscreened"), reproduced there with the identical minimal steps (fullscreen a window, scratchpad it, fullscreen a different window). Root cause lives in `arrange_root()` (`sway/desktop/transaction.c`), the function that disables the scene-graph nodes of everything currently parked in the scratchpad on each transaction — for a container that was fullscreen at the moment it got scratched, the old code didn't fully disable its scene tree, leaving stale composited content that resurfaces on the next fullscreen transaction elsewhere. Confirmed via `gh api`/`gh pr view` against swaywm/sway directly (not assumed from the issue thread alone): fixed by [PR #9007](https://github.com/swaywm/sway/pull/9007) (`call disable_container in arrange_root`, merged 2026-03-21), present in `sway/desktop/transaction.c` at the `1.12` tag, absent at `1.11.0` (the exact version this session's swayfx 0.5.3 is built on — confirmed by diffing the file at both tags directly, not inferring from release dates alone). **swayfx `0.6`** (released 2026-08-05, 8 days before this entry was written) rebases onto sway `1.12.0` per its own release notes — so it carries the fix.

No tuicc-side workaround was implemented — this is exactly the "known limitation, not fixed with complexity nobody hits" case, since the real fix is a compositor upgrade already published and one version away, not something worth papering over with speculative in-repo code (e.g. an unverified `fullscreen disable` before `move scratchpad` in `dismiss_self()`) when the actual bug lives entirely below sway's own IPC layer and isn't detectable or preventable from tuicc's side at all. If you hit this on a still-older sway/swayfx: upgrade past sway 1.12 / swayfx 0.6; there's nothing to fix in this codebase.

**Upgrade status (as of 2026-08-13, this session's dev machine, NixOS):** swayfx 0.6 is NOT yet in nixpkgs — checked live (`gh api` against `pkgs/by-name/sw/swayfx-unwrapped/package.nix` at the `nixos-unstable` branch tip) still shows `version = "0.5.3"`. The bump exists as an open, mergeable PR ([NixOS/nixpkgs#552219](https://github.com/NixOS/nixpkgs/pull/552219), opened the same day this was written). Considered and rejected: pinning a second `nixpkgs` flake input directly at that PR's fork commit to get 0.6 early via an overlay — technically doable, but the actual `nixos-rebuild switch` needed to apply a `programs.sway.package` change kills the whole running graphical session (everything under sway dies, including whatever this was being investigated from), and building against an unmerged, unreviewed PR branch for that isn't worth the disruption for a cosmetic bug. Decided instead to wait for #552219 to merge and reach `nixos-unstable` normally, then a plain `nix flake update nixpkgs` picks it up — re-check nixpkgs before assuming this is still unpackaged.

## Workspace switch away from fullscreen leaves the destination workspace invisible until forced (swayfx 0.6 / sway 1.12.0, upstream, not tuicc-specific) {#workspace-switch-fullscreen-invisible}

Confirmed live, this session, **without tuicc in the loop at all** — general sway/swayfx behavior, first noticed via tuicc's own "Enter on a sidebar workspace" flow (which always leaves tuicc's own fullscreen container right as it switches focus) but reproducible with nothing but plain `swaymsg workspace number <n>`. Minimal repro: workspace A has a `fullscreen_mode: 1` container and is focused; workspace B (any other, non-fullscreen, with real windows on it) is not focused. `swaymsg workspace number <B>` switches focus/visibility to B successfully per IPC (`get_workspaces` reports `focused: true`, and every window on B reports `visible: true` in `get_tree`) — but the *actual composited output* shows nothing but the wallpaper where B's windows should be. Not a subtle rendering glitch (dimmed border, partial content) — full invisibility, confirmed via `grim` screenshot taken ~0.3s after the switch, correlated against a `get_tree` dump from the same moment showing `visible: true`/correct `rect` for both windows on B.

Confirmed live NOT wallpaper-related: this machine normally runs an animated `mpvpaper` background, but swapping it out for a plain static `swaybg` (same output, same repro steps) reproduced the identical invisibility — rules out "stale wallpaper repaint frame" as the mechanism, since the wallpaper layer itself was static/trivially correct in this variant and the window content still failed to composite.

Not confirmed whether this is swayfx-specific or affects vanilla sway too. One exploratory attempt: a nested vanilla sway 1.12 instance (run as a Wayland client inside this same swayfx session, not a real DRM session) got exactly one clean trial before an unrelated side effect (repeatedly driving the nested instance's own IPC socket caused the *outer* swayfx session's own keyboard/window focus to steal away mid-test) made further trials unreliable before a real 3/3 could be collected. That one trial did NOT reproduce the bug — a weak lead toward "swayfx-specific," not a confirmed result. A real (non-nested, actual DRM) vanilla sway session is needed to settle this properly.

**Mitigations tried and rejected, in order, all live-tested 2026-08-27:**
1. Bounce through a third workspace AFTER switching (`workspace B` → `workspace C` → `workspace B`). Worked in careful manual testing (with ~0.2-0.3s pauses between each `swaymsg` call) but proved unreliable once implemented as three back-to-back IPC commands with no delay — almost certainly because sway coalesces rapid-fire `workspace` commands into effectively one transition, since nothing forces each one to actually settle before the next fires. Reverted.
2. Nudging the pointer (`seat seat0 cursor move`), on the theory that pointer motion forces a compositor repaint (this is the documented fix for the *old*, related, already-fixed sway#665). Live-confirmed to do **nothing** — Rafi could see swayfx's own decoration/focus-shadow layer redraw on cursor motion, but the actual window content stayed invisible. Useful negative result: it rules out "the compositor just needs any repaint nudge" as the mechanism — something more specific is broken.

**Third mitigation tried and ALSO rejected, but only after it shipped and got live-tested more:** explicitly drop fullscreen (`[con_mark=...] fullscreen disable`) on the about-to-be-hidden window and confirm it settled, BEFORE switching workspace at all. Manually verified working two ways at the time: (a) the general repro (this section's own minimal steps) fixed cleanly when fullscreen was dropped pre-switch; (b) directly on the broken/invisible destination window itself — `fullscreen enable` on it makes its real content appear immediately, and `fullscreen disable` on that same window (still without switching away) makes it revert to invisible again, showing this isn't "broken once, fixed once" but a compositing path that stays broken until something resets it. This shipped as `Provider.leave_fullscreen_self()`, with a poll-based confirm (`_self_still_fullscreen()`) replacing an initial blind `time.sleep(0.05)` that had been live-found insufficient on the very first call after a fresh launch.

**Then live-found to have traded one bug for another, closely-related one.** Reproduced live (2026-08-27, Rafi, on tuicc's real first-launch flow): workspace switched correctly, but tuicc's OWN window kept rendering as a translucent ghost on top of the real destination content — confirmed via `get_tree` showing tuicc genuinely `visible: false`/scratchpadded/`fullscreen_mode: 0` (the WM model was already fully correct) while a live `grim` screenshot, taken well over a minute later, still showed tuicc's sidebar faintly composited over the real window underneath. This is the exact same "IPC says one thing, the screen shows another" signature as the rest of this section, just relocated: explicitly calling `fullscreen disable` on a window that's currently being scanned out is ITSELF a scanout→composited transition on that window's own then-current workspace — the exact transition the root cause below is missing the damage call for. `leave_fullscreen_self()` was fixing the destination by moving the same bug onto tuicc's own window instead of avoiding it.

**What actually ships, live-confirmed 4/4 including the exact fresh-launch case that broke the mitigation above:** don't touch fullscreen at all — call `dismiss_self()` (plain `[con_mark=...] move scratchpad`, unchanged) BEFORE `focus_region()`/`focus_window()`, instead of after. `move scratchpad` alone, with the window still genuinely `fullscreen_mode: 1` at the moment it's called, correctly clears fullscreen and avoids the ghost — reproducibly, with zero delay between the two commands, including the cold-first-launch timing that broke the sleep-based version. Working explanation (not verified against source the way the root cause below is): removing a container from a workspace's render list entirely is a structurally different, much more fundamental operation than toggling a `fullscreen_mode` flag on a container that stays in the tree — container removal almost certainly already goes through well-tested damage/reparent handling, sidestepping the narrow `prev_scanout`-transition gap entirely, while an explicit flag toggle on a persisting node walks straight into it.

**Root cause, confirmed directly against source (`curl` + grep on the real files, not an LLM summary — the first attempt at this WAS an LLM-summarized fetch and it was WRONG, claimed `prev_scanout` didn't exist in scenefx's file at all; always re-verify a source claim like this against the raw text directly before trusting it).** `wlrfx/scenefx`'s fork of `types/scene/wlr_scene.c` (scenefx replaces wlroots' own `wlr_scene` with its own fork to add blur/shadow/corner-radius — swayfx uses scenefx, not plain wlroots, for exactly this file) is missing one thing upstream wlroots has. Upstream (`swaywm/wlroots`, `types/scene/wlr_scene.c`, `wlr_scene_output_commit`):

```c
bool scanout = scene_output_scanout(scene_output);
if (scanout != scene_output->prev_scanout) {
    wlr_log(WLR_DEBUG, "Direct scan-out %s", scanout ? "enabled" : "disabled");
    // When exiting direct scan-out, damage everything
    wlr_output_damage_add_whole(scene_output->damage);
}
scene_output->prev_scanout = scanout;
```

scenefx's equivalent (same file, ~line 3225, the frame-commit path):

```c
bool scanout = scanout_result == SCANOUT_SUCCESS;
if (scene_output->prev_scanout != scanout) {
    scene_output->prev_scanout = scanout;
    wlr_log(WLR_DEBUG, "Direct scan-out %s",
        scanout ? "enabled" : "disabled");
}
```

scenefx logs the scanout→composited transition but never calls the whole-output-damage equivalent upstream calls right there (`wlr_output_damage_add_whole` in that older wlroots damage API — scenefx's own file already defines and uses `scene_output_damage_whole(scene_output)` elsewhere for other cases, e.g. geometry changes, just not this one). Without it, the first frame back in normal compositing mode has no damage region for whatever was being scanned out, so the renderer skips redrawing that area entirely — explains every observation in this section: swayfx's own decoration/shadow layer (`output_configure_scene()`, a separate code path, config-driven not damage-driven) always redraws regardless; a window's content only ever shows while it's the one actively being scanned out (`fullscreen enable` → real content, immediately, every time); turning it back off returns to the same permanently-undamaged compositing path, not a one-time fixable state. This is a one-line-fix-shaped bug (call the existing `scene_output_damage_whole()` on the same transition upstream damages), not an architectural one — worth leading with in the upstream report.

**Implemented:** `actions.py`'s `_handle_region`/`_handle_window` (region/window `target_kind` handlers — the concrete case is tuicc's own "Enter on a sidebar workspace") call `ctx.provider.dismiss_self()` BEFORE `focus_region()`/`focus_window()`, instead of relying solely on `main.py`'s own post-dispatch `dismiss_self()` call (which still runs too, afterward, as a harmless no-op repeat — its `dismissed=True` bookkeeping stays intact). No new `Provider` method, no fullscreen-specific logic anywhere in the fix — just reordering two calls that already existed. `Provider.dismiss_self()` itself is unchanged (still just `[con_mark=...] move scratchpad`, same as ever); nothing here is sway-specific in the *code*, only in *why it matters* (i3 has never shown this bug, so the reordering is a no-op improvement there rather than a targeted fix, and costs nothing extra to leave in place for both providers).

This is the SIMPLER of the two options Rafi and this session weighed explicitly before either was tried: reorder existing calls (his own original suggestion) vs. add dedicated fullscreen-handling infrastructure. The dedicated-infrastructure path was tried first anyway (see above) specifically because of an at-the-time-reasonable but ultimately wrong worry — that `move scratchpad` doesn't clear `fullscreen_mode` on its own (true per `#scratchpad-fullscreen-ghost` above, on swayfx 0.5.3/sway 1.11.0) and so reordering alone might not be enough. Live-tested on swayfx 0.6/sway 1.12.0: it clears fullscreen correctly and avoids the scanout-exit bug entirely, 4/4 trials including the exact cold-launch timing that broke the fullscreen-disable version. Whether that's a genuine 0.5.3→0.6 behavior change or was never quite what the older note implied is unconfirmed — noted here so a future session doesn't re-import the old worry unexamined.

A GitHub issue draft (repro steps without tuicc, screenshots) was prepared 2026-08-27 but deliberately not yet filed — see chat history / ask Rafi before submitting upstream. Filing it is still worth doing even with the mitigation in place — the root cause above (direct scanout not properly released) would make a genuinely useful lead to hand upstream, and this affects every sway/swayfx user hitting the same pattern outside tuicc, not just tuicc's own workaround.

## `for_window` rules must be split, not comma-chained {#for-window-chained-actions}

`for_window [crit] floating enable, fullscreen enable` (or the fuller chain with move/resize too) as a single rule reports every action as `"success": true`, but the window that actually maps ends up neither floating-sized nor fullscreen — `fullscreen_mode` stays `0`. Splitting the exact same actions into separate `for_window` rules against the same criteria reliably produces the correct end state — confirmed 3/3 repeated tries on swayfx 0.5.3 (based on sway 1.11.0, not vanilla sway). Whether this is a swayfx-specific quirk or also affects vanilla sway/i3 is not yet confirmed — see `CLAUDE/I3_TESTING_LOG.md`. `install.sh`/README generate the split form regardless of WM, since it costs nothing extra even where the chained form would've worked fine.
