# Known limitations

Gaps that are understood and accepted (or not yet fixed), not silent bugs waiting to be found. Each section is a stable anchor (`CLAUDE/NOTES/known-limitations.md#anchor`).

## `mark_self()`'s focus-based fallback race {#mark-self-focus-race}

`Provider.mark_self(app_id=None)` (the default when `[wm] self_app_id` isn't set in config.toml) assumes tuicc's own window is whichever one is currently focused at call time. Launching several tuicc instances back-to-back can race this assumption — whichever instance calls `mark_self()` last "wins" the currently-focused window, regardless of which one actually owns it.

Passing `app_id` (sway/i3 mark by WM criteria — `app_id`/`class` respectively — instead of "whatever's focused") removes the race entirely. This is why `install.sh` and README's launch commands set `[wm] self_app_id` for the documented scratchpad launch (`kitty --app-id tuicc_scratch`). The focus-based fallback stays as a documented degraded case for setups that don't set it, not a crash.

Confirmed on sway, not just a rapid-back-to-back-launch edge case: a single ordinary launch (one instance, keybind-paced) hit it when a slow-to-yield-focus app (VS Code) still held focus for a moment as tuicc started — tuicc marked that window as itself instead, and it silently vanished from tuicc's own sidebar/window lists (no error, no crash) until the stray mark was found via a tree poll and removed by hand. Same underlying mechanism applies on i3 (X11 focus timing is just as racy as sway/Wayland's). The pid suffix in the mark string prevents mark *collisions* between tuicc instances, not this timing assumption — a real fix needs identifying "my own window" independent of focus timing, which is exactly what `self_app_id` does.

A `[pid=...]` for_window rule (the same trick `no_focus_next_window` uses) does not generalize to fixing this the same way: that pid comes from `spawn_detached()`'s own return value (the process that owns the resulting window), but `mark_self()` runs from *inside* tuicc, typically wrapped in a terminal (`kitty -e python main.py`) — `os.getpid()` there is Python's own pid, a child of the terminal, not the terminal's own pid that i3's window `pid` field actually reports.

**Update, 2026-08-18: auto-cleanup landed, the race itself is still unfixed.** `Provider.cleanup_stale_self_marks()` (called once at startup, right before `mark_self()`) now strips a leftover `_tuicc_self_<pid>` mark sitting on the WRONG window — found live again, the exact same failure mode described above (a real VS Code window vanished from tuicc's own sidebar with no error, caused this time by several ad-hoc test launches with no `self_app_id` set). It works by comparing the mark's own embedded pid against the window's REAL owning pid (sway: native `Window.pid`; i3: `resolve_pid()`'s existing X11 lookup, inconclusive treated as "leave it alone" — never assumed stale) — no liveness probing needed, a mismatch is unambiguous proof regardless of whether the offending old process is still running. This closes the *lingering damage* (a bad mark surviving indefinitely into future sessions) but does **not** close the race itself — a launch racing focus RIGHT NOW can still mismark a window for the remainder of THAT session, until the next tuicc startup's cleanup pass catches it. `self_app_id` remains the only way to prevent the race from happening at all.

## Fork/exec pid-mismatch apps silently fail to relocate — resolved {#fork-exec-pid-mismatch}

Reliably reproduced (deterministically, 3/3 runs) with a wrapper script that backgrounds its real child instead of exec-replacing itself: `spawn_detached()`'s captured pid never matches the window's real owning pid. If the app's real `app_id` *also* doesn't match the launcher's `.desktop`-derived hint, `resolve_pending_move()` never reached its "any remaining unclaimed window" fallback tier — that tier only ever triggers when **both** `pid` and `app_id` are `None` on the entry, and an app_id-mismatch-but-not-`None` entry never got there. The window sat on tuicc's own workspace, unrelocated, until `MOVE_TIMEOUT_SECONDS` passed and the entry was silently dropped.

**Confirmed real-world trigger, 2026-08-22: Discord.** Live-reported by Rafi — launched from tuicc on ws1, targeting ws3. The updater window landed correctly on ws3 (its pid/app_id matched fine). The real Discord app that the updater spawns afterward did not: it landed on ws1 (tuicc's own workspace), unrelocated, exactly this mechanism. Discord's own installer additionally opened an unrelated Firefox tab on ws1 — that part is Discord's own behavior (its updater/crash-handler reaching for a browser), not caused by or fixable from tuicc's side at all.

Also suspected, not yet confirmed to be this exact mechanism: OnlyOffice (could also just be a very slow cold start exceeding the timeout).

**Fixed, same day, once a real trigger existed to design against — took two real attempts, the first one live-caught as still broken before landing.** The originally-proposed fix here (a last-resort escalation to the "any remaining" tier right before timeout) was rejected in favor of something faster and more precise, in two parts:

1. `pending_moves.py`'s `_grow_known_pids()` tracks the captured pid's WHOLE observed descendant tree every frame (~50ms while anything's pending), reusing `procmon.py`'s own `scan_all_processes()`/`build_children_map()`/`subtree_pids()` — built for R6's per-window process-subtree aggregation, now promoted to public (`build_children_map`, dropped its leading underscore) so this module can reuse it directly. Each entry's `known_pids` set is grown (unioned), never recomputed from scratch — essential, not just tidier: live-verified (real `/proc`, a real forked child, not a mock) that once the parent that spawned it exits, the child gets reparented to init/a subreaper and a *fresh* subtree walk from the original pid no longer finds it at all. `resolve_pending_move()`'s pid-tier matches against `known_pids` instead of exact pid equality.

2. **Found still broken on the first live test through tuicc itself** (a purpose-built mock app, `IFTNTSMWTISA.py` — see below): part 1 alone tracks the pid tree correctly, but `process()` used to drop an entry from the queue the INSTANT it matched any window — exactly what happens to the updater's own window, almost immediately, long before the real app has even been forked yet. By the time the real app's window actually mapped seconds later, nothing was tracking it anymore; it landed unrelocated exactly as before this fix existed. `process()` now keeps every matched entry pending for `SETTLE_SECONDS` after its most recent match, watching for one more — deliberately unconditional (not gated on `known_pids` already showing a descendant, which was the first, still-broken attempt: that evidence doesn't exist yet at the moment of the FIRST match, so gating on it never actually triggers for the real timing). The accepted cost is a few extra seconds of fast polling after every launcher spawn, not just ones that turn out to need it. A quick-exit clean-exit downgrade (to app_id-tier) is similarly now skipped once a real descendant has been observed, so it can't undo what `known_pids` already learned.

**Verified live, end to end, through the real code path** (not mocked): `IFTNTSMWTISA.py` ("I Feel The Need To Spawm More Windows Than I Should App") is a small mock fixture that reproduces the exact pattern on demand — `os.execvp()`'s itself into a kitty window (stage 1, "the updater"), waits a few seconds, then `setsid`s a genuinely separate process (stage 2, "the real app", several generations removed by the time IT execs into its own kitty window) with a deliberately mismatched `app_id`. Installed as a real `.desktop` entry (`~/.local/bin/IFTNTSMWTISA.py` + `~/.local/share/applications/iftntsmwtisa.desktop`) so it's launchable from tuicc's own launcher like any other app. Driven against Rafi's real, live sway session (a script that runs `pending_moves.process()` in the same loop shape `main.py` does, against a real `SwayProvider`, no mocking) — both stage 1 and stage 2's windows resolved to the same target workspace, at t≈0.6s and t≈4.5s respectively.

The same pid-mismatch gap silently no-ops `no_focus_next_window()` too (see `CLAUDE/NOTES/wm-quirks.md#no-focus-pid-criteria`) — not a new gap, the same underlying mismatch.

**Not fixed by `pending_moves.py`'s quick-exit detection** (`CLAUDE/NOTES/design-decisions.md#pending-moves-quick-exit-detection`), which resolves a related but different mechanism: an app (VS Code's NixOS wrapper, live-confirmed) whose captured process itself exits cleanly after handing a new-window request off to an already-running instance via its own IPC. That fix works because the captured pid actually *exits* — `_check_quick_exit()` can observe that and react immediately. The wrapper-backgrounds-its-child case documented above is different: the captured pid never exits at all (it keeps running as a supervisor/wrapper), so `_check_quick_exit()`'s `os.waitpid(pid, os.WNOHANG)` just keeps returning "still running," forever — the unchanged `PID_GRACE_SECONDS` timer remains the only downgrade path for this class, exactly as before.

## `for_window` rules accumulate for the WM session {#for-window-accumulation}

sway/i3 have no IPC command to remove a `for_window` rule once added — only a full WM restart clears them. `no_focus_next_window()` adds one such rule per spawn, for the lifetime of the WM session. See `CLAUDE/NOTES/wm-quirks.md#no-focus-pid-criteria` for the collision-probability math and why this is an accepted tradeoff rather than a bug to fix.

## Session-restore relaunch can silently crash for wrapper-launched apps {#restore-relaunch-crash}

`promote_restore_queue()` relaunches a saved session entry from its captured `cmdline`. A match that never happens looks identical from the outside whether the process never started or started and immediately died — confirmed concretely: a saved Obsidian entry's cmdline (`electron <asar path>`), relaunched exactly as captured, crashes with `Cannot find module 'electron'`. The real launcher is a wrapper script (NixOS packages Electron apps this way) that sets up environment before exec'ing into that same binary — invisible to `/proc/<pid>/cmdline`, which only ever captures argv *after* that exec.

Every restore spawn gets a log_path under `SPAWN_LOG_DIR` (named by app_id + wall-clock time, known before the pid is) so a crash like this is at least diagnosable after the fact. `session_entry.get("env")` (session.py's captured `/proc/<pid>/environ` snapshot) is threaded through `spawn_detached()` for the same reason — `None` for entries saved before this existed, or where the environ read failed, falls back to "just use the current environment."

## i3's pid enrichment is scoped to just-spawned windows, not every open window {#pid-enrichment-scope}

`_enrich_pids()` only fills in `.pid` for windows not yet seen by any pending entry and not already claimed — typically 0-1 windows, not every window on the desktop. This scoping matters on a provider whose `get_state()` never populates pid at all (i3 today): without it, every pending entry would burn the full `PID_GRACE_SECONDS` before downgrading to the app_id tier, and if the spawned app's real app_id doesn't match its `.desktop` hint (common for Python/Electron apps launched via a bare interpreter), it would never resolve, silently dropped after `MOVE_TIMEOUT_SECONDS`. A spawn timing out this way leaves its window sitting wherever the WM naturally opened it — typically tuicc's own workspace — with no resolved match to move it, which also happens to be the trigger for the unrelated-looking symptom of tuicc losing fullscreen (a new tiled window landing on its own workspace; see `CLAUDE/NOTES/wm-quirks.md#fullscreen-suppresses-layout`).

`provider.resolve_pid()` defaults to a no-op returning `None` for providers that don't need it (sway's windows already carry a real pid from `get_state()`), so calling `_enrich_pids()` unconditionally is safe everywhere — just a no-op where it isn't needed.

## pyudev's `libudev.so` isn't always ctypes-discoverable on NixOS {#pyudev-libudev-nixos}

`battery.watch()` is pyudev-backed now (see `CLAUDE/NOTES/design-decisions.md#battery-push-pyudev` for the full story — the earlier sysfs `select.poll()` attempt this replaced, confirmed unreliable on real hardware, is history there, not repeated here). `pyudev.Context()` lazily `dlopen()`s the real `libudev.so` via `ctypes.util.find_library()` the first time it's constructed — this can fail even when the `pyudev` Python package itself is installed and importable fine. Confirmed live in this project's own dev environment: a plain `pip install pyudev` into `.venv` imports cleanly, but `pyudev.Context()` raises `ImportError("No library named udev")`, because NixOS doesn't populate `ldconfig`/the standard FHS search paths `ctypes.util.find_library()` relies on, unlike most other distros. `nix-shell -p 'python3.withPackages (ps: [ps.pyudev])'` links it correctly (Nix's own Python package wrapping handles this), confirming the mechanism itself is sound — this is a packaging/library-discovery gap specific to running a plain pip-installed `pyudev` from a NixOS system Python, not a flaw in pyudev or in `battery.watch()`'s own design.

`battery.PYUDEV_AVAILABLE` probes this for real (constructs a throwaway `Context()`, not just checking the bare import) specifically so this degrades automatically — see `battery.py`'s own docstring. On an affected machine, tuicc keeps working exactly as before (battery on plain `StatusWorker` polling, `poll_interval=0.3`), with zero crash and zero manual intervention required. The only thing lost is the event-driven low-latency win pyudev would otherwise provide. Fixing it for real (so the push path actually engages) needs one of: `LD_LIBRARY_PATH` pointed at the nix store's `systemd` (or `eudev`) `lib` output, or launching tuicc via a nix-provided Python that already has `pyudev` wired correctly instead of the plain `.venv`/pip install — neither attempted as part of landing this feature, left as an optional, one-time environment fix for whoever wants the faster path active on a NixOS machine specifically.

## Agent shutdown replies to pending requests before disconnecting {#agent-shutdown-cancels-pending}

`IwdAgent.stop()`/`BluezAgent.stop()` reply to any still-pending request with a Canceled error *before* tearing the D-Bus connection down. Without this — main.py's `finally` block or a plain Ctrl+C calling `stop()` while a passphrase/pairing overlay is still open — the connection used to just close out from under iwd/bluez, leaving its own blocked `Network.Connect()`/pairing call waiting on a peer that had simply vanished mid-request instead of getting a normal, in-protocol answer. This is a suspected (not proven — no way to reproduce a daemon segfault on demand) trigger for a real iwd crash (SIGSEGV, systemd auto-restarted it) encountered during exactly this kind of abrupt-disconnect testing. Even setting the crash risk aside, there's no reason to rely on iwd/bluez handling a dropped peer gracefully when a clean Canceled reply costs nothing. Best-effort `UnregisterAgent` happens afterward — the connection is being torn down either way, so a failure there (daemon already gone, bus already closing) isn't worth surfacing.

## Resummon can keep a stale workspace selection {#stale-resummon-selection}

Reported on both sway and i3: dismissing tuicc and re-summoning it sometimes shows the sidebar still selected on whatever workspace was selected *before* dismiss, not necessarily matching real current WM focus. Never conclusively root-caused — could be a real bug in the focus-change detector, or could be correct behavior that looked like a bug because real focus happened to coincide. Needs a clean, deliberate repro (dismiss tuicc while workspace A is selected in the sidebar, switch WM focus to workspace B via a non-tuicc means, re-summon, check what's selected) before concluding anything.

## `dismissed`'s reset timing lags one keypress behind resummon {#dismissed-reset-timing}

`dismissed` (main.py) is true from `dismiss_self()` until the next real keypress — it tells `pending_moves.process()` not to call `focus_self()` while tuicc is deliberately hidden, since focusing a scratchpadded window un-hides it on sway/i3. It resets on the next **keypress**, not the next **resummon**: a pending-moves entry that resolves after you've resummoned tuicc but before pressing anything still skips `focus_self()`, even though tuicc is genuinely visible again. Narrow (needs the spawned window to finish moving in that exact gap) and not tightened further — same accepted-race category as `mark_self()`'s focus-based fallback (`#mark-self-focus-race` above).

## `connect_hidden()` silent-failure gaps, unverified and deferred {#connect-hidden-silent-failure}

Backlogged deliberately (Rafi's own call — he doesn't use hidden networks and has no way to test this locally right now), not fixed speculatively. Two known, real gaps in `IwdBackend.connect_hidden()` (`connectivity/iwd.py`), found by inspection while explaining the feature, neither live-confirmed:

1. **No false-success post-check.** `IwdBackend.connect()` does its own post-attempt verification (`_connect_succeeded()`) specifically because `Network.Connect()` returns cleanly even on a wrong passphrase — confirmed live, deterministically (`#iwd-connect-false-success` above). `connect_hidden()` calls `Station.ConnectHiddenNetwork()` with no equivalent check. If that method shares the same underlying auth machinery (plausible — same Station interface — but not confirmed), a wrong passphrase on a hidden network would raise no exception, `StatusWorker` would record success, and the passphrase overlay would just silently close as if it connected. Proposed fix, not implemented: after `ConnectHiddenNetwork()` returns, read `Station.ConnectedNetwork`, then that path's own `Network.Name`, and compare against the typed ssid (can't compare by path the way `connect()` does — a hidden network was never in `GetOrderedNetworks()` to have a known path in the first place).

2. **Failures with no NavItem to show them on.** A hidden network never appears in `ctx.wifi_networks` (`get_networks()` only walks `Station.GetOrderedNetworks()`, i.e. scanned/visible networks) — so if `connect_hidden()` fails via a real raised exception (SSID genuinely not in range, any D-Bus error) *before* an agent passphrase prompt ever opens, `StatusWorker` records the action error correctly, but no row exists anywhere in the UI to read `get_action_error_for()` off of. Fully silent: the browsing view just sits there, nothing happens. Needs a toast-style mechanism (`frame_update.py` watching the specific pending `("wifi", ssid)` key and surfacing via `loop_state.resize_message` on failure) that doesn't exist yet — not attempted, since gap 1 needs the same live-testing access to validate a fix against.

## WiFi radio power toggle — resolved, re-enabled {#wifi-power-toggle-disabled}

`wifi_power_toggle` (`o` while browsing WiFi) called `WifiBackend.set_powered()`. Live-confirmed on Rafi's own machine (2026-08-15): a single press broke networking badly enough to need a full reboot to recover, AND left tuicc's own UI stuck on repeated re-entry (had to Ctrl+C) — two separate bugs, BOTH now root-caused, fixed, and live-confirmed working (including turning the radio off and back on again with no reboot needed).

**Root cause #1 — the network break.** `journalctl -b -1` (the boot before the reboot) showed the kernel side went cleanly: `wlan0: deauthenticating ... by local choice (Reason: 3=DEAUTH_LEAVING)`, then silence — no crash, no rfkill event, nothing. Read-only `busctl introspect net.connman.iwd` found the real bug: iwd exposes **two separate, both-writable** `Powered` booleans — `net.connman.iwd.Adapter.Powered` (the whole physical PHY, e.g. "phy0") and `net.connman.iwd.Device.Powered` (just the one station device, "wlan0"). The original `set_powered()` targeted **Adapter.Powered** — the more drastic, whole-radio one — instead of the narrower Device-scoped one a "turn wifi off" UI control should mean. Confirmed against impala's own `iwdrs` Rust crate source (`pythops/iwdrs`, `src/device.rs`): its own `is_powered()`/`set_power()` target `Device`, not `Adapter`, corroborating the fix.

**Root cause #2 — power back on doing nothing, and a mid-browse focus jump.** Fixing #1 alone left two more symptoms on retest: pressing `o` again once the radio was off did nothing at all, and browsing into WiFi with the radio off threw focus to the sidebar. Both traced to the same thing: iwd **removes the `net.connman.iwd.Station` interface entirely** from the device object when it's powered off (confirmed live via `busctl introspect` — the interface is genuinely gone, not just reporting empty state) — but `set_powered()`/`get_adapter_info()` both located the device via `_find_station_path()` (which searches for that same Station interface), so once the radio was off, that lookup returned `None` and every subsequent call silently no-opped. Fixed by adding `_find_device_path()` — searches for the `net.connman.iwd.Device` interface instead, which persists across power state — and switching `set_powered()`/`get_adapter_info()` to use it. The focus-jump was a second, compounding bug on top: `frame_update.py`'s generic stale-selection recovery reassigned `loop_state.selected_id` to an unrelated module whenever the browsed section's item list emptied out (no networks visible with the radio off) while `mode_stack` kept the browsing claim active — fixed via `handle_wifi_header`/`handle_bt_header` always setting `reselect_item_id` (previously left unset when empty) plus a proactive `frame_update.py` block keeping `selected_id` in sync with the browsed section's real item count every frame.

Also fixed while in here (real, independent of the above): `get_adapter_info()` did two separate full `GetManagedObjects()` tree walks per poll (once via `_find_station_path`, once via `_find_adapter_path`) — now reuses the station Device's own `Adapter` property (its parent's object path, already present in the same `GetAll` reply) instead, falling back to the tree walk only when there's no station to read it off.

Re-enabled at the key-dispatch level (`main.py`'s `handle_connectivity_browsing`, the `wifi_power_toggle` branch). Polish added once the fix was confirmed working: a "Powering on…"/"Powering off…" progress line (`_power_progress_line()`, `pending_key="power"`) shows mid-toggle, and `_browsing_hint_footer()` narrows to just `[O] Power   [Esc] Back` while the radio is off — Scan/Hidden/Forget can't do anything without a radio, so offering them read as actively confusing rather than just unhelpful.

Confirmed live, this session, both directions (off→on and on→off), no reboot needed either time.

## `weather.resolve_from_geoclue()` is not yet live-verified {#weather-geoclue-unverified}

Implemented against the documented `org.freedesktop.GeoClue2` D-Bus API (`Manager.GetClient()` → `Start()` → bounded-wait poll of the `Location` property → read `Latitude`/`Longitude` → `Stop()`), following the same request-response `jeepney` pattern as `media/mpris.py`, but never exercised against a real, working GeoClue2 daemon this session — the same machine's own GeoClue2 setup status is unknown (see the gammastep/Night Light example's own real error, `"GeoClue2 provider is not installed!"`, confirming at least one machine touched by this project genuinely lacks it). If `geoclue = true` doesn't work as expected — a raised error is the honest, intended behavior (see `CLAUDE/NOTES/design-decisions.md#weather-location-sources`), but the exact error text/behavior hasn't been confirmed against a real daemon. Worth a real test on a machine with GeoClue2 actually configured (verify with `gdbus introspect --system --dest org.freedesktop.GeoClue2 --object-path /org/freedesktop/GeoClue2/Manager` that the service is even present first) before trusting this path blindly. `lat`/`lon` and `ip_approx` are both live-verified (real HTTP fixtures, live-tested caching behavior).

## Layout squeeze/chain: two flexible boxes never protect each other {#layout-flexible-vs-flexible-unprotected}

`layout_engine.py`'s `compute_boxes()` (see its own module docstring for the full three-exception mechanism — fixed-box edge-hold, flexible-box squeeze, fixed-vs-fixed chaining) deliberately only reacts a flexible (`h`/`w`, not `fh`/`fw`) box against a FIXED neighbor on the resolving axis, never against another flexible box, even one it genuinely overlaps. Found live: letting flexible boxes react to each other too (the original, more general design) broke `control`/`power_menu` — their already-accepted, honest row-axis "can't fit" overlap (see this same file's own degrade case) also spuriously triggered a completely unrelated column-axis squeeze between them, since both still carried plain (non-`fw`) width at the time. Restricting exception 2 to "flexible reacts only to fixed" removed that whole bug class outright, and cost nothing in the packaged preset — no two flexible boxes have ever actually shared space on the same axis there.

The real, live consequence: if a future preset (hand-edited or via several F2 sessions) ends up with two genuinely flexible boxes (both `h`, or both `w`) whose ranges truly overlap on some terminal size, **nothing catches it** — they will visibly overlap on that size, silently, no different from how boxes behaved before any of this squeeze/chain work existed. This is the one case in the whole mechanism that can still surprise someone authoring a preset by hand; every other box in the system (fixed-vs-fixed, flexible-vs-fixed) is actively protected. Revisit only if a real preset actually needs two mutually-overlapping flexible boxes — no such case exists today, and solving it well (without reintroducing the control/power_menu bug) needs more design than a quick patch.

## Layout squeeze/chain: a fixed stack that genuinely doesn't fit still overlaps, on purpose {#layout-fixed-stack-cannot-fit}

Two (or more) `fh`/`fw` boxes chained directly on top of/next to each other (exception 3, e.g. `control` above `power_menu`) hold a clean, non-overlapping stack all the way down to the terminal size where their combined fixed size genuinely no longer fits (8+6=14 rows for that pair). Below that size, the box nearest the terminal's near edge clamps at 0 and the stack **does** visibly overlap — this is accepted, not a bug: neither box can shrink by definition, so there is no non-overlapping answer once the terminal is that small. Same, deterministic outcome every time for a given size — not flaky, just visually broken on a terminal too small for what's configured. `pick_preset_for_size`'s `[preset] min_cols`/`min_rows` (see `presets/1.toml`'s own comment) is the intended fix for a user who regularly hits this: ship a second, smaller preset for a known small terminal instead of relying on this degradation to look good.
