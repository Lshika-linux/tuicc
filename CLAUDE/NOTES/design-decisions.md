# Design decisions

Why things are shaped the way they are, when the reasoning isn't obvious from reading the code. Each section is a stable anchor (`CLAUDE/NOTES/design-decisions.md#anchor`).

## Dismiss vs. quit {#dismiss-vs-quit}

tuicc's main loop, once started, is never expected to exit in normal use. Every handler's `should_dismiss` bit (renamed from `should_exit`) means "call `Provider.dismiss_self()` and keep looping," not "terminate." `main.py`'s `while True:` has no `break` in it anywhere — the only way out is an unhandled exception, which in practice means Ctrl+C, caught quietly at the bottom of `main.py` with a `try/finally` around the loop for cleanup. See `CLAUDE/VISION.md` section 2 for the full lifecycle model this comes from.

## Optional `Provider` methods default to a documented no-op, not `abstractmethod` {#optional-provider-methods}

`mark_self()`, `dismiss_self()`, `focus_self()`, `no_focus_next_window()`, `resolve_pid()`, and `set_floating_geometry()` on `Provider` (`providers/base.py`) all default to a no-op (or `None`) rather than being abstract. Each covers a WM capability that not every window manager has an equivalent for (marks, scratchpad-style hiding, focus stealing back, per-window no-autofocus hints, non-native pid lookup, floating geometry). A provider for a WM lacking the concept simply inherits the default and accepts the resulting degraded case — tuicc shows up in its own preview, a launcher spawn's focus briefly wobbles, a restored floating window lands at the WM's default geometry instead of its saved one — never a crash. This is deliberately different from `close_window()`, which stays `abstractmethod`: every WM worth supporting can close a window, so there's no meaningful degraded case to fall back to there.

Severity varies sharply across this group even though the mechanism (no-op default) is the same: `focus_self()`'s degraded case is severe enough to call out explicitly (see `CLAUDE/NOTES/wm-quirks.md#focus-on-map-stealing`) where `mark_self()`'s or `set_floating_geometry()`'s are minor and cosmetic.

## `no_focus_next_window` is keyed on pid, not class/app_id {#pid-vs-class-criteria}

See `CLAUDE/NOTES/wm-quirks.md#no-focus-pid-criteria` for the full tradeoff — the short version: `pid` matches exactly one process and effectively never collides again, where `class`/`app_id` would keep matching every future window of that app for the rest of the WM session.

## `pending_moves.py`: pid > app_id > any-remaining matching tiers {#pending-move-tiers}

`resolve_pending_move()` matches a spawned process back to its window in three exclusive tiers, each only considering windows not already claimed by another entry: (1) exact pid match — unambiguous, but only available when the provider exposes `Window.pid` and the process wasn't launched via a shell; (2) app_id match — distinguishes the expected app from an unrelated new window, but not from a second simultaneous instance of the *same* app_id; (3) any remaining unclaimed new window — last resort.

The tiers are exclusive, not a cascade: an entry expecting a specific pid/app_id waits for exactly that (or times out in the caller) rather than settling for a weaker signal because its own match hasn't appeared yet on this tick. Falling through early looks fine until two entries share an app_id (e.g. two `kitty` launches) and one's window is simply slower to appear — a premature fallback then hands it the wrong entry's window. This exact bug reassigned 3 of 10 windows to the wrong workspace in a burst-launch test before the exclusive-tier fix.

Same-app_id entries not colliding at the app_id tier relies on callers processing pending entries in order, each claiming its match before the next entry looks — `resolve_pending_move()` itself has no notion of which window actually appeared first in real time, it just picks the first unclaimed match available to it. Two simultaneous instances of the same app_id landing on each other's targets (rather than crashing) is an accepted tradeoff, not a bug, as long as both instances are otherwise identical.

`resolve_pending_move()` doesn't mutate `claimed` itself — the caller adds the result's id only once it commits to the match (calls `move_window_to_region`), so a per-tier scan here never leaves a side effect to undo if the caller doesn't use the result.

The app_id tier compares case-insensitively, found live while re-verifying `#pending-moves-quick-exit-detection`'s own VS Code repro: its `.desktop` declares `StartupWMClass=Code`, but the real window's runtime app_id is `code` — an exact-case match waited forever for a window that could never satisfy it, independent of and stacked on top of the pid-tier failure the quick-exit fix addresses. A different problem from the fork/exec pid-mismatch class (`CLAUDE/NOTES/known-limitations.md#fork-exec-pid-mismatch`, where the two strings are genuinely unrelated, not just differently-cased) — this is purely a casing convention gap between a `.desktop` file's own hint and a window's runtime identity.

## Why `PID_GRACE_SECONDS` is 6.0s {#pid-grace-seconds}

Was 1.5s until i3 testing surfaced a real race: `_enrich_pids()`'s `provider.resolve_pid()` call (a full `get_tree()` round-trip plus a fresh Xlib connection per call, see `i3.py`'s `_x11_pid_for_window`) isn't guaranteed to resolve a freshly-mapped window's pid within 1.5s, and once an entry downgrades to app_id-tier matching, the pid tier is gone for good — `resolve_pending_move()`'s tiers are exclusive, so a later successful enrichment can no longer help. If the app_id fallback also doesn't match (common on i3, where a Python/Electron app's real WM_CLASS often isn't its `.desktop`-derived hint), the entry just times out unmatched at `MOVE_TIMEOUT_SECONDS` with nothing left to try. Widened to 6.0s to give the slower, async i3 enrichment path a real chance to land before giving up on the more precise pid signal, while still leaving a couple of seconds of runway for the app_id fallback before the hard timeout.

This timer is still the *only* downgrade path for a pid that never exits at all but doesn't own the eventual window either — see `#pending-moves-quick-exit-detection` for the separate, non-timer-based downgrade added alongside it for pids that *do* exit.

## `pending_moves.py`'s quick-exit detection {#pending-moves-quick-exit-detection}

Some spawned apps use their own single-instance IPC: the process `spawn_detached()` captured detects an already-running instance of itself, forwards "open a new window" to that pre-existing process over its own IPC channel, and exits cleanly (code 0) itself. Live-confirmed with VS Code's NixOS wrapper. The window that eventually appears belongs to the *pre-existing* process's pid, never the one `pending_moves.py` captured — the pid-tier (`#pending-move-tiers`) can never match it. The app_id-tier fallback should eventually catch it, but previously only activated after the fixed `PID_GRACE_SECONDS` timer (`#pid-grace-seconds`) — for a slow handoff, `MOVE_TIMEOUT_SECONDS` could drop the entry before its window even appeared.

The rejected fix was raising `MOVE_TIMEOUT_SECONDS` globally — that penalizes every genuinely broken launcher command (typo, missing binary, which also exits fast but with a *nonzero* code and never opens any window) by making tuicc wait longer before giving up, for zero benefit in that case. Instead, `process()` calls `_check_quick_exit(entry)` once per frame for any entry with a live pid — `os.waitpid(pid, os.WNOHANG)`, the same non-blocking primitive `control.py`'s `_run_detached_detecting_quick_failure()` already uses for the same kind of check, just called once per frame here (`process()` already runs every frame) instead of in a bounded blocking spin-loop. `spawn_detached()`'s pid is always a direct child of tuicc's own process (`start_new_session=True` only detaches the session, not the parent-child `wait()` relationship), so this works without any change to its signature.

Exit 0 and nonzero get deliberately different treatment, since they mean different things: exit 0 immediately clears `entry["pid"]` to `None`, handing off to app_id-tier matching right away instead of waiting out the rest of `PID_GRACE_SECONDS` — a known-benign "someone else will own the window" signal. A nonzero exit is a genuine failure (the window will never come) — the entry is dropped immediately rather than left to burn out the rest of `MOVE_TIMEOUT_SECONDS`, and a message is added to `PendingMovesResult.failure_messages` (see `#pending-moves-process-contract` below) — previously this failed 100% silently. The existing `PID_GRACE_SECONDS` timer-based downgrade stays as an unchanged fallback for pids that never exit at all but still don't own the eventual window — a different, still-open failure class (see `CLAUDE/NOTES/known-limitations.md#fork-exec-pid-mismatch`) this check can't see, since nothing ever exits for it to catch.

The `MOVE_TIMEOUT_SECONDS` give-up path (pre-existing, previously silent regardless of cause) also now adds a `failure_messages` entry, with different wording (no exit code — the process may still be running).

## `pending_moves.process()`'s return contract {#pending-moves-process-contract}

`process()` returns a `PendingMovesResult` dataclass (`reclaimed_focus: bool`, `resolved_target_regions: list`, `failure_messages: list`) — promoted from a `(reclaimed_focus, resolved_target_regions)` 2-tuple once `failure_messages` was added (`#pending-moves-quick-exit-detection` above), same "value outgrew 2 fields, make it a dataclass" convention as `frame_update.FrameResult`/`resize_mode.EditKeyResult`. `process()` always tries to reclaim tuicc's own focus (unless `dismissed`) before dropping a timed-out or quick-exit-failed entry, even for entries that never matched — a spawn's own placement failing is a separate concern from tuicc's own fullscreen/focus, which the transient co-location problem (see `CLAUDE/NOTES/wm-quirks.md#fullscreen-drop-on-map`) already broke the moment the new window mapped. Without this, a spawn that timed out unmatched left tuicc's window stuck floating and unfocused indefinitely, with nothing left in the queue to ever call `focus_self()` on its behalf again.

`reclaimed_focus` tells `main.py` whether `focus_self()` was called this round — a real WM-focus transition, but a self-inflicted one, not the user switching to a different real context. `main.py`'s own real-focus-transition detector needs to know this to avoid misreading tuicc reclaiming its own focus as the user having gone elsewhere, which would otherwise silently reset `selected_id`/`focus_id` mid-launcher-session (concrete regression: a spawn's target silently switching workspace because an earlier spawn's `focus_self()` call happened to land between selecting a workspace and confirming — see the regression test).

`resolved_target_regions` lists the target region of every entry that matched a window this round (never a give-up path, which has no real destination to report) so `main.py` can let `focus_id` — and the preview panel — follow a spawn/restore to wherever it actually landed. Without this, the preview panel showed nothing, indefinitely, for the rest of that tuicc session after a restore completed, until a dismiss+resummon forced a reset.

`failure_messages` is populated on a quick nonzero-exit give-up or a `MOVE_TIMEOUT_SECONDS` give-up (see `#pending-moves-quick-exit-detection`) — never on a real match or while an entry is still pending. `frame_update.py` is the one place that reads it and applies it onto `loop_state.resize_message`/`resize_message_until`/`resize_message_urgent` — `pending_moves.py` itself stays fully provider/state-agnostic and never imports `loop_state`, same boundary it's always kept.

`own_region_id` is compared against each resolving entry's `target_region` to decide whether to request `force_relayout` from `focus_self()` — see `CLAUDE/NOTES/wm-quirks.md#fullscreen-suppresses-layout` for why a window landing on tuicc's own fullscreen workspace needs this. `None` (the default) never requests it, same opt-in shape as `fullscreen_only`.

## Battery percent is energy-weighted, not a plain average across packs {#battery-energy-weighted-percent}

`battery.aggregate()` computes overall percent as `sum(energy_now)/sum(energy_full)*100` when every pack reports both fields — the real combined charge, not skewed by packs of different physical capacity. Concrete case that motivated this: a two-pack machine with BAT0 at 6%/22.62Wh full and BAT1 at 15%/68.7Wh full — a plain percent average reads ~10-11%, the energy-weighted combined charge is ~13%, a real, non-trivial difference given BAT1 holds triple BAT0's capacity. Falls back to a plain percent average only when any pack is missing `energy_now`/`energy_full` (some drivers only expose `charge_*`/`capacity`).

`aggregate()`'s status is "Charging" if *any* pack is charging (a topped-off sibling reporting "Not charging" shouldn't override "the machine is charging" overall), else "Discharging" if any pack is, else the first pack's own status verbatim.

## `get_ac_online()` is separate from any pack's own status {#battery-ac-online-separate}

## bluez discovery needs its own held-open connection {#bluez-discovery-connection}

`BluezBackend.start_discovery()` runs the whole `StartDiscovery` -> wait -> `StopDiscovery` sequence on its own background thread with a connection it holds open for `DISCOVERY_WINDOW_SECONDS`, unlike every other method on this backend (which opens a connection, makes one call, and closes it immediately). This is required, not a style choice: bluez ties a discovery session to the *calling client's own D-Bus connection* — it ends automatically the instant that connection closes, so the short-lived-connection style would end discovery before it had any real chance to find anything. Running it on its own thread also keeps it from blocking StatusWorker's one shared action-dispatch thread, which would stall every other domain too.

## iwd's `Network.Connect()` returns cleanly even on a wrong passphrase {#iwd-connect-false-success}

`IwdBackend.connect()` (`connectivity/iwd.py`) does its own post-attempt verification — checking the Station's `ConnectedNetwork` property against the network path just attempted, right after `Connect()` returns — instead of trusting a clean `Connect()` return as success. This isn't documented anywhere and contradicts the naive reading of the D-Bus Agent pattern: reproduced deterministically, a deliberately wrong passphrase against a real AP completed `Connect()` in ~3.4s with a clean, non-error reply, while the Station's own `ConnectedNetwork` property never changed to the attempted network. iwd apparently considers `Connect()` "done" once the attempt has been fully processed (right passphrase or wrong), not "authentication actually succeeded" — trusting the return alone made a wrong passphrase indistinguishable from success: no exception, nothing for StatusWorker to capture, nothing for the UI to show. The post-check needs no extra wait: by the time the blocking `Connect()` call gets its reply, iwd's own internal state for the same operation has already settled.

NetworkManager's `ActivateConnection()`/`AddAndActivateConnection()` have the same fundamental gotcha but a structurally different fix — see `CLAUDE/NOTES/design-decisions.md#networkmanager-vs-iwd` point 4 (a genuinely async activation needing a real poll loop, not a one-shot check).

## Connectivity module: signal bars, fixed-slot windowing, action feedback {#connectivity-module-design}

`_signal_bars()` always draws all 5 segments (filled + empty), never just the filled ones — an earlier 4-asterisk scheme only ever drew the filled asterisks ("*   " for a weak signal), giving no way to tell at a glance whether that's 1-of-4 or the rest of the scale simply isn't there. Uses plain Unicode Geometric Shapes (▮/▯), not a Nerd Font icon — tuicc's established convention is symbols any reasonable monospace font already has, and a signal indicator is exactly the kind of thing that must never render as a broken tofu box. `None` (backend can't report a signal) renders as all-empty rather than a distinct glyph, keeping the "always 5 segments" consistency intact.

WiFi/Bluetooth each use the fixed-slot-plus-scroll-window mechanic (`windowed_list.py`, shared with media.py/sysmon.py) instead of an earlier hand-rolled "cap WiFi at a fixed row count with a static '+N more' line, don't cap Bluetooth at all": with no cap on Bluetooth, a long pairing history could push WiFi off-screen entirely, and "+N more" had no way to actually reach those extra networks. The section header and its Scan/Discover trigger share one row (header left-aligned, trigger right-aligned) rather than the trigger getting its own row, to give the scrollable list back one more row of height — the trigger is still its own distinct NavItem/target_kind, matching sysmon.py's CLOSE-vs-KILL idiom for "second action on a section."

The Scan/Discover trigger's "Scanning…"/"Discovering…" label is driven by main.py's dedicated `wifi_scanning`/`bluetooth_discovering` Domains (polling the daemon's own real `Scanning`/`Discovering` property), not `StatusWorker.is_pending()` — the fire-and-forget `scan()`/`start_discovery()` call itself only pends for a brief D-Bus round trip, nowhere near the real scan/discovery duration, so `is_pending()` alone made the label flicker instead of holding steady for the actual scan.

A wifi passphrase overlay's "waiting" state must stay open until the real connect result (success/failure) is known, not close the instant Enter is pressed — closing early meant a wrong passphrase produced total silence (the connect attempt kept running in the background with nothing on screen reflecting it, indistinguishable from tuicc having silently dropped the input).

An unknown wifi network shows a "[new] " *prefix*, not a " (new)" suffix — a prefix reads as a real label attached to the name ("this row is new"), where a suffix could get pushed out of view entirely by a long SSID. Signal bars get their own color independent of the row's selection/dim styling (accent when connected, plain text color otherwise, never dimmed) so signal strength stays legible to scan regardless of which row is currently selected.

`_action_progress_line()` (a hover-preview line reflecting a live connect/disconnect attempt for one specific item) exists because pressing Enter on a network/device previously gave no feedback beyond the row's own blink, and no way to tell *why* it failed. It uses `get_action_error_for()`, not the plain per-domain `get_action_error()`, because many networks/devices share one "wifi"/"bluetooth" domain — without the per-item key, an old network's stale error would bleed onto whatever's selected now. `_wifi_scan_preview_text()` similarly shows the *full* network list on hover, not just the visible-slots window the scrollable section itself shows, since the box's own row budget can't show everything at once.

## sysmon's compact stats grid: layout, formatting, and per-metric choices {#sysmon-stats-grid}

`modules/sysmon.py`'s middle stats block is a real N-column table (`GRID_COL_WIDTH` = 18, `_grid_row()`), not a loose run-on line of "LABEL value LABEL value ..." — a fixed column boundary is what actually reads as tidy and scannable, verbatim: "the config should be the one place you configure everything about that box" is why layout, per-metric visibility, and thresholds all became real `[[sysmon.block]]` config.toml entries (`config.py`'s `_build_sysmon_blocks()`/`DEFAULT_SYSMON_BLOCKS`) rather than constants in this module — see `CLAUDE/VISION.md`'s R6 section for the full config shape. Metric labels render in accent color, values in plain text color, so the eye can scan for just labels or just values instead of a flat wall of text.

Every cell except the last in a row is padded/truncated to `GRID_COL_WIDTH` so the next column lines up; the last cell keeps its natural length. This is deliberate, not an oversight: HOT's own `describe_sensor()` label (e.g. "58°C (CPU (Package id 0))") routinely runs past `GRID_COL_WIDTH`, and in the packaged default layout it's the one cell with no fixed-width neighbor to its right — a user who repositions that block into a row that *does* share width with another column takes on the truncation risk themselves, a consequence of their own layout choice, not something the function tries to prevent for them.

Per-metric formatting choices: RAM and disk show used/available amounts (e.g. "5.2/12.0 GiB"), not a bare percent — a percentage alone doesn't say how much room is actually left, though the cell's color still follows the real usage percent even though the displayed text doesn't show one. RAM uses GiB (binary, /1024², matching what the kernel's own MemTotal/MemAvailable already round to); disk uses GB (decimal, /1e9, matching `df`'s own convention) — deliberately different units for the two, not an inconsistency. The `cputemp` metric is labeled "CPUTEMP", not "TEMP", for clarity against the "HOT" (hottest sensor) block that often sits right next to it in the packaged layout — same value shape, different meaning (one is specifically the CPU package, the other is whatever sensor is hottest right now). THROTTLED rides along on HOT's own cell as a separate urgent-colored segment specifically because that's the one cell layout-wise that isn't at risk of column-width clipping in the packaged default.

`_friendly_app_name()` shows the app's display name ("Firefox"), not the raw app_id ("firefox") or the full window title — a resource-monitor row cares about *which app*, not *which document/tab*, and a full title (VS Code/Firefox tabs routinely run 40+ characters) would otherwise push the CPU/RAM numbers themselves off the edge of the box. It reuses launcher.py's `scan_desktop_apps()` cache (matching a window's app_id against a `.desktop` entry's `StartupWMClass`/filename hint, case-insensitively — looser than pending_moves.py's own app_id tier, which needs an exact match to disambiguate multiple pending spawns; a display-name lookup has no such collision risk) rather than a hardcoded app_id-to-name table, which CONTRIBUTING.md's "no hardcoded personal preferences" rule would rule out anyway. `_format_window_label()` always shows the CPU/RAM readout in full and truncates the app name instead — the numbers are the actual point of a system-monitor row, so they get priority over the name when width runs out.

## sysmon module: row-expansion model, NICE's write range, action reuse {#sysmon-module-design}

`modules/sysmon.py` (`CLAUDE/VISION.md`'s R6) uses the same two-level browsing/expanded row model `sessions.py` established: level 1 is one row per window with CLOSE/KILL/NICE dimmed at the box's right edge; Enter expands the row, lighting those three actions up (`_action_positions` reuses sessions.py's own right-aligned layout logic, 3 actions instead of 4). NICE additionally opens its own small inline numeric input ("-3_", the same in-place idiom sessions.py's rename field uses) rather than running immediately — `is_editing_nice()`/`start_nice_edit()`/`handle_nice_key()`/`apply_nice_edit()` mirror sessions.py's `is_naming()`/`start_naming()`/`handle_naming_key()`/`apply_naming()` quartet shape exactly. `_expanded_window_id`/`_nice_target`/`_nice_input` are plain module-level state, same pattern as sessions.py's `_expanded_slot`/`_naming_slot`/`_name_input` and media.py's `_expanded_bus_name`.

NICE only ever writes 0..19 (positive/"nicer" only) — lowering niceness (negative values) needs `CAP_SYS_NICE`/root tuicc doesn't assume it has, and `os.setpriority()` would just fail depending on the kernel; restricting the input range to what's always safe sidesteps that failure mode entirely rather than handling it after the fact.

CLOSE/KILL both act through pieces that already exist elsewhere: `Provider.close_window()` (already implemented on both sway.py/i3.py, no provider changes needed) and a plain `pending_confirm` dict routed through `actions.py`'s existing `spawn_detached(shell_true=False)` — KILL needed zero changes to `actions.py` itself, `kill -9 <pid>` already splits cleanly via `shlex.split`, exactly like sessions.py's own "del" action.

## NetworkManager backend: real structural differences from iwd.py {#networkmanager-vs-iwd}

`connectivity/networkmanager.py` is the second `WifiBackend`, alongside `iwd.py`'s, for users who don't run iwd. It differs from iwd.py in ways that aren't just different method names:

1. **No bulk tree walk.** iwd/bluez both implement `org.freedesktop.DBus.ObjectManager.GetManagedObjects()` at their root, fetching their whole object graph in one call. NetworkManager doesn't expose ObjectManager the same way — its own `GetAllDevices()`/`Settings.ListConnections()` are the real enumeration mechanism, and each object's properties need their own `Properties.GetAll` call. More D-Bus round trips per poll than iwd.py needs — an accepted cost, no different in spirit from iwd.py's own one-GetAll-per-network pattern, just one level less bulk.
2. **`AccessPoint` is per-BSSID, not per-SSID.** iwd's `Network` object is already collapsed to one per SSID; NetworkManager's scan results are one `AccessPoint` object per physical radio actually seen (a mesh, or multiple APs on the same SSID, show up as several objects). `merge_access_points_by_ssid()` is what iwd.py never needed.
3. **No built-in link between a scan result and a saved profile.** iwd's `Network.KnownNetwork` property points straight at it; NetworkManager's `Settings.Connection` profiles are a wholly separate object graph, correlated with a scanned `AccessPoint` only by matching decoded SSID (`find_known_profile_for_ssid()`).
4. **`ActivateConnection()`/`AddAndActivateConnection()` return almost instantly**, before real activation starts — the same "returns cleanly even on a wrong passphrase" gotcha already fixed for iwd.py's own `connect()`, but structurally worse here: unlike iwd.py's one-shot post-call property check (`Connect()` itself blocks for the whole attempt), NetworkManager's activation is genuinely asynchronous even from the calling client's perspective, needing an actual bounded poll loop (`_wait_for_activation()`), not a single read.

**Not yet confirmed against a real, running NetworkManager** (built and fixture-tested against hand-built, doc-accurate D-Bus reply shapes on a machine that runs iwd) — whether `ActivateConnection` really behaves as documented on some real distro's NM version, and whether polling `State` really observes the transitions assumed here, are both unverified. Flagged explicitly rather than presented as proven the way iwd.py's live-tested behavior is.

## `spawn_detached`'s env layering: captured values win, except live session identifiers {#spawn-detached-env-layering}

`spawn_detached(env=...)` layers a captured `/proc/<pid>/environ` snapshot (session.py's `read_environ()`) on top of a copy of tuicc's own current environment — captured values win, since the whole point is restoring app-specific setup a plain relaunch wouldn't have. Exception: `_ALWAYS_LIVE_ENV_KEYS` (`WAYLAND_DISPLAY`, `DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `I3SOCK`, `SWAYSOCK`, `XAUTHORITY`) always come from the *current* environment regardless of what the snapshot says — a session saved today and loaded after a relogin/reboot would otherwise carry yesterday's now-nonexistent socket paths straight into the respawned process, a launch failure with a confusing, unrelated-looking cause.

See `CLAUDE/NOTES/known-limitations.md#restore-relaunch-crash` for the concrete bug (`spawn_detached`'s `log_path` param exists for) this env handling is paired with.

## `ActionContext.reselect_item_id`: exact id vs. region search {#reselect-item-id-vs-region-search}

`ActionContext` has two single-use "move selection here after this action" signals: `reselect_region_id` (main.py searches the current frame's nav items for a region-kind item matching this id) and `reselect_item_id` (main.py jumps directly to this exact NavItem id, no search). The direct form exists because a handler sometimes already knows precisely which id it wants — typically its own module's — where a region search doesn't apply (there's no "region" to search for, just an exact row). sessions.py's "expand a row" handler is the motivating case: expanding changes what its own `nav_items()` reports on the very next frame, making the just-selected row id vanish from the list, which would otherwise trip main.py's "selection no longer valid" recovery (a region-kind fallback search, meant for real external focus changes) into jumping to the sidebar instead of landing on the newly-revealed actions.

## Media module: collapsed rows, fixed-slot sections, transport-cluster layout {#media-module-layout}

`modules/media.py`'s now-playing rows use the same two-level browsing/expanded model `sessions.py` established: each player collapses to a single NavItem row until expanded (Enter), rather than always exposing its 1-3 transport controls as separate NavItems. This isn't just visual — three always-active transport NavItems per row, positioned near the box's right edge, interacted badly with `tab_order`'s default "columns_first" ordering (sorts by x first): a row visually near the top of the box could land navigationally near the bottom of the Tab sequence, since its x was large even though its y was small. Collapsing to one NavItem per row at the browsing level sidesteps this; the transport actions only become separate NavItems once that player is expanded.

The player list is genuinely dynamic (a player can quit, appear, or reorder between polls), so `_expanded_bus_name` tracks the expanded player by its stable D-Bus identity, not a list position, and `_reconcile_expanded_state()` clears it if that player disappears while expanded — otherwise `is_expanded()` would report `True` forever for a player that no longer exists.

Both sections (Now Playing's players, Output's sinks) always render exactly `VISIBLE_SLOTS` (3) rows — never more, never fewer — regardless of how many players/sinks actually exist. Fewer than 3 real items: remaining slots show a `"[empty - player N]"`/`"[empty - output N]"` placeholder. More than 3: a scroll window keeps whatever's selected/expanded in view, recomputed fresh from `ctx.selected_id` every call (same "derive from what's true right now" idiom `_reconcile_expanded_state` uses) so it can't drift stale. media.py was the first module to get this treatment; the underlying tension (box size is a static config ratio, content amount is a live runtime quantity) applies elsewhere too — `connectivity.py`'s wifi/bluetooth lists have the same shape — but `control.py`/`power_menu.py`/`sessions.py` don't need it since their content count is a config.toml choice, not runtime-variable.

Once anything in the Now Playing section is expanded, every row's info text (dot + label) goes dimmed — including the expanded row's own label, not just its siblings: once inside a row, its name isn't what you're navigating anymore, its transport controls are, and only the one truly-focused control glyph stays bright among those.

The transport-control cluster ("◀◀ ▶ ▶▶") uses Unicode from the same block as the ●/○ status dots already confirmed safe on the target terminal (U+25A0-25FF, "Geometric Shapes") rather than "Miscellaneous Technical" (⏮/⏸/⏭), which rendered double-width via emoji-font fallback and broke column alignment — curses' `addstr` always advances by exactly 1 column per Python character regardless of the glyph's actual drawn width. Play/pause uses a single character in both states ("▶"/"■") rather than two glyphs of different lengths, since no left/right padding split ever looks truly centered when a 1-char glyph sits next to a 2-char one — matching lengths is the actual fix, not a cleverer split.

## Media module: cava visualizer placement and source-label heuristics {#media-cava-and-source-label}

The cava frequency visualizer is drawn inline to the right of the Output section's rows (not as separate fixed rows below everything), filling the same space to the right of a sink name that "◀◀ ▶ ▶▶" fills to the right of a Now Playing row. It always spans the full `VISIBLE_SLOTS` window rather than however many real sinks exist, so the idle baseline sits on a consistent fixed bottom slot rather than shifting with sink count. The idle/no-frame baseline draws on only the bottommost row, in plain "text" theme color (not also dimmed — the glyph's own short 1/8-height fill already reads as quiet without dimming on top) rather than "accent" (which read as too visually loud next to the Output list's quieter styling).

`_source_label()` picks the "where is this playing from" tag: a browser's current domain (MPRIS's `xesam:url`) when available, else the app's `DesktopEntry` (shorter/more uniform than `Identity`, e.g. "firefox" not "Mozilla firefox"), else `Identity` as the last resort. One exception: native apps can tag their metadata with a URL pointing at their own web player (Spotify's `xesam:url` is an `open.spotify.com` track link) — that's not "you're browsing this site" the way a real browser tab's URL is, so showing `[open.spotify.com]` for the desktop app would be misleading. Detected by the app's `desktop_entry` showing up inside the domain (`desktop_entry="spotify"` in `"open.spotify.com"`); when that matches, `Identity` is preferred over both the domain and `DesktopEntry`, since `Identity` is usually the nicer-cased name ("Spotify" vs "spotify") in exactly this case.

## Bars module is separate from control, not sliders bolted onto it {#bars-separate-from-control}

`modules/bars.py` (vertical VOL/BRI/BAT gauges) is a deliberately separate module from `control.py`, not sliders added to it. `control.py`'s own visual rule is "ONE box, uniform dense rows (dot + label) — not one framed box per feature"; a continuous gauge is a different visual language, and BAT in particular isn't something you toggle at all (`CLAUDE/VISION.md`'s four-category test calls that shape "Context": read-only decision input), so it doesn't belong in control's row list either way. Inspired by swcc's (this project's predecessor) own vertical bars, rebuilt with finer fill resolution via eighth-block glyphs (`render_utils.eighth_block_level` — the same technique `modules/media.py`'s cava visualizer uses) to fix swcc's own "bars move inconsistently with the real percentage" complaint. No fixed reference ticks (25/50/75% marks) — tried, read as visual clutter, dropped. A per-bar framed box was also tried and dropped as "too much" for what's meant to be a plain, dense display; bars ended up flat, same footprint as the first cut (BAR_W columns, BAR_GAP between them, no border around the fill).

This first pass is display-only — `nav_items()` returns `[]` on purpose (same as `clock.py`). VOL/BRI grab/adjust (Enter grabs, ←→ ±5%, Enter/Esc releases) is planned as `input_claim`'s 4th consumer (see `CLAUDE/VISION.md`'s R2/R5 sections) as its own follow-up pass.

## Bars: quantized fill vs. exact readout, and why empty cells draw nothing {#bars-fill-quantization}

The readout text above each bar always shows the real, exact live percent (61%, not rounded). The bar's own visual fill is a deliberately coarser, independent number: quantized to the nearest `BAR_FILL_STEP` (5%, `_quantize_percent()`) before it reaches `eighth_block_level()`. Without this, the same real percentage change (say 59% → 61%) could look like a visible jump on one box height and nothing at all on another, purely because `eighth_block_level`'s `num_rows*8` resolution (8 is a hard Unicode constant — block glyphs only come in eighths) doesn't divide evenly into 100, and that remainder shifts with box height. Quantizing the filled value first makes the visible step boundaries (every 5%) height-independent; `num_rows*8` still governs how smoothly the already-quantized value renders within a row, not where the boundaries fall. 5% also matches the ±5%/keypress step the future VOL/BRI grab interaction will use, so the bar's visual language and how you move it agree 1:1.

A partial eighth-block glyph (▁▂▃▄▅▆▇) only paints ink across the fraction of the cell it represents. Two earlier attempts at rendering the *rest* of that cell — a "░" track texture, then a solid colored background — both ended up visibly mismatched against the empty rows around them, in two different ways. The fix that actually worked: draw nothing at all for a fully-empty row and for a partial row's unpainted remainder alike (`draw()`'s `if level == 0: continue`) — both "empty" cases render as the exact same thing (nothing, blending into the terminal's own background), trivially consistent with each other by construction, with no separate shade to mismatch in the first place.

## BAT bar's three states: Charging > plugged > plain {#bars-battery-states}

`_bat_spec()` distinguishes three mutually exclusive states, in priority order: Charging (actively adding charge — "CHG" readout, accent glow via `BarSpec.charging`) > plugged (a charger is connected per `battery.get_ac_online()`, but this pack isn't presently accepting charge — a ThinkPad charge_control threshold pausing mid-range, or already topped off) > plain (genuinely running on battery alone). Charging needs to visually pop, not just say "CHG" in text, hence the accent glow on the fill itself, not just the readout.

"plugged" shows the real percent in the same plain styling as an ordinary reading (an earlier accent-tinted version of "plugged" was tried and dropped as visually confusing next to real charging) and swaps the *label* from "BAT" to "AC" instead — the label is what actually communicates "there's a charger here" without implying an active charge. Before this distinction existed, "plugged in but paused" and "genuinely running on battery alone" looked identical (both a plain percentage), even though they're very different things to know.

`battery.get_ac_online()` is a deliberately separate signal from any pack's own `status` field: a charger can be fully connected with every pack correctly declining to charge (e.g. a ThinkPad's charge_control threshold keeping a pack between 40-80%), and without a dedicated "is a charger physically connected" check, tuicc had no way to distinguish that from "genuinely unplugged, draining" — both read as a plain percentage with no charging status. It checks *every* entry under `/sys/class/power_supply`, not a hardcoded `AC` name, because a real ThinkPad exposes charging via both a traditional `AC` (type=Mains) node and two USB-C PD ports (type=USB) simultaneously — hardcoding `AC` alone would miss USB-C-only charging setups. Returns `None` (not `False`) when the machine exposes no non-battery power sources at all, distinct from "checked, none are online" — the same None-vs-`[]` discipline used throughout this codebase (see `status_worker.py`).

## Box coordinates round to 9 decimals; navigation compares them exactly {#box-coordinate-float-noise}

Found live, this session: `resize_mode.py`'s `resize_step()`/`move_step()` computed a box's new x/y/w/h as `current + delta` (or its clamped form) with no rounding — mathematically fine, but repeated `+=`/`-=` steps through binary floating point leave a residual epsilon behind even when the net movement is exactly zero (moving a box right N cells then back left N cells landed at `5.204170427930421e-18`, not exactly `0.0` — confirmed by reproducing the exact same value in a test with the same step count). Invisible on screen — but `navigation.py`'s `tab_order()` (and `main.py`'s matching `module_position_key` for module-to-module Left/Right/Tab-rollover order) sorts by *exact* `(x, y)` tuple comparison, no tolerance. A box sitting at `5.2e-18` instead of `0.0` is no longer tied with its visually-flush neighbors at exactly `0.0` — it sorts into its own separate "column" after all of them, which silently reordered a whole module (`sessions`) to the far end of the tab/Left-Right sequence, well away from where it visually sits. Symptom: Shift+Tab backward out of `sidebar` skipped straight past `sessions` (its real, intended predecessor) and wrapped around to `sysmon` instead.

Fixed at the source rather than defensively in `navigation.py`'s comparison: `resize_step()`/`move_step()` now `round(..., 9)` their result before storing it. 9 decimals is far finer than any real terminal's `1/term_size` granularity (a 10,000-column terminal is still only 4 decimals of real precision), so it can't visibly affect where a box actually lands — it only kills noise several orders of magnitude below that. `navigation.py`'s sort itself was deliberately left exact-comparison, not given its own epsilon tolerance: the real bug was bad data reaching it, and fixing generation is more robust than having every consumer of `ModuleBox` coordinates separately guess at a "close enough" threshold.

Two currently-saved preset files had the bad values already baked in from before this fix (both cleaned as part of the same pass): `src/tuicc/presets/1.toml` (the packaged default, rounded when it was captured from live use for `CLAUDE/VISION.md`'s R7) and this machine's own `~/.config/tuicc/presets/1.toml`. A preset file saved before this fix and never re-touched by resize mode since could still carry old noise — regenerate via F2 (nudge a box one step and back) + F3 if `tab_order` ever looks wrong on an old preset.

## `mode_stack`: replacing `input_claim`'s string tiers with a real stack, one tier at a time {#mode-stack-phase-1}

A pasted proposal to "unfuck main.py" (a class-based `App` + abstract `Mode` + `push_mode`/`pop_mode`) was rejected in favor of a hybrid: a real `mode_stack: list[str]` replacing `input_claim`'s single string slot (plus `resize.active`/`resize.editing`/`help_state.active`/`spawn_picker.active`'s own separate bools, eventually), but each stack entry still dispatches to a **pure function**, not a class with methods — staying inside this codebase's established "pure function over an explicit value" convention rather than introducing an OOP layer alongside it. `MODE_HANDLERS: dict[str, Callable[[int], bool]]` is the dispatch registry, the same "add an entry, not a new branch" idiom `MODULES`/`NAV_PROVIDERS` (`render.py`) and `ACTION_HANDLERS` (`actions.py`) already use. The handler contract (`bool` return = `still_claiming`) isn't new either — it's the exact shape `launcher.handle_typing_key`/`sessions.handle_naming_key`/`sysmon.handle_nice_key`/`help_mode`'s color editor/`connectivity.handle_passphrase_key` already use and call "R2's input_claim shape" in their own docstrings.

Deliberately staying `bool`, not a richer result type, even though a later phase (resize) will need one: `VISION.md`'s own R2 backlog note already concluded resize needs a 3-state shape specifically *because* its browsing tier falls through to normal dispatch on an unhandled key, unlike every actual `input_claim` consumer today — that's a structurally different problem, not evidence the `bool` contract itself is insufficient for tiers like this one. No mypy/pyright in this repo, so widening later costs a coordinated docstring/call-site update, not a compile-time break — not worth paying for speculatively.

**Phase 1** (done) migrated only `sessions_naming`/`sysmon_nice` — the two simplest, most structurally-identical tiers — to prove the mechanism end to end before touching anything harder. Both handlers stayed as closures in `main()` (next to the existing `do_*` ones), not new functions in `sessions.py`/`sysmon.py`: `sessions_naming`'s handler needs `cfg.session_names`/`set_session_name()`, and no module in this codebase imports `config.py` — that boundary (`main.py` owns `cfg`/`theme_pairs` writes, per this file's own dismiss-vs-quit-adjacent architecture notes in `CLAUDE/GUIDE.md`) stays intact rather than growing a new cross-module dependency to avoid one closure.

**Found in review before it shipped, not live:** `connectivity_wants_input` (main.py, gating whether a passphrase/pairing prompt is allowed to claim input right now) read `input_claim is None` as a bare "is anything at all currently claimed" proxy. Migrating a tier off `input_claim` onto `mode_stack` leaves `input_claim` permanently `None` for that tier's whole lifetime, so without a matching `and mode_stack[-1] == "normal"` added to the guard, a connectivity prompt would have silently stolen the claim out from under an in-progress rename/NICE edit. This is a **standing checklist item for every future phase**, not a one-off fix: before assuming a tier's migration is purely mechanical, re-grep the file for every other place that reads that tier's old flag as a bare "is anything claimed" proxy — `resize.active`/`spawn_picker.active`/`help_state.active` all appear in that same boolean and will need the identical treatment when they migrate.

**Not touched by Phase 1, and not part of this pattern at all:** the two-level module-expansion mechanism (`any_two_level_module_expanded()` — sessions/media/sysmon's own browsing-vs-expanded state, e.g. a session slot showing LOAD/SAVE/DEL/NAME). That's an orthogonal concern — it modifies *how* Tab/Shift+Tab/Left/Right behave (`same_row_neighbor(wrap=...)` instead of module-rollover), not *who* owns the keypress — and stays exactly as it is.

**Phase 2** (done) migrated `connectivity_passphrase`/`connectivity_pairing`. Harder than Phase 1 because entry AND resolution are driven by per-frame polling of `wifi_agent.mailbox.has_pending()`/`bluez_agent.mailbox.has_pending()` (checked every loop iteration, before `getch()` runs) — a live iwd/bluez daemon can cancel a prompt at any moment, not just answer a keypress. Split accordingly: the per-keypress handling (confirm/escape/typed-text/yes-no) became two `MODE_HANDLERS` closures, same shape as Phase 1's; the entry/resolution logic itself (deciding whether something NEW should claim the stack this frame, before any key even exists) stayed a plain inline block reading/writing `mode_stack` directly, not forced into the registry — its contract (`Callable[[int], bool]`, dispatched by keypress) genuinely doesn't fit a "should I start now" question asked once a frame from two independently-shaped sources (`wifi_agent` always present, `bluez_agent` possibly `None`). Inventing a second poll-registry for two call sites would have been premature abstraction, not adherence to the pure-function convention — reading/writing the stack value directly already satisfies it.

**Found in review before it shipped, not live (second instance of the same kind of catch as Phase 1's):** the entry block's old code did `input_claim = "connectivity_passphrase"` unconditionally on both the fresh-claim path AND the retry path (iwd re-asking `RequestPassphrase` after a wrong password while already mid-flow) — a harmless idempotent overwrite either way. Naively translating that to `mode_stack.append(...)` is NOT idempotent: the retry path would push a second, duplicate frame, and the eventual single `mode_stack.pop()` only ever removes one — leaving a stale frame on top that silently swallows the next real keypress (routed into the handler, which finds nothing to do, cancels again, and only then pops the duplicate) with zero visible feedback. Fixed with `if mode_stack[-1] != "connectivity_passphrase": mode_stack.append(...)` (mirrored for pairing). **General lesson for future phases, beyond the standing "re-grep for stale is-anything-claimed proxies" checklist Phase 1 already flagged:** any `input_claim = "same value it might already be"` assignment being migrated needs the SAME idempotency check before becoming a bare `mode_stack.append(...)` — string reassignment and stack push are not interchangeable operations just because they look similar at the call site.

**Priority-ordering framing, corrected:** the old code's "connectivity checked ahead of sessions_naming/sysmon_nice/help_colors" comments described *keypress-dispatch order* (which `if input_claim == "..."` happened to run first). Once every migrated tier shares one real stack, that framing is moot — mutual exclusion is structural (one stack, one top), not achieved by check ordering. Connectivity's practical priority now comes from *when in the frame* its entry check runs: every frame, before `getch()` reads a key at all, so it claims the stack before a keypress could ever let `sessions_naming`/`sysmon_nice` claim it that same frame.

**Phase 3** (done) migrated `help_colors` + `help_state.active` — the first tier with genuine 2-level nesting on `mode_stack`: `"help"` (browsing `help_mode.py`'s panel/pages) can push `"help_colors"` (editing one color value) on top of itself, then pop back to `"help"`, landing on the colors page it came from rather than exiting entirely. Phases 1-2 only ever had one non-`"normal"` frame active at a time. `handle_help`'s colors-page confirm branch is the first case of a `MODE_HANDLERS` closure itself pushing a second frame (`mode_stack.append("help_colors")`) rather than a push happening in a plain per-frame block — confirmed safe by review: it's symmetric with the later pop, and `do_enter_help()`'s own unconditional `mode_stack.append("help")` (no idempotency guard needed here, unlike Phase 2's connectivity — there's no out-of-band re-trigger source the way daemon-mailbox polling was) can't double-fire since the generic dispatch already intercepts once `"help"` is on top.

`help_state.active` deliberately stays untouched everywhere else (the draw call site, `connectivity_wants_input`'s guard) — it's depth-agnostic (true at either `"help"` or `"help_colors"`), exactly the invariant those two sites need. Swapping either for `mode_stack[-1] == "help"` would have broken specifically during color-editing (stack-top is `"help_colors"` then).

**New subtlety this phase, not present in Phases 1-2:** `handle_help_colors` needs `nonlocal theme_pairs` — the original `theme_pairs = reassign_theme_pairs(...)` ran directly in `main()`'s own loop body, a same-scope reassignment; nested in a new closure without `nonlocal`, it would silently shadow the outer `theme_pairs` instead of updating it. The color would still save correctly to `cfg.theme`/`config.toml`, but on-screen rendering would never see the change until restart — invisible, easy to miss without deliberately checking for it. General lesson for future phases: any migrated block that reassigns (not mutates) a `main()`-local variable needs this checked explicitly, the same way Phase 2's lesson was about idempotent-assignment-vs-append.

Review found no runtime bug in the core mechanism this time (unlike Phases 1-2, each of which had one) — only three stale doc comments, one of which had already gone stale since Phase 2 shipped without catching it (the `mode_stack` declaration's own comment still said "Only sessions_naming/sysmon_nice are migrated so far"). All three fixed in the same commit. Lesson: these comments need updating on *every* phase, not just the phase that changes the code they describe, or they drift silently.

**Phase 4** (done) migrated `launcher` — the ambient "type anywhere to search apps" claim, `input_claim`'s very first historical consumer. `handle_launcher` needed three `nonlocal`s (`focus_id`, `selected_id`, `active_module`), the most of any handler so far — the only tier that reassigns `focus_id` (Up/Down shifts the ambient launch target without leaving typing mode) on top of the `selected_id`/`active_module` restore every exit path already needed. Review traced the full dispatch order and confirmed unconditional `mode_stack.append("launcher")` at both entry sites is safe, same reasoning as Phase 3's `do_enter_help()` — no out-of-band re-trigger source, and the vim/non-vim entry branches are mutually exclusive by `cfg.vim_mode` so they can't double-fire.

**Capstone: `input_claim` retired entirely.** Once launcher moved, nothing in the file assigned to it any more — `resize.active`/`resize.editing`/`spawn_picker.active` were never on `input_claim` to begin with (a separate mechanism since Phase 1's own original design), so there was nothing left for them to migrate away from on this specific variable. The declaration, its own comment block, and `connectivity_wants_input`'s now-permanently-true `input_claim is None` clause were all removed. A repo-wide grep-driven sweep also closed two comments that had already gone stale without being caught by Phases 1-2's own (main.py-scoped) sweeps: `sysmon.py`'s NICE-input section header still called itself "a 4th input_claim consumer" after Phase 1 migrated it, and `iwd.py`/`bluez.py`'s timeout-reasoning comments still named `input_claim` after Phase 2 migrated connectivity. **Lesson for any future refactor with a multi-phase comment-sweep habit: scope the sweep to the whole repo from the start, not just the file being edited** — a comment describing main.py's behavior can live in a completely different file (a docstring explaining *why* some other module's function exists) and go stale exactly as silently.

Comments that read as *historical narration* of why `input_claim`/R2 was originally introduced (`VISION.md`'s own R2/R4 sections, several "VISION.md's R2 `input_claim` shape" provenance notes on the `still_claiming` bool contract across `launcher.py`/several test files) were deliberately left alone — accurate as a record of a past decision, not a claim that the variable still exists. One `VISION.md` mention was *not* historical, though (a forward-pointer telling a future implementer to hook the not-yet-built bars VOL/BRI grab feature into "a 4th `input_claim` consumer") — that one was actionable guidance pointing at a now-nonexistent mechanism, so it got updated to `mode_stack` instead, same treatment as the analogous forward-pointer in `bars.py` itself.

**Phase 5 (final)** migrated `spawn_picker`/resize's editing level — the last two hijack tiers, never on `input_claim` to begin with. Every earlier phase's postmortem (including this section's own Phase 4 paragraph above) predicted resize would need a 3-state contract, because its browsing tier falls through to normal dispatch on an unhandled key. **That turned out to be avoidable, not just harder — the real fix was recognizing browsing isn't a true modal claim at all.** It never swallows an unrecognized key, so it's categorically the same *kind* of thing as sessions/media/sysmon's own two-level expansion state, which Phase 3 already declared orthogonal to `mode_stack`. So browsing stays exactly where and how it's always been — its own non-stack check, unchanged code, permanently excluded, not deferred further. Only `resize.editing` (a real modal — always consumes) and `spawn_picker.active` (real modal, single-shot — `resize_mode.choose()` always resolves/closes on any key) became actual `mode_stack` tags, `"resize_editing"` and `"spawn_picker"`. No `MODE_HANDLERS` contract change was needed anywhere — every handler still just returns a plain `bool`.

**New idiom this phase introduced: the "handoff."** Every prior phase's entries either stayed claimed (`return True`) or ended cleanly with nothing new pushed (`return False`, generic dispatch pops). Phase 5 has several transitions that end one claim while *immediately* starting a different one in the same keypress — picking a module in the spawn picker goes straight into editing it; F1/F3/F4/F5/F6 from inside editing hand off to help/a fully-closed session/a fresh browsing session/the spawn picker. The generic dispatch's own post-call `mode_stack.pop()` blindly pops whatever's on top *after* the handler returns — so a handler that pushes a new tag before returning `False` would have the new tag incorrectly popped, not its own old one. Fixed by a small shared pattern: the handler pops its **own** tag itself, calls whatever lands in (or pushes) the next state, then `return True` — telling the generic dispatch the stack is already correctly arranged, don't touch it again. Factored into a 3-line `handoff(do_fn)` helper for the six F-key branches (in the same spirit as `do_apply_reselect()` already being a shared helper for a repeated pattern, not a new abstraction style), and inlined once for `handle_spawn_picker`'s own choice-made case.

**Found in review before it shipped, not live (fourth instance of this exact review process catching something real):** the initial closure sketch for `handle_resize_editing` had explicit `return` statements on every branch that ends or hands off editing, but no explicit `return True` after the whole `if`/`elif` chain for the branches that just mutate and stay editing (`direction_keys`/`move_toggle`/`delete_box`) or for a genuinely unrecognized key. The *original* code always ended in one unconditional `continue` regardless of which branch matched or none did — a stray key while editing was always a harmless no-op. Without an explicit trailing `return True`, those paths would return `None` (falsy), and the generic dispatch would read that as "done" and pop — **silently ending the whole editing session on a stray keypress**, strictly worse than the original's no-op. One line (`return True` after the whole chain) fixes it; flagged explicitly in the shipped code as load-bearing, not decoration, so a future edit doesn't accidentally drop it while adding a new branch.

**This closes the whole `input_claim`→`mode_stack` migration.** Every text-input/modal claim in the codebase — sessions_naming, sysmon_nice, connectivity_passphrase, connectivity_pairing, help, help_colors, launcher, spawn_picker, resize_editing — now dispatches through one `mode_stack: list[str]` + `MODE_HANDLERS: dict[str, Callable[[int], bool]]` registry, the same "add an entry, not a new branch" idiom `MODULES`/`NAV_PROVIDERS`/`ACTION_HANDLERS` already used elsewhere in this codebase, entirely without introducing a class hierarchy — the original "unfuck main.py" proposal's `App`/`Mode`/`push_mode`/`pop_mode` sketch is nowhere in the final shape. Resize's browsing tier is the one deliberate, permanent exception, for the reason explained above — not a gap, a considered design boundary. `CLAUDE/GUIDE.md`'s resize-mode paragraph was updated in this same commit to describe the final architecture, closing the "deferred" note Phase 4's own postmortem left open.

## `LoopState`: replacing closure-capture + `nonlocal` with an explicit state object {#loopstate-migration}

A later attempt to extract main()'s per-frame update step (marquee/cava lifecycle, connectivity poll, focus-transition detection, `pending_moves` processing, `RenderContext` construction) found it blocked for a different reason than any `mode_stack` phase: most of the shared state it reads/writes (`selected_id`, `focus_id`, `active_module`, ...) is *also* read/written by every other closure in `main()` via ordinary Python closure-capture, not scoped to that one block. A plain function extraction would need ~13 in-params/~13 out-values — past where "pure function over an explicit value" stays readable, closer to a disguised class.

Root cause, not just that one block's problem: `main()`'s 18 nested closures rely on Python closures + `nonlocal` for everything they share — the same mechanism that let the mode_stack phases above work at all, but one with two real costs, both already hit live in this same session: (1) a missing `nonlocal` is a silent bug, not a crash — Phase 3 above shipped with a missing `nonlocal theme_pairs`, caught only by Plan-agent review; (2) a closure can never be flattened to a top-level function (and therefore never unit-tested, never moved to another file) as long as anything it touches is closure-captured — this is *why* candidate 3's extraction is stuck, and why `resize_mode.handle_editing_key`'s own extraction earlier this session needed a returned-signal design instead of just moving the closure as-is.

**Fix: `LoopState`** (`loop_state.py`) — a plain `@dataclass`, no methods, same shape as `ResizeState`/`LauncherState`/`PendingMovesQueue`, holding every name `main()`'s loop genuinely rebinds/mutates across frames. Explicitly excludes anything recomputed fresh every frame and never read across frames (`boxes`, `term_width`, `term_height`, WM `state`, `ordered` nav items — confirmed by tracing every read site) — those stay plain per-call parameters, since bundling them in would conflate two different kinds of "shared state." Also excludes (permanently, not just for now) `cfg`/`resize`/`spawn_picker`/`help_state`/`launcher`/`moves`/`action_ctx` — each assigned once and only ever mutated via its own fields/collections, never rebound by name, so `nonlocal` was never needed for them regardless of `LoopState`'s existence.

An exhaustive Explore pass (this session) inventoried the real scope: 18 closures, 8 `nonlocal` statements naming 6 variables (`resize_message`/`resize_message_until`, `active_module`, `selected_id`/`focus_id`, `theme_pairs`), plus `mode_stack` (shared but never literally rebound — only `.append`/`.pop`/`[-1]`-indexed) and 6 more names that are cross-frame-persistent but touched only at top level, never inside a closure (`pending_confirm`, `dismissed`, `last_focused_region_id`, `origin_region_id`, `expect_focus_reclaim`, `resolved_pid_cache`). 13 fields total. A Plan-agent review validated this and designed the phased migration below — sized (honestly) at 4-6 hours across 2-3 sessions, comparable to the whole 5-phase `mode_stack` effort above, likely bigger.

**Hard constraint driving every phase's boundary:** a field can't be half-plain-local/half-`loop_state.field` — every reader and writer, closures and top-level code alike, converts together, in the same phase. Fields are declared on `LoopState` incrementally, one phase at a time, never pre-declared as placeholders for a later phase.

**Phase 0 (done, this session) — flatten the 6 closures touching ZERO `LoopState` fields**: `do_enter_resize`, `handle_sessions_naming`, `handle_sysmon_nice`, `handle_connectivity_passphrase`, `handle_connectivity_pairing`, `any_two_level_module_expanded`. No `LoopState` dependency at all — proved the flatten-and-rewire mechanic (updating `MODE_HANDLERS`/`HANDOFF_TARGETS`/direct call sites to pass explicit params or wrap in a forwarding lambda) before touching anything stateful. `any_two_level_module_expanded` needed no signature change whatsoever — it never touched main()-local state even as a closure, only module-level functions.

**Phase 1 (done, this session) — `mode_stack`.** The single most-touched field (present in nearly every closure) but, found live during design, the *safest* to migrate first: it was never actually `nonlocal`-rebound to begin with (only mutated via `.append`/`.pop`/`[-1]`-indexing), the same "mutate an object's own field" category `cfg`/`resize`/etc. already were — so converting it needed zero `nonlocal` removal anywhere, just a rename to `loop_state.mode_stack` at all 22 real code sites (confirmed via a targeted regex pass — bare-word prose mentions of "mode_stack" in comments were left alone, matched only `mode_stack` immediately followed by `.` or `[`). Fully flattened `do_spawn_picker`, `do_enter_box_editing`, `do_enter_help`, `handle_help` (mode_stack was their only shared-state dependency). `handle_spawn_picker`/`handle_resize_editing` converted their `mode_stack` references but stayed closures — both still need `nonlocal active_module` until Phase 5, expected, not a smell mid-migration. `HANDOFF_TARGETS`/`MODE_HANDLERS` entries for the now-flattened functions became thin forwarding lambdas (`"spawn_box": lambda: do_spawn_picker(loop_state, cfg, spawn_picker)`) rather than containing logic themselves — built once before the loop, exactly as before.

**Phases 2-5 — all done, same session, continued after Phase 0+1's own commit:**
- **Phase 2 — `resize_message` + `resize_message_until`** (always paired). Fully flattened `do_save_layout`/`do_new_preset`; `do_cycle_preset` converted this pair (drops from a 3-name to a 1-name `nonlocal`), keeps `nonlocal active_module` until Phase 5.
- **Phase 3 — `theme_pairs`.** Fully flattened `handle_help_colors` — the same closure that needed the explicit `nonlocal theme_pairs` call-out back in Phase 3 of the `mode_stack` migration above; same lesson applied here too, now via `loop_state.theme_pairs` reassignment instead of `nonlocal`. Caught a real bug live, not by `pytest` (`main()`'s loop has no direct coverage — this is exactly the gap that lets this class of bug through): a regex substitution over-matched `app.theme_pairs` (`app_setup.AppContext`'s own field) into `app.loop_state.theme_pairs`, an `AttributeError` at startup, found on the first live launch and fixed immediately.
- **Phase 4 — the 6 top-level-only fields** (`pending_confirm`, `dismissed`, `last_focused_region_id`, `origin_region_id`, `expect_focus_reclaim`, `resolved_pid_cache`), batched together since none is touched by any closure — zero closure risk, purely mechanical top-level rewrites, despite the field count. One real collision risk found and avoided before it became a repeat of Phase 3's bug: `_resolve_visible_pids()` (a module-level function, not a `main()` closure) has its own unrelated parameter also named `resolved_pid_cache` — a blind text-wide substitution would have wrongly rewritten that function's own internal references too. Fixed by converting via an exact line-number-and-substring patch script instead of a pattern match.
- **Phase 5 (highest risk, landed as one atomic unit) — `active_module` + `selected_id` + `focus_id` together.** Couldn't be split further: `resolve_selection()` returns all three at 8+ call sites, and splitting them across phases would have forced ugly mixed-target unpacking for no benefit. Flattened the last remaining closures (`do_cycle_preset`, `do_apply_reselect`, `handle_launcher`, `handle_spawn_picker`, `handle_resize_editing`) and converted the entire bottom key-dispatch chain — the single largest, most mechanical piece of the whole migration, done via the same exact-line-number patch script Phase 4 introduced (one genuine mismatch caught immediately by the script's own check, a multi-line `old` string against a single-line target — fixed by hand, not a real bug). `do_apply_reselect`'s `ordered` param and `handle_launcher`'s `state`/`launcher`/`provider`/`moves` params are per-frame/stable-reference values passed explicitly, same pattern `handle_resize_editing` already used for `boxes`/`term_width`/`term_height` since Phase 1 — `MODE_HANDLERS`'s lambdas for these still close over `main()`'s own frame-local `state`/`boxes`/`term_width`/`term_height`, resolved at call time same as before, not at the dict's own one-time construction.

**This closes the whole `LoopState` migration.** Every one of `main()`'s 18 original closures either flattened to a plain module-level function (12 of them) or, for the 6 still nested (`do_save_layout`/`do_cycle_preset`/`do_new_preset`/`do_apply_reselect`/`handle_launcher`/`handle_spawn_picker`/`handle_resize_editing` — wait, those flattened too; the only closures left inside `main()` are `MODE_HANDLERS`/`HANDOFF_TARGETS`'s own forwarding lambdas), lost every `nonlocal` it ever needed. Candidate 3 (the per-frame update step, VISION.md's original third extraction target) is now genuinely unblocked — `loop_state` plus the same per-frame-transient-as-explicit-param pattern already proven here is enough to extract it normally, the way `app_setup.py`/`resize_mode.py` already were. Not attempted this session; a real next step, not infrastructure-building.

**Testability, a genuine bonus this migration unlocked incrementally, not just at the end:** field migration alone never made a closure testable — a nested `def` isn't importable regardless of `nonlocal`. Testability arrived at *flattening*, automatic at the end of whichever phase converted a closure's last remaining field — mirroring how `resize_mode.handle_editing_key` became unit-testable this same session once it stopped being a closure. Every flattened function stays in `main.py` (not moved into `modules/*.py` — the "no module imports config.py" boundary still applies; this is main-loop dispatch, not a UI module's own concern) — real unit tests for `do_apply_reselect`/`handle_launcher`/`do_cycle_preset`/`handle_spawn_picker` are a natural next step, not done this session.
