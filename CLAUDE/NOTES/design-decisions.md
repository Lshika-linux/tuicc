# Design decisions

Why things are shaped the way they are, when the reasoning isn't obvious from reading the code. Each section is a stable anchor (`CLAUDE/NOTES/design-decisions.md#anchor`).

## Stabilization pass: CI, packaging, hermetic tests {#stabilization-2026-08-31}

Prompted by three independent architectural reviews of the codebase (all three analyzing commit `f12458f`) landing the same day — deliberately NOT tracked as a GitHub issue/scoreboard; the point was to fix things, not perform fixing them. Cross-checked each review's specific claims against the real repo before acting on any of them (several didn't hold up exactly as stated — a "20 symmetric wifi_*/bt_* pairs" claim was really 6; a quoted three-if-block "two-level module collapse" snippet doesn't match `main.py`, which already uses the registry-style loop at `main.py:1082` the reviews were themselves recommending; a claimed "4 failing tests" didn't reproduce — 1765/1765 passed clean on this machine at that exact commit). The two claims that DID hold and got fixed here:

- **`.github/workflows/tests.yml`** — `pytest` on push/PR, plain `ubuntu-latest` + `pip install -r requirements.txt`, no WM/display needed (see CLAUDE.md's own "Commands" section — providers are tested against recorded fixtures, WM commands against a `FakeConnection`). 1783 tests, verified clean in a genuinely fresh venv (not this machine's existing `.venv`) before trusting the workflow.
- **`pyproject.toml`** — real project metadata + every dependency pinned (`requirements.txt`'s `jeepney`/`tomli_w`/`wcwidth`/`pyudev` were unpinned before this; pinned now to whatever this machine's own `.venv` had actually resolved and been running against). `requires-python = ">=3.11"` — `tomllib` (`config.py`/`session.py`) is stdlib-since-3.11 with no fallback, so that's already the real floor, not a guess. Deliberately does NOT (yet) give `pip install .` a working console-script entry point — `main.py` still lives at the repo root, run directly, not inside the `src/tuicc` package tree; wiring a real launcher is a separate, bigger step than "add pinned, versioned packaging metadata," not bundled in here. Verified live: `pip install .` in a scratch venv actually builds and imports `tuicc` cleanly.

**Two real, live-verified bugs found and fixed along the way, not just test hygiene:**
- `tests/test_session.py::test_read_environ_unreadable_pid_returns_none` asserted `read_environ(1) is None` — true for this repo's own dev machine (unprivileged), but silently WRONG the moment the suite runs as root (a real, common CI-runner default), since root can read any pid's `/proc/<pid>/environ`. Fixed by targeting a pid so far past any real kernel's `pid_max` (`999999999`) that `open()` raises `FileNotFoundError` regardless of privilege level — deterministic in every environment, not just this one.
- `control.py`'s `_run_detached_detecting_quick_failure()` (the fast-failure detector behind every `[[control.toggle]]` command — see `CLAUDE/VISION.md`'s own R3 section for the gammastep/Night Light example this exists for) called `os.waitpid(pid, os.WNOHANG)` with no exception guard at all — a REAL crash risk if anything else ever reaps that child first (a container's own init being an aggressive reaper, a subreaper misconfiguration), not just a test-environment quirk. `pending_moves.py`'s own `_check_quick_exit()` already guards the identical call with `except ChildProcessError`, treating it as "can't tell" rather than a crash — this one hadn't gotten the same treatment. Fixed the same way, plus a regression test using the same real, unmocked trick `test_pending_moves.py` already established: `os.waitpid(os.getpid(), ...)` always raises `ChildProcessError` for real (a process is never its own child), so the test exercises the actual exception path, not a simulated one.

Explicitly NOT done in this pass (real, agreed-on debt, just not today's scope): splitting `connectivity.py` (2052 lines, genuinely the single largest/most-tangled file, all three reviews independently flagged it) and `config.py` into smaller pieces, and centralizing `mode_stack`'s two-mutator split (`main.py` + `frame_update.py`, both push and pop it — deliberate, guarded, see `#mode-stack-phase-1`, but a single `push_mode()`/`pop_mode()` surface with an assertion would still be a cheap, real hardening). Sequencing reasoning: CI needs to exist and be green BEFORE a refactor that size gets attempted, not after — so the cheap wins came first.

## Dismiss vs. quit {#dismiss-vs-quit}

tuicc's main loop, once started, is never expected to exit in normal use. Every handler's `should_dismiss` bit (renamed from `should_exit`) means "call `Provider.dismiss_self()` and keep looping," not "terminate." `main.py`'s `while True:` has no `break` in it anywhere — the only way out is an unhandled exception, which in practice means Ctrl+C, caught quietly at the bottom of `main.py` with a `try/finally` around the loop for cleanup. See `CLAUDE/VISION.md` section 2 for the full lifecycle model this comes from.

## Optional `Provider` methods default to a documented no-op, not `abstractmethod` {#optional-provider-methods}

`mark_self()`, `dismiss_self()`, `focus_self()`, `no_focus_next_window()`, `resolve_pid()`, and `set_floating_geometry()` on `Provider` (`providers/base.py`) all default to a no-op (or `None`) rather than being abstract. Each covers a WM capability that not every window manager has an equivalent for (marks, scratchpad-style hiding, focus stealing back, per-window no-autofocus hints, non-native pid lookup, floating geometry). A provider for a WM lacking the concept simply inherits the default and accepts the resulting degraded case — tuicc shows up in its own preview, a launcher spawn's focus briefly wobbles, a restored floating window lands at the WM's default geometry instead of its saved one — never a crash. This is deliberately different from `close_window()`, which stays `abstractmethod`: every WM worth supporting can close a window, so there's no meaningful degraded case to fall back to there.

Severity varies sharply across this group even though the mechanism (no-op default) is the same: `focus_self()`'s degraded case is severe enough to call out explicitly (see `CLAUDE/NOTES/wm-quirks.md#focus-on-map-stealing`) where `mark_self()`'s or `set_floating_geometry()`'s are minor and cosmetic.

## `no_focus_next_window` is keyed on pid, not class/app_id {#pid-vs-class-criteria}

See `CLAUDE/NOTES/wm-quirks.md#no-focus-pid-criteria` for the full tradeoff — the short version: `pid` matches exactly one process and effectively never collides again, where `class`/`app_id` would keep matching every future window of that app for the rest of the WM session.

## `pending_moves.py`: pid > app_id > any-remaining matching tiers {#pending-move-tiers}

`resolve_pending_move()` matches a spawned process back to its window in three exclusive tiers, each only considering windows not already claimed by another entry: (1) exact pid match — unambiguous, but only available when the provider exposes `Window.pid` and the process wasn't launched via a shell; (2) app_id match — distinguishes the expected app from an unrelated new window, but not from a second simultaneous instance of the *same* app_id; (3) any remaining unclaimed new window — last resort.

The tiers are exclusive, not a cascade: an entry expecting a specific pid/app_id waits for exactly that (or times out in the caller) rather than settling for a weaker signal because its own match hasn't appeared yet on this tick. Falling through early looks fine until two entries share an app_id (e.g. two `kitty` launches) and one's window is simply slower to appear — a premature fallback then hands it the wrong entry's window. This exact bug reassigned 3 of 10 windows to the wrong workspace in a burst-launch test before the exclusive-tier fix.

Same-app_id entries not colliding at the app_id tier relies on callers processing pending entries in order, each claiming its match before the next entry looks — `resolve_pending_move()` itself has no notion of which window actually appeared first in real time, it just picks the first unclaimed match available to it. Two simultaneous instances of the same app_id landing on each other's targets (rather than crashing) is an accepted tradeoff, not a bug, as long as both instances are otherwise identical.

`resolve_pending_move()` doesn't mutate `claimed` itself — the caller adds the result's id only once it commits to the match (calls `move_window_to_region`), so a per-tier scan here never leaves a side effect to undo if the caller doesn't use the result.

The app_id tier compares case-insensitively, found live while re-verifying `#pending-moves-quick-exit-detection`'s own VS Code repro: its `.desktop` declares `StartupWMClass=Code`, but the real window's runtime app_id is `code` — an exact-case match waited forever for a window that could never satisfy it, independent of and stacked on top of the pid-tier failure the quick-exit fix addresses. A different problem from the fork/exec pid-mismatch class (`CLAUDE/NOTES/known-limitations.md#fork-exec-pid-mismatch`, where the two strings are genuinely unrelated, not just differently-cased) — this is purely a casing convention gap between a `.desktop` file's own hint and a window's runtime identity.

## Why `PID_GRACE_SECONDS` is 6.0s {#pid-grace-seconds}

Was 1.5s until i3 testing surfaced a real race: `_enrich_pids()`'s `provider.resolve_pid()` call (a full `get_tree()` round-trip plus a fresh Xlib connection per call, see `i3.py`'s `_x11_pid_for_window`) isn't guaranteed to resolve a freshly-mapped window's pid within 1.5s, and once an entry downgrades to app_id-tier matching, the pid tier is gone for good — `resolve_pending_move()`'s tiers are exclusive, so a later successful enrichment can no longer help. If the app_id fallback also doesn't match (common on i3, where a Python/Electron app's real WM_CLASS often isn't its `.desktop`-derived hint), the entry just times out unmatched at `MOVE_TIMEOUT_SECONDS` with nothing left to try. Widened to 6.0s to give the slower, async i3 enrichment path a real chance to land before giving up on the more precise pid signal, while still leaving a couple of seconds of runway for the app_id fallback before the hard timeout.

This timer is still the *only* downgrade path for a pid that never exits at all but doesn't own the eventual window either — see `#pending-moves-quick-exit-detection` for the separate, non-timer-based downgrade added alongside it for pids that *do* exit.

## `pending_moves.py`'s quick-exit detection {#pending-moves-quick-exit-detection}

Some spawned apps use their own single-instance IPC: the process `spawn_detached()` captured detects an already-running instance of itself, forwards "open a new window" to that pre-existing process over its own IPC channel, and exits cleanly (code 0) itself. Live-confirmed with VS Code's NixOS wrapper. The window that eventually appears belongs to the *pre-existing* process's pid, never the one `pending_moves.py` captured — the pid-tier (`#pending-move-tiers`) can never match it. The app_id-tier fallback should eventually catch it, but previously only activated after the fixed `PID_GRACE_SECONDS` timer (`#pid-grace-seconds`) — for a slow handoff, `MOVE_TIMEOUT_SECONDS` could drop the entry before its window even appeared.

The rejected fix was raising `MOVE_TIMEOUT_SECONDS` globally — that penalizes every genuinely broken launcher command (typo, missing binary, which also exits fast but with a *nonzero* code and never opens any window) by making tuicc wait longer before giving up, for zero benefit in that case. Instead, `process()` calls `_check_quick_exit(entry)` once per frame for any entry with a live pid — `os.waitpid(pid, os.WNOHANG)`, the same non-blocking primitive `control.py`'s `_run_detached_detecting_quick_failure()` already uses for the same kind of check, just called once per frame here (`process()` already runs every frame) instead of in a bounded blocking spin-loop. `spawn_detached()`'s pid is always a direct child of tuicc's own process (`start_new_session=True` only detaches the session, not the parent-child `wait()` relationship), so this works without any change to its signature.

Exit 0 and nonzero get deliberately different treatment, since they mean different things: exit 0 immediately clears `entry["pid"]` to `None`, handing off to app_id-tier matching right away instead of waiting out the rest of `PID_GRACE_SECONDS` — a known-benign "someone else will own the window" signal. A nonzero exit is a genuine failure (the window will never come) — the entry is dropped immediately rather than left to burn out the rest of `MOVE_TIMEOUT_SECONDS`, and a message is added to `PendingMovesResult.failure_messages` (see `#pending-moves-process-contract` below) — previously this failed 100% silently. The existing `PID_GRACE_SECONDS` timer-based downgrade stays as an unchanged fallback for pids that never exit at all but still don't own the eventual window — a different, still-open failure class (see `CLAUDE/NOTES/known-limitations.md#fork-exec-pid-mismatch`) this check can't see, since nothing ever exits for it to catch.

The `MOVE_TIMEOUT_SECONDS` give-up path (pre-existing, previously silent regardless of cause) also now adds a `failure_messages` entry, with different wording (no exit code — the process may still be running).

## `pending_moves.process()`'s return contract {#pending-moves-process-contract}

`process()` returns a `PendingMovesResult` dataclass (`reclaimed_focus: bool`, `resolved_target_regions: list`, `failure_messages: list`) — promoted from a `(reclaimed_focus, resolved_target_regions)` 2-tuple once `failure_messages` was added (`#pending-moves-quick-exit-detection` above), same "value outgrew 2 fields, make it a dataclass" convention as `frame_update.FrameResult`/`resize_mode.EditKeyResult`. `process()` always tries to reclaim tuicc's own focus (unless `dismissed`) before dropping a timed-out or quick-exit-failed entry, even for entries that never matched — a spawn's own placement failing is a separate concern from tuicc's own fullscreen/focus, which the transient co-location problem (see `CLAUDE/NOTES/wm-quirks.md#fullscreen-drop-on-map`) already broke the moment the new window mapped. Without this, a spawn that timed out unmatched left tuicc's window stuck floating and unfocused indefinitely, with nothing left in the queue to ever call `focus_self()` on its behalf again.

`reclaimed_focus` tells `main.py` whether `focus_self()` was called this round — a real WM-focus transition, but a self-inflicted one, not the user switching to a different real context. `main.py`'s own real-focus-transition detector needs to know this to avoid misreading tuicc reclaiming its own focus as the user having gone elsewhere, which would otherwise silently reset `selected_id`/`focus_id` mid-launcher-session (concrete regression: a spawn's target silently switching workspace because an earlier spawn's `focus_self()` call happened to land between selecting a workspace and confirming — see the regression test).

`resolved_target_regions` lists the target region of every entry that matched a window this round (never a give-up path, which has no real destination to report) so `main.py` can let `focus_id` — and the preview panel — follow a spawn/restore to wherever it actually landed. Without this, the preview panel showed nothing, indefinitely, for the rest of that tuicc session after a restore completed, until a dismiss+resummon forced a reset.

`failure_messages` is populated on a quick nonzero-exit give-up or a `MOVE_TIMEOUT_SECONDS` give-up (see `#pending-moves-quick-exit-detection`) — never on a real match or while an entry is still pending. `frame_update.py` is the one place that reads it and applies it onto `loop_state.resize_message`/`resize_message_until`/`resize_message_urgent` — `pending_moves.py` itself stays fully provider/state-agnostic and never imports `loop_state`, same boundary it's always kept.

`own_region_id` is compared against each resolving entry's `target_region` to decide whether to request `force_relayout` from `focus_self()` — see `CLAUDE/NOTES/wm-quirks.md#fullscreen-suppresses-layout` for why a window landing on tuicc's own fullscreen workspace needs this. `None` (the default) never requests it, same opt-in shape as `fullscreen_only`.

## Battery percent is energy-weighted, not a plain average across packs {#battery-energy-weighted-percent}

`battery.aggregate()` computes overall percent as `sum(energy_now)/sum(energy_full)*100` when every pack reports both fields — the real combined charge, not skewed by packs of different physical capacity. Concrete case that motivated this: a two-pack machine with BAT0 at 6%/22.62Wh full and BAT1 at 15%/68.7Wh full — a plain percent average reads ~10-11%, the energy-weighted combined charge is ~13%, a real, non-trivial difference given BAT1 holds triple BAT0's capacity. Falls back to a plain percent average only when any pack is missing `energy_now`/`energy_full` (some drivers only expose `charge_*`/`capacity`).

`aggregate()`'s status is "Charging" if *any* pack is charging (a topped-off sibling reporting "Not charging" shouldn't override "the machine is charging" overall), else "Discharging" if any pack is, else the first pack's own status verbatim.

## `get_ac_online()` is separate from any pack's own status {#battery-ac-online-separate}

## bluez discovery needs its own held-open connection {#bluez-discovery-connection}

`BluezBackend.start_discovery()` runs the whole `StartDiscovery` -> wait -> `StopDiscovery` sequence on its own background thread with a connection it holds open for `DISCOVERY_WINDOW_SECONDS`, unlike every other method on this backend (which opens a connection, makes one call, and closes it immediately). This is required, not a style choice: bluez ties a discovery session to the *calling client's own D-Bus connection* — it ends automatically the instant that connection closes, so the short-lived-connection style would end discovery before it had any real chance to find anything. Running it on its own thread also keeps it from blocking StatusWorker's one shared action-dispatch thread, which would stall every other domain too.

## iwd's `Network.Connect()` returns cleanly even on a wrong passphrase {#iwd-connect-false-success}

`IwdBackend.connect()` (`connectivity/iwd.py`) does its own post-attempt verification — checking the Station's `ConnectedNetwork` property against the network path just attempted, right after `Connect()` returns — instead of trusting a clean `Connect()` return as success. This isn't documented anywhere and contradicts the naive reading of the D-Bus Agent pattern: reproduced deterministically, a deliberately wrong passphrase against a real AP completed `Connect()` in ~3.4s with a clean, non-error reply, while the Station's own `ConnectedNetwork` property never changed to the attempted network. iwd apparently considers `Connect()` "done" once the attempt has been fully processed (right passphrase or wrong), not "authentication actually succeeded" — trusting the return alone made a wrong passphrase indistinguishable from success: no exception, nothing for StatusWorker to capture, nothing for the UI to show. The post-check needs no extra wait: by the time the blocking `Connect()` call gets its reply, iwd's own internal state for the same operation has already settled.

NetworkManager's `ActivateConnection()`/`AddAndActivateConnection()` have the same fundamental gotcha but a structurally different fix — see `CLAUDE/NOTES/design-decisions.md#networkmanager-vs-iwd` point 4 (a genuinely async activation needing a real poll loop, not a one-shot check).

## Connectivity module: signal bars, fixed-slot windowing, action feedback {#connectivity-module-design}

`_signal_bars()` always draws all 5 segments (filled + empty), never just the filled ones — an earlier 4-asterisk scheme only ever drew the filled asterisks ("*   " for a weak signal), giving no way to tell at a glance whether that's 1-of-4 or the rest of the scale simply isn't there. Uses plain Unicode Geometric Shapes (▮/▯), not a Nerd Font icon — tuicc's established convention is symbols any reasonable monospace font already has, and a signal indicator is exactly the kind of thing that must never render as a broken tofu box. `None` (backend can't report a signal) renders as all-empty rather than a distinct glyph, keeping the "always 5 segments" consistency intact.

WiFi/Bluetooth each use the fixed-slot-plus-scroll-window mechanic (`windowed_list.py`, shared with media.py/sysmon.py) instead of an earlier hand-rolled "cap WiFi at a fixed row count with a static '+N more' line, don't cap Bluetooth at all": with no cap on Bluetooth, a long pairing history could push WiFi off-screen entirely, and "+N more" had no way to actually reach those extra networks. The section header and its Scan/Discover trigger share one row (header left-aligned, trigger right-aligned) rather than the trigger getting its own row, to give the scrollable list back one more row of height — the trigger is still its own distinct NavItem/target_kind, matching sysmon.py's CLOSE-vs-KILL idiom for "second action on a section."

The Scan/Discover trigger's "Scanning…"/"Discovering…" label is driven by main.py's dedicated `wifi_scanning`/`bluetooth_discovering` Domains (polling the daemon's own real `Scanning`/`Discovering` property), not `StatusWorker.is_pending()` — the fire-and-forget `scan()`/`start_discovery()` call itself only pends for a brief D-Bus round trip, nowhere near the real scan/discovery duration, so `is_pending()` alone made the label flicker instead of holding steady for the actual scan.

A wifi passphrase overlay's "waiting" state must stay open until the real connect result (success/failure) is known, not close the instant Enter is pressed — closing early meant a wrong passphrase produced total silence (the connect attempt kept running in the background with nothing on screen reflecting it, indistinguishable from tuicc having silently dropped the input).

An unknown wifi network shows a "[new] " *prefix*, not a " (new)" suffix — a prefix reads as a real label attached to the name ("this row is new"), where a suffix could get pushed out of view entirely by a long SSID. Signal bars get their own color independent of the row's selection/dim styling (accent when connected, plain text color otherwise, never dimmed) so signal strength stays legible to scan regardless of which row is currently selected.

`_action_progress_line()` (a hover-preview line reflecting a live connect/disconnect attempt for one specific item) exists because pressing Enter on a network/device previously gave no feedback beyond the row's own blink, and no way to tell *why* it failed. It uses `get_action_error_for()`, not the plain per-domain `get_action_error()`, because many networks/devices share one "wifi"/"bluetooth" domain — without the per-item key, an old network's stale error would bleed onto whatever's selected now. `_wifi_scan_preview_text()` similarly shows the *full* network list on hover, not just the visible-slots window the scrollable section itself shows, since the box's own row budget can't show everything at once.

## sysmon's compact stats grid: layout, formatting, and per-metric choices {#sysmon-stats-grid}

`modules/sysmon.py`'s middle stats block is a real N-column table (`GRID_COL_WIDTH` = 18, `_grid_row()`), not a loose run-on line of "LABEL value LABEL value ..." — a fixed column boundary is what actually reads as tidy and scannable, verbatim: "the config should be the one place you configure everything about that box" is why layout, per-metric visibility, and thresholds all became real `[[sysmon.block]]` config.toml entries (`config.py`'s `_build_sysmon_blocks()`/`DEFAULT_SYSMON_BLOCKS`) rather than constants in this module — see `CLAUDE/VISION.md`'s R6 section for the full config shape. Metric labels render in accent color, values in plain text color, so the eye can scan for just labels or just values instead of a flat wall of text.

Every cell except the last in a row is padded/truncated to `GRID_COL_WIDTH` so the next column lines up; the last cell keeps its natural length. This is deliberate, not an oversight: HOT's own `describe_sensor()` label (e.g. "58°C (CPU (Package id 0))") routinely runs past `GRID_COL_WIDTH`, and in the packaged default layout it's the one cell with no fixed-width neighbor to its right — a user who repositions that block into a row that *does* share width with another column takes on the truncation risk themselves, a consequence of their own layout choice, not something the function tries to prevent for them.

Per-metric formatting choices: RAM and disk show used/available amounts (e.g. "5.2/12.0 GiB"), not a bare percent — a percentage alone doesn't say how much room is actually left, though the cell's color still follows the real usage percent even though the displayed text doesn't show one. RAM uses GiB (binary, /1024², matching what the kernel's own MemTotal/MemAvailable already round to); disk uses GB (decimal, /1e9, matching `df`'s own convention) — deliberately different units for the two, not an inconsistency. The `cputemp` metric is labeled "CPUTEMP", not "TEMP", for clarity against the "HOT" (hottest sensor) block that often sits right next to it in the packaged layout — same value shape, different meaning (one is specifically the CPU package, the other is whatever sensor is hottest right now). THROTTLED rides along on HOT's own cell as a separate urgent-colored segment specifically because that's the one cell layout-wise that isn't at risk of column-width clipping in the packaged default.

`_friendly_app_name()` shows the app's display name ("Firefox"), not the raw app_id ("firefox") or the full window title — a resource-monitor row cares about *which app*, not *which document/tab*, and a full title (VS Code/Firefox tabs routinely run 40+ characters) would otherwise push the CPU/RAM numbers themselves off the edge of the box. It reuses launcher.py's `scan_desktop_apps()` cache (matching a window's app_id against a `.desktop` entry's `StartupWMClass`/filename hint, case-insensitively — looser than pending_moves.py's own app_id tier, which needs an exact match to disambiguate multiple pending spawns; a display-name lookup has no such collision risk) rather than a hardcoded app_id-to-name table, which CONTRIBUTING.md's "no hardcoded personal preferences" rule would rule out anyway. `_format_window_label()` always shows the CPU/RAM readout in full and truncates the app name instead — the numbers are the actual point of a system-monitor row, so they get priority over the name when width runs out.

## sysmon module: row-expansion model, NICE's write range, action reuse {#sysmon-module-design}

`modules/sysmon.py` (`CLAUDE/VISION.md`'s R6) uses the same two-level browsing/expanded row model `sessions.py` established: level 1 is one row per window with CLOSE/KILL/NICE dimmed at the box's right edge; Enter expands the row, lighting those three actions up (`_action_positions` reuses sessions.py's own right-aligned layout logic, 3 actions instead of 4). NICE additionally opens its own small inline numeric input ("-3_", the same in-place idiom sessions.py's rename field uses) rather than running immediately — `is_editing_nice()`/`start_nice_edit()`/`handle_nice_key()`/`apply_nice_edit()` mirror sessions.py's `is_naming()`/`start_naming()`/`handle_naming_key()`/`apply_naming()` quartet shape exactly. `_expanded_window_id`/`_nice_target`/`_nice_input` are plain module-level state, same pattern as sessions.py's `_expanded_slot`/`_naming_slot`/`_name_input` and media.py's `_expanded_bus_name`.

NICE only ever writes 0..19 (positive/"nicer" only) — lowering niceness (negative values) needs `CAP_SYS_NICE`/root tuicc doesn't assume it has, and `os.setpriority()` would just fail depending on the kernel; restricting the input range to what's always safe sidesteps that failure mode entirely rather than handling it after the fact.

CLOSE/KILL both act through pieces that already exist elsewhere: `Provider.close_window()` (already implemented on both sway.py/i3.py, no provider changes needed) and a plain `pending_confirm` dict routed through `actions.py`'s existing `spawn_detached(shell_true=False)` — KILL needed zero changes to `actions.py` itself, `kill -9 <pid>` already splits cleanly via `shlex.split`, exactly like sessions.py's own "del" action.

## NetworkManager backend: real structural differences from iwd.py {#networkmanager-vs-iwd}

`connectivity/networkmanager.py` is the second `WifiBackend`, alongside `iwd.py`'s, for users who don't run iwd. It differs from iwd.py in ways that aren't just different method names:

1. **No bulk tree walk.** iwd/bluez both implement `org.freedesktop.DBus.ObjectManager.GetManagedObjects()` at their root, fetching their whole object graph in one call. NetworkManager doesn't expose ObjectManager the same way — its own `GetAllDevices()`/`Settings.ListConnections()` are the real enumeration mechanism, and each object's properties need their own `Properties.GetAll` call. More D-Bus round trips per poll than iwd.py needs — an accepted cost, no different in spirit from iwd.py's own one-GetAll-per-network pattern, just one level less bulk.
2. **`AccessPoint` is per-BSSID, not per-SSID.** iwd's `Network` object is already collapsed to one per SSID; NetworkManager's scan results are one `AccessPoint` object per physical radio actually seen (a mesh, or multiple APs on the same SSID, show up as several objects). `merge_access_points_by_ssid()` is what iwd.py never needed.
3. **No built-in link between a scan result and a saved profile.** iwd's `Network.KnownNetwork` property points straight at it; NetworkManager's `Settings.Connection` profiles are a wholly separate object graph, correlated with a scanned `AccessPoint` only by matching decoded SSID (`find_known_profile_for_ssid()`).
4. **`ActivateConnection()`/`AddAndActivateConnection()` return almost instantly**, before real activation starts — the same "returns cleanly even on a wrong passphrase" gotcha already fixed for iwd.py's own `connect()`, but structurally worse here: unlike iwd.py's one-shot post-call property check (`Connect()` itself blocks for the whole attempt), NetworkManager's activation is genuinely asynchronous even from the calling client's perspective, needing an actual bounded poll loop (`_wait_for_activation()`), not a single read.

**Not yet confirmed against a real, running NetworkManager** (built and fixture-tested against hand-built, doc-accurate D-Bus reply shapes on a machine that runs iwd) — whether `ActivateConnection` really behaves as documented on some real distro's NM version, and whether polling `State` really observes the transitions assumed here, are both unverified. Flagged explicitly rather than presented as proven the way iwd.py's live-tested behavior is.

## `spawn_detached`'s env layering: captured values win, except live session identifiers {#spawn-detached-env-layering}

`spawn_detached(env=...)` layers a captured `/proc/<pid>/environ` snapshot (session.py's `read_environ()`) on top of a copy of tuicc's own current environment — captured values win, since the whole point is restoring app-specific setup a plain relaunch wouldn't have. Exception: `_ALWAYS_LIVE_ENV_KEYS` (`WAYLAND_DISPLAY`, `DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `I3SOCK`, `SWAYSOCK`, `XAUTHORITY`) always come from the *current* environment regardless of what the snapshot says — a session saved today and loaded after a relogin/reboot would otherwise carry yesterday's now-nonexistent socket paths straight into the respawned process, a launch failure with a confusing, unrelated-looking cause.

See `CLAUDE/NOTES/known-limitations.md#restore-relaunch-crash` for the concrete bug (`spawn_detached`'s `log_path` param exists for) this env handling is paired with.

## `ActionContext.reselect_item_id`: exact id vs. region search {#reselect-item-id-vs-region-search}

`ActionContext` has two single-use "move selection here after this action" signals: `reselect_region_id` (main.py searches the current frame's nav items for a region-kind item matching this id) and `reselect_item_id` (main.py jumps directly to this exact NavItem id, no search). The direct form exists because a handler sometimes already knows precisely which id it wants — typically its own module's — where a region search doesn't apply (there's no "region" to search for, just an exact row). sessions.py's "expand a row" handler is the motivating case: expanding changes what its own `nav_items()` reports on the very next frame, making the just-selected row id vanish from the list, which would otherwise trip main.py's "selection no longer valid" recovery (a region-kind fallback search, meant for real external focus changes) into jumping to the sidebar instead of landing on the newly-revealed actions.

## Media module: collapsed rows, fixed-slot sections, transport-cluster layout {#media-module-layout}

`modules/media.py`'s now-playing rows use the same two-level browsing/expanded model `sessions.py` established: each player collapses to a single NavItem row until expanded (Enter), rather than always exposing its 1-3 transport controls as separate NavItems. This isn't just visual — three always-active transport NavItems per row, positioned near the box's right edge, interacted badly with `tab_order`'s default "columns_first" ordering (sorts by x first): a row visually near the top of the box could land navigationally near the bottom of the Tab sequence, since its x was large even though its y was small. Collapsing to one NavItem per row at the browsing level sidesteps this; the transport actions only become separate NavItems once that player is expanded.

The player list is genuinely dynamic (a player can quit, appear, or reorder between polls), so `_expanded_bus_name` tracks the expanded player by its stable D-Bus identity, not a list position, and `_reconcile_expanded_state()` clears it if that player disappears while expanded — otherwise `is_expanded()` would report `True` forever for a player that no longer exists.

Both sections (Now Playing's players, Output's sinks) always render exactly `VISIBLE_SLOTS` (3) rows — never more, never fewer — regardless of how many players/sinks actually exist. Fewer than 3 real items: remaining slots show a `"[empty - player N]"`/`"[empty - output N]"` placeholder. More than 3: a scroll window keeps whatever's selected/expanded in view, recomputed fresh from `ctx.selected_id` every call (same "derive from what's true right now" idiom `_reconcile_expanded_state` uses) so it can't drift stale. media.py was the first module to get this treatment; the underlying tension (box size is a static config ratio, content amount is a live runtime quantity) applies elsewhere too — `connectivity.py`'s wifi/bluetooth lists have the same shape — but `control.py`/`power_menu.py`/`sessions.py` don't need it since their content count is a config.toml choice, not runtime-variable.

Once anything in the Now Playing section is expanded, every row's info text (dot + label) goes dimmed — including the expanded row's own label, not just its siblings: once inside a row, its name isn't what you're navigating anymore, its transport controls are, and only the one truly-focused control glyph stays bright among those.

The transport-control cluster ("◀◀ ▶ ▶▶") uses Unicode from the same block as the ●/○ status dots already confirmed safe on the target terminal (U+25A0-25FF, "Geometric Shapes") rather than "Miscellaneous Technical" (⏮/⏸/⏭), which rendered double-width via emoji-font fallback and broke column alignment — curses' `addstr` always advances by exactly 1 column per Python character regardless of the glyph's actual drawn width. Play/pause uses a single character in both states ("▶"/"■") rather than two glyphs of different lengths, since no left/right padding split ever looks truly centered when a 1-char glyph sits next to a 2-char one — matching lengths is the actual fix, not a cleverer split.

## Media module: cava visualizer placement and source-label heuristics {#media-cava-and-source-label}

The cava frequency visualizer is drawn inline to the right of the Output section's rows (not as separate fixed rows below everything), filling the same space to the right of a sink name that "◀◀ ▶ ▶▶" fills to the right of a Now Playing row. It always spans the full `VISIBLE_SLOTS` window rather than however many real sinks exist, so the idle baseline sits on a consistent fixed bottom slot rather than shifting with sink count. The idle/no-frame baseline draws on only the bottommost row, in plain "text" theme color (not also dimmed — the glyph's own short 1/8-height fill already reads as quiet without dimming on top) rather than "accent" (which read as too visually loud next to the Output list's quieter styling).

`_source_label()` picks the "where is this playing from" tag: a browser's current domain (MPRIS's `xesam:url`) when available, else the app's `DesktopEntry` (shorter/more uniform than `Identity`, e.g. "firefox" not "Mozilla firefox"), else `Identity` as the last resort. One exception: native apps can tag their metadata with a URL pointing at their own web player (Spotify's `xesam:url` is an `open.spotify.com` track link) — that's not "you're browsing this site" the way a real browser tab's URL is, so showing `[open.spotify.com]` for the desktop app would be misleading. Detected by the app's `desktop_entry` showing up inside the domain (`desktop_entry="spotify"` in `"open.spotify.com"`); when that matches, `Identity` is preferred over both the domain and `DesktopEntry`, since `Identity` is usually the nicer-cased name ("Spotify" vs "spotify") in exactly this case.

## Bars module is separate from control, not sliders bolted onto it {#bars-separate-from-control}

`modules/bars.py` (vertical VOL/BRI/BAT gauges) is a deliberately separate module from `control.py`, not sliders added to it. `control.py`'s own visual rule is "ONE box, uniform dense rows (dot + label) — not one framed box per feature"; a continuous gauge is a different visual language, and BAT in particular isn't something you toggle at all (`CLAUDE/VISION.md`'s four-category test calls that shape "Context": read-only decision input), so it doesn't belong in control's row list either way. Inspired by swcc's (this project's predecessor) own vertical bars, rebuilt with finer fill resolution via eighth-block glyphs (`render_utils.eighth_block_level` — the same technique `modules/media.py`'s cava visualizer uses) to fix swcc's own "bars move inconsistently with the real percentage" complaint. No fixed reference ticks (25/50/75% marks) — tried, read as visual clutter, dropped. A per-bar framed box was also tried and dropped as "too much" for what's meant to be a plain, dense display; bars ended up flat, same footprint as the first cut (BAR_W columns, BAR_GAP between them, no border around the fill).

This first pass is display-only — `nav_items()` returns `[]` on purpose (same as `clock.py`). VOL/BRI grab/adjust (Enter grabs, ←→ ±5%, Enter/Esc releases) is planned as `input_claim`'s 4th consumer (see `CLAUDE/VISION.md`'s R2/R5 sections) as its own follow-up pass.

## Bars: quantized fill vs. exact readout, and why empty cells draw nothing {#bars-fill-quantization}

The readout text above each bar always shows the real, exact live percent (61%, not rounded). The bar's own visual fill is a deliberately coarser, independent number: quantized to the nearest `BAR_FILL_STEP` (5%, `_quantize_percent()`) before it reaches `eighth_block_level()`. Without this, the same real percentage change (say 59% → 61%) could look like a visible jump on one box height and nothing at all on another, purely because `eighth_block_level`'s `num_rows*8` resolution (8 is a hard Unicode constant — block glyphs only come in eighths) doesn't divide evenly into 100, and that remainder shifts with box height. Quantizing the filled value first makes the visible step boundaries (every 5%) height-independent; `num_rows*8` still governs how smoothly the already-quantized value renders within a row, not where the boundaries fall. 5% also matches the ±5%/keypress step the future VOL/BRI grab interaction will use, so the bar's visual language and how you move it agree 1:1.

A partial eighth-block glyph (▁▂▃▄▅▆▇) only paints ink across the fraction of the cell it represents. Two earlier attempts at rendering the *rest* of that cell — a "░" track texture, then a solid colored background — both ended up visibly mismatched against the empty rows around them, in two different ways. The fix that actually worked: draw nothing at all for a fully-empty row and for a partial row's unpainted remainder alike (`draw()`'s `if level == 0: continue`) — both "empty" cases render as the exact same thing (nothing, blending into the terminal's own background), trivially consistent with each other by construction, with no separate shade to mismatch in the first place.

## BAT bar's three states: Charging > plugged > plain {#bars-battery-states}

`_bat_spec()` distinguishes three mutually exclusive states, in priority order: Charging (actively adding charge — "CHG" readout, accent glow via `BarSpec.charging`) > plugged (a charger is connected per `battery.get_ac_online()`, but this pack isn't presently accepting charge — a ThinkPad charge_control threshold pausing mid-range, or already topped off) > plain (genuinely running on battery alone). Charging needs to visually pop, not just say "CHG" in text, hence the accent glow on the fill itself, not just the readout.

"plugged" shows the real percent in the same plain styling as an ordinary reading (an earlier accent-tinted version of "plugged" was tried and dropped as visually confusing next to real charging) and swaps the *label* from "BAT" to "AC" instead — the label is what actually communicates "there's a charger here" without implying an active charge. Before this distinction existed, "plugged in but paused" and "genuinely running on battery alone" looked identical (both a plain percentage), even though they're very different things to know.

`battery.get_ac_online()` is a deliberately separate signal from any pack's own `status` field: a charger can be fully connected with every pack correctly declining to charge (e.g. a ThinkPad's charge_control threshold keeping a pack between 40-80%), and without a dedicated "is a charger physically connected" check, tuicc had no way to distinguish that from "genuinely unplugged, draining" — both read as a plain percentage with no charging status. It checks *every* entry under `/sys/class/power_supply`, not a hardcoded `AC` name, because a real ThinkPad exposes charging via both a traditional `AC` (type=Mains) node and two USB-C PD ports (type=USB) simultaneously — hardcoding `AC` alone would miss USB-C-only charging setups. Returns `None` (not `False`) when the machine exposes no non-battery power sources at all, distinct from "checked, none are online" — the same None-vs-`[]` discipline used throughout this codebase (see `status_worker.py`).

## Box coordinates round to 9 decimals; navigation compares them exactly {#box-coordinate-float-noise}

Found live, this session: `resize_mode.py`'s `resize_step()`/`move_step()` computed a box's new x/y/w/h as `current + delta` (or its clamped form) with no rounding — mathematically fine, but repeated `+=`/`-=` steps through binary floating point leave a residual epsilon behind even when the net movement is exactly zero (moving a box right N cells then back left N cells landed at `5.204170427930421e-18`, not exactly `0.0` — confirmed by reproducing the exact same value in a test with the same step count). Invisible on screen — but `navigation.py`'s `tab_order()` (and `main.py`'s matching `module_position_key` for module-to-module Left/Right/Tab-rollover order) sorts by *exact* `(x, y)` tuple comparison, no tolerance. A box sitting at `5.2e-18` instead of `0.0` is no longer tied with its visually-flush neighbors at exactly `0.0` — it sorts into its own separate "column" after all of them, which silently reordered a whole module (`sessions`) to the far end of the tab/Left-Right sequence, well away from where it visually sits. Symptom: Shift+Tab backward out of `sidebar` skipped straight past `sessions` (its real, intended predecessor) and wrapped around to `sysmon` instead.

Fixed at the source rather than defensively in `navigation.py`'s comparison: `resize_step()`/`move_step()` now `round(..., 9)` their result before storing it. 9 decimals is far finer than any real terminal's `1/term_size` granularity (a 10,000-column terminal is still only 4 decimals of real precision), so it can't visibly affect where a box actually lands — it only kills noise several orders of magnitude below that. `navigation.py`'s sort itself was deliberately left exact-comparison, not given its own epsilon tolerance: the real bug was bad data reaching it, and fixing generation is more robust than having every consumer of `ModuleBox` coordinates separately guess at a "close enough" threshold.

Two currently-saved preset files had the bad values already baked in from before this fix (both cleaned as part of the same pass): `src/tuicc/presets/1.toml` (the packaged default, rounded when it was captured from live use for `CLAUDE/VISION.md`'s R7) and this machine's own `~/.config/tuicc/presets/1.toml`. A preset file saved before this fix and never re-touched by resize mode since could still carry old noise — regenerate via F2 (nudge a box one step and back) + F3 if `tab_order` ever looks wrong on an old preset.

## `mode_stack`: replacing `input_claim`'s string tiers with a real stack, one tier at a time {#mode-stack-phase-1}

A pasted proposal to "unfuck main.py" (a class-based `App` + abstract `Mode` + `push_mode`/`pop_mode`) was rejected in favor of a hybrid: a real `mode_stack: list[str]` replacing `input_claim`'s single string slot (plus `resize.active`/`resize.editing`/`help_state.active`/`spawn_picker.active`'s own separate bools, eventually), but each stack entry still dispatches to a **pure function**, not a class with methods — staying inside this codebase's established "pure function over an explicit value" convention rather than introducing an OOP layer alongside it. `MODE_HANDLERS: dict[str, Callable[[int], bool]]` is the dispatch registry, the same "add an entry, not a new branch" idiom `MODULES`/`NAV_PROVIDERS` (`render.py`) and `ACTION_HANDLERS` (`actions.py`) already use. The handler contract (`bool` return = `still_claiming`) isn't new either — it's the exact shape `launcher.handle_typing_key`/`sessions.handle_naming_key`/`sysmon.handle_nice_key`/`help_mode`'s color editor/`connectivity.handle_passphrase_key` already use and call "R2's input_claim shape" in their own docstrings.

Deliberately staying `bool`, not a richer result type, even though a later phase (resize) will need one: `VISION.md`'s own R2 backlog note already concluded resize needs a 3-state shape specifically *because* its browsing tier falls through to normal dispatch on an unhandled key, unlike every actual `input_claim` consumer today — that's a structurally different problem, not evidence the `bool` contract itself is insufficient for tiers like this one. No mypy/pyright in this repo, so widening later costs a coordinated docstring/call-site update, not a compile-time break — not worth paying for speculatively.

**Phase 1** (done) migrated only `sessions_naming`/`sysmon_nice` — the two simplest, most structurally-identical tiers — to prove the mechanism end to end before touching anything harder. Both handlers stayed as closures in `main()` (next to the existing `do_*` ones), not new functions in `sessions.py`/`sysmon.py`: `sessions_naming`'s handler needs `cfg.session_names`/`set_session_name()`, and no module in this codebase imports `config.py` — that boundary (`main.py` owns `cfg`/`theme_pairs` writes, per this file's own dismiss-vs-quit-adjacent architecture notes in `CLAUDE/GUIDE.md`) stays intact rather than growing a new cross-module dependency to avoid one closure.

**Found in review before it shipped, not live:** `connectivity_wants_input` (main.py, gating whether a passphrase/pairing prompt is allowed to claim input right now) read `input_claim is None` as a bare "is anything at all currently claimed" proxy. Migrating a tier off `input_claim` onto `mode_stack` leaves `input_claim` permanently `None` for that tier's whole lifetime, so without a matching `and mode_stack[-1] == "normal"` added to the guard, a connectivity prompt would have silently stolen the claim out from under an in-progress rename/NICE edit. This is a **standing checklist item for every future phase**, not a one-off fix: before assuming a tier's migration is purely mechanical, re-grep the file for every other place that reads that tier's old flag as a bare "is anything claimed" proxy — `resize.active`/`spawn_picker.active`/`help_state.active` all appear in that same boolean and will need the identical treatment when they migrate.

**Not touched by Phase 1, and not part of this pattern at all:** the two-level module-expansion mechanism (`any_two_level_module_expanded()` — sessions/media/sysmon's own browsing-vs-expanded state, e.g. a session slot showing LOAD/SAVE/DEL/NAME). That's an orthogonal concern — it modifies *how* Tab/Shift+Tab/Left/Right behave (`same_row_neighbor(wrap=...)` instead of module-rollover), not *who* owns the keypress — and stays exactly as it is.

**Phase 2** (done) migrated `connectivity_passphrase`/`connectivity_pairing`. Harder than Phase 1 because entry AND resolution are driven by per-frame polling of `wifi_agent.mailbox.has_pending()`/`bluez_agent.mailbox.has_pending()` (checked every loop iteration, before `getch()` runs) — a live iwd/bluez daemon can cancel a prompt at any moment, not just answer a keypress. Split accordingly: the per-keypress handling (confirm/escape/typed-text/yes-no) became two `MODE_HANDLERS` closures, same shape as Phase 1's; the entry/resolution logic itself (deciding whether something NEW should claim the stack this frame, before any key even exists) stayed a plain inline block reading/writing `mode_stack` directly, not forced into the registry — its contract (`Callable[[int], bool]`, dispatched by keypress) genuinely doesn't fit a "should I start now" question asked once a frame from two independently-shaped sources (`wifi_agent` always present, `bluez_agent` possibly `None`). Inventing a second poll-registry for two call sites would have been premature abstraction, not adherence to the pure-function convention — reading/writing the stack value directly already satisfies it.

**Found in review before it shipped, not live (second instance of the same kind of catch as Phase 1's):** the entry block's old code did `input_claim = "connectivity_passphrase"` unconditionally on both the fresh-claim path AND the retry path (iwd re-asking `RequestPassphrase` after a wrong password while already mid-flow) — a harmless idempotent overwrite either way. Naively translating that to `mode_stack.append(...)` is NOT idempotent: the retry path would push a second, duplicate frame, and the eventual single `mode_stack.pop()` only ever removes one — leaving a stale frame on top that silently swallows the next real keypress (routed into the handler, which finds nothing to do, cancels again, and only then pops the duplicate) with zero visible feedback. Fixed with `if mode_stack[-1] != "connectivity_passphrase": mode_stack.append(...)` (mirrored for pairing). **General lesson for future phases, beyond the standing "re-grep for stale is-anything-claimed proxies" checklist Phase 1 already flagged:** any `input_claim = "same value it might already be"` assignment being migrated needs the SAME idempotency check before becoming a bare `mode_stack.append(...)` — string reassignment and stack push are not interchangeable operations just because they look similar at the call site.

**Priority-ordering framing, corrected:** the old code's "connectivity checked ahead of sessions_naming/sysmon_nice/help_colors" comments described *keypress-dispatch order* (which `if input_claim == "..."` happened to run first). Once every migrated tier shares one real stack, that framing is moot — mutual exclusion is structural (one stack, one top), not achieved by check ordering. Connectivity's practical priority now comes from *when in the frame* its entry check runs: every frame, before `getch()` reads a key at all, so it claims the stack before a keypress could ever let `sessions_naming`/`sysmon_nice` claim it that same frame.

**Phase 3** (done) migrated `help_colors` + `help_state.active` — the first tier with genuine 2-level nesting on `mode_stack`: `"help"` (browsing `help_mode.py`'s panel/pages) can push `"help_colors"` (editing one color value) on top of itself, then pop back to `"help"`, landing on the colors page it came from rather than exiting entirely. Phases 1-2 only ever had one non-`"normal"` frame active at a time. `handle_help`'s colors-page confirm branch is the first case of a `MODE_HANDLERS` closure itself pushing a second frame (`mode_stack.append("help_colors")`) rather than a push happening in a plain per-frame block — confirmed safe by review: it's symmetric with the later pop, and `do_enter_help()`'s own unconditional `mode_stack.append("help")` (no idempotency guard needed here, unlike Phase 2's connectivity — there's no out-of-band re-trigger source the way daemon-mailbox polling was) can't double-fire since the generic dispatch already intercepts once `"help"` is on top.

`help_state.active` deliberately stays untouched everywhere else (the draw call site, `connectivity_wants_input`'s guard) — it's depth-agnostic (true at either `"help"` or `"help_colors"`), exactly the invariant those two sites need. Swapping either for `mode_stack[-1] == "help"` would have broken specifically during color-editing (stack-top is `"help_colors"` then).

**New subtlety this phase, not present in Phases 1-2:** `handle_help_colors` needs `nonlocal theme_pairs` — the original `theme_pairs = reassign_theme_pairs(...)` ran directly in `main()`'s own loop body, a same-scope reassignment; nested in a new closure without `nonlocal`, it would silently shadow the outer `theme_pairs` instead of updating it. The color would still save correctly to `cfg.theme`/`config.toml`, but on-screen rendering would never see the change until restart — invisible, easy to miss without deliberately checking for it. General lesson for future phases: any migrated block that reassigns (not mutates) a `main()`-local variable needs this checked explicitly, the same way Phase 2's lesson was about idempotent-assignment-vs-append.

Review found no runtime bug in the core mechanism this time (unlike Phases 1-2, each of which had one) — only three stale doc comments, one of which had already gone stale since Phase 2 shipped without catching it (the `mode_stack` declaration's own comment still said "Only sessions_naming/sysmon_nice are migrated so far"). All three fixed in the same commit. Lesson: these comments need updating on *every* phase, not just the phase that changes the code they describe, or they drift silently.

**Phase 4** (done) migrated `launcher` — the ambient "type anywhere to search apps" claim, `input_claim`'s very first historical consumer. `handle_launcher` needed three `nonlocal`s (`focus_id`, `selected_id`, `active_module`), the most of any handler so far — the only tier that reassigns `focus_id` (Up/Down shifts the ambient launch target without leaving typing mode) on top of the `selected_id`/`active_module` restore every exit path already needed. Review traced the full dispatch order and confirmed unconditional `mode_stack.append("launcher")` at both entry sites is safe, same reasoning as Phase 3's `do_enter_help()` — no out-of-band re-trigger source, and the vim/non-vim entry branches are mutually exclusive by `cfg.vim_mode` so they can't double-fire.

**Capstone: `input_claim` retired entirely.** Once launcher moved, nothing in the file assigned to it any more — `resize.active`/`resize.editing`/`spawn_picker.active` were never on `input_claim` to begin with (a separate mechanism since Phase 1's own original design), so there was nothing left for them to migrate away from on this specific variable. The declaration, its own comment block, and `connectivity_wants_input`'s now-permanently-true `input_claim is None` clause were all removed. A repo-wide grep-driven sweep also closed two comments that had already gone stale without being caught by Phases 1-2's own (main.py-scoped) sweeps: `sysmon.py`'s NICE-input section header still called itself "a 4th input_claim consumer" after Phase 1 migrated it, and `iwd.py`/`bluez.py`'s timeout-reasoning comments still named `input_claim` after Phase 2 migrated connectivity. **Lesson for any future refactor with a multi-phase comment-sweep habit: scope the sweep to the whole repo from the start, not just the file being edited** — a comment describing main.py's behavior can live in a completely different file (a docstring explaining *why* some other module's function exists) and go stale exactly as silently.

Comments that read as *historical narration* of why `input_claim`/R2 was originally introduced (`VISION.md`'s own R2/R4 sections, several "VISION.md's R2 `input_claim` shape" provenance notes on the `still_claiming` bool contract across `launcher.py`/several test files) were deliberately left alone — accurate as a record of a past decision, not a claim that the variable still exists. One `VISION.md` mention was *not* historical, though (a forward-pointer telling a future implementer to hook the not-yet-built bars VOL/BRI grab feature into "a 4th `input_claim` consumer") — that one was actionable guidance pointing at a now-nonexistent mechanism, so it got updated to `mode_stack` instead, same treatment as the analogous forward-pointer in `bars.py` itself.

**Phase 5 (final)** migrated `spawn_picker`/resize's editing level — the last two hijack tiers, never on `input_claim` to begin with. Every earlier phase's postmortem (including this section's own Phase 4 paragraph above) predicted resize would need a 3-state contract, because its browsing tier falls through to normal dispatch on an unhandled key. **That turned out to be avoidable, not just harder — the real fix was recognizing browsing isn't a true modal claim at all.** It never swallows an unrecognized key, so it's categorically the same *kind* of thing as sessions/media/sysmon's own two-level expansion state, which Phase 3 already declared orthogonal to `mode_stack`. So browsing stays exactly where and how it's always been — its own non-stack check, unchanged code, permanently excluded, not deferred further. Only `resize.editing` (a real modal — always consumes) and `spawn_picker.active` (real modal, single-shot — `resize_mode.choose()` always resolves/closes on any key) became actual `mode_stack` tags, `"resize_editing"` and `"spawn_picker"`. No `MODE_HANDLERS` contract change was needed anywhere — every handler still just returns a plain `bool`.

**New idiom this phase introduced: the "handoff."** Every prior phase's entries either stayed claimed (`return True`) or ended cleanly with nothing new pushed (`return False`, generic dispatch pops). Phase 5 has several transitions that end one claim while *immediately* starting a different one in the same keypress — picking a module in the spawn picker goes straight into editing it; F1/F3/F4/F5/F6 from inside editing hand off to help/a fully-closed session/a fresh browsing session/the spawn picker. The generic dispatch's own post-call `mode_stack.pop()` blindly pops whatever's on top *after* the handler returns — so a handler that pushes a new tag before returning `False` would have the new tag incorrectly popped, not its own old one. Fixed by a small shared pattern: the handler pops its **own** tag itself, calls whatever lands in (or pushes) the next state, then `return True` — telling the generic dispatch the stack is already correctly arranged, don't touch it again. Factored into a 3-line `handoff(do_fn)` helper for the six F-key branches (in the same spirit as `do_apply_reselect()` already being a shared helper for a repeated pattern, not a new abstraction style), and inlined once for `handle_spawn_picker`'s own choice-made case.

**Found in review before it shipped, not live (fourth instance of this exact review process catching something real):** the initial closure sketch for `handle_resize_editing` had explicit `return` statements on every branch that ends or hands off editing, but no explicit `return True` after the whole `if`/`elif` chain for the branches that just mutate and stay editing (`direction_keys`/`move_toggle`/`delete_box`) or for a genuinely unrecognized key. The *original* code always ended in one unconditional `continue` regardless of which branch matched or none did — a stray key while editing was always a harmless no-op. Without an explicit trailing `return True`, those paths would return `None` (falsy), and the generic dispatch would read that as "done" and pop — **silently ending the whole editing session on a stray keypress**, strictly worse than the original's no-op. One line (`return True` after the whole chain) fixes it; flagged explicitly in the shipped code as load-bearing, not decoration, so a future edit doesn't accidentally drop it while adding a new branch.

**This closes the whole `input_claim`→`mode_stack` migration.** Every text-input/modal claim in the codebase — sessions_naming, sysmon_nice, connectivity_passphrase, connectivity_pairing, help, help_colors, launcher, spawn_picker, resize_editing — now dispatches through one `mode_stack: list[str]` + `MODE_HANDLERS: dict[str, Callable[[int], bool]]` registry, the same "add an entry, not a new branch" idiom `MODULES`/`NAV_PROVIDERS`/`ACTION_HANDLERS` already used elsewhere in this codebase, entirely without introducing a class hierarchy — the original "unfuck main.py" proposal's `App`/`Mode`/`push_mode`/`pop_mode` sketch is nowhere in the final shape. Resize's browsing tier is the one deliberate, permanent exception, for the reason explained above — not a gap, a considered design boundary. `CLAUDE/GUIDE.md`'s resize-mode paragraph was updated in this same commit to describe the final architecture, closing the "deferred" note Phase 4's own postmortem left open.

## `LoopState`: replacing closure-capture + `nonlocal` with an explicit state object {#loopstate-migration}

A later attempt to extract main()'s per-frame update step (marquee/cava lifecycle, connectivity poll, focus-transition detection, `pending_moves` processing, `RenderContext` construction) found it blocked for a different reason than any `mode_stack` phase: most of the shared state it reads/writes (`selected_id`, `focus_id`, `active_module`, ...) is *also* read/written by every other closure in `main()` via ordinary Python closure-capture, not scoped to that one block. A plain function extraction would need ~13 in-params/~13 out-values — past where "pure function over an explicit value" stays readable, closer to a disguised class.

Root cause, not just that one block's problem: `main()`'s 18 nested closures rely on Python closures + `nonlocal` for everything they share — the same mechanism that let the mode_stack phases above work at all, but one with two real costs, both already hit live in this same session: (1) a missing `nonlocal` is a silent bug, not a crash — Phase 3 above shipped with a missing `nonlocal theme_pairs`, caught only by Plan-agent review; (2) a closure can never be flattened to a top-level function (and therefore never unit-tested, never moved to another file) as long as anything it touches is closure-captured — this is *why* candidate 3's extraction is stuck, and why `resize_mode.handle_editing_key`'s own extraction earlier this session needed a returned-signal design instead of just moving the closure as-is.

**Fix: `LoopState`** (`loop_state.py`) — a plain `@dataclass`, no methods, same shape as `ResizeState`/`LauncherState`/`PendingMovesQueue`, holding every name `main()`'s loop genuinely rebinds/mutates across frames. Explicitly excludes anything recomputed fresh every frame and never read across frames (`boxes`, `term_width`, `term_height`, WM `state`, `ordered` nav items — confirmed by tracing every read site) — those stay plain per-call parameters, since bundling them in would conflate two different kinds of "shared state." Also excludes (permanently, not just for now) `cfg`/`resize`/`spawn_picker`/`help_state`/`launcher`/`moves`/`action_ctx` — each assigned once and only ever mutated via its own fields/collections, never rebound by name, so `nonlocal` was never needed for them regardless of `LoopState`'s existence.

An exhaustive Explore pass (this session) inventoried the real scope: 18 closures, 8 `nonlocal` statements naming 6 variables (`resize_message`/`resize_message_until`, `active_module`, `selected_id`/`focus_id`, `theme_pairs`), plus `mode_stack` (shared but never literally rebound — only `.append`/`.pop`/`[-1]`-indexed) and 6 more names that are cross-frame-persistent but touched only at top level, never inside a closure (`pending_confirm`, `dismissed`, `last_focused_region_id`, `origin_region_id`, `expect_focus_reclaim`, `resolved_pid_cache`). 13 fields total. A Plan-agent review validated this and designed the phased migration below — sized (honestly) at 4-6 hours across 2-3 sessions, comparable to the whole 5-phase `mode_stack` effort above, likely bigger.

**Hard constraint driving every phase's boundary:** a field can't be half-plain-local/half-`loop_state.field` — every reader and writer, closures and top-level code alike, converts together, in the same phase. Fields are declared on `LoopState` incrementally, one phase at a time, never pre-declared as placeholders for a later phase.

**Phase 0 (done, this session) — flatten the 6 closures touching ZERO `LoopState` fields**: `do_enter_resize`, `handle_sessions_naming`, `handle_sysmon_nice`, `handle_connectivity_passphrase`, `handle_connectivity_pairing`, `any_two_level_module_expanded`. No `LoopState` dependency at all — proved the flatten-and-rewire mechanic (updating `MODE_HANDLERS`/`HANDOFF_TARGETS`/direct call sites to pass explicit params or wrap in a forwarding lambda) before touching anything stateful. `any_two_level_module_expanded` needed no signature change whatsoever — it never touched main()-local state even as a closure, only module-level functions.

**Phase 1 (done, this session) — `mode_stack`.** The single most-touched field (present in nearly every closure) but, found live during design, the *safest* to migrate first: it was never actually `nonlocal`-rebound to begin with (only mutated via `.append`/`.pop`/`[-1]`-indexing), the same "mutate an object's own field" category `cfg`/`resize`/etc. already were — so converting it needed zero `nonlocal` removal anywhere, just a rename to `loop_state.mode_stack` at all 22 real code sites (confirmed via a targeted regex pass — bare-word prose mentions of "mode_stack" in comments were left alone, matched only `mode_stack` immediately followed by `.` or `[`). Fully flattened `do_spawn_picker`, `do_enter_box_editing`, `do_enter_help`, `handle_help` (mode_stack was their only shared-state dependency). `handle_spawn_picker`/`handle_resize_editing` converted their `mode_stack` references but stayed closures — both still need `nonlocal active_module` until Phase 5, expected, not a smell mid-migration. `HANDOFF_TARGETS`/`MODE_HANDLERS` entries for the now-flattened functions became thin forwarding lambdas (`"spawn_box": lambda: do_spawn_picker(loop_state, cfg, spawn_picker)`) rather than containing logic themselves — built once before the loop, exactly as before.

**Phases 2-5 — all done, same session, continued after Phase 0+1's own commit:**
- **Phase 2 — `resize_message` + `resize_message_until`** (always paired). Fully flattened `do_save_layout`/`do_new_preset`; `do_cycle_preset` converted this pair (drops from a 3-name to a 1-name `nonlocal`), keeps `nonlocal active_module` until Phase 5.
- **Phase 3 — `theme_pairs`.** Fully flattened `handle_help_colors` — the same closure that needed the explicit `nonlocal theme_pairs` call-out back in Phase 3 of the `mode_stack` migration above; same lesson applied here too, now via `loop_state.theme_pairs` reassignment instead of `nonlocal`. Caught a real bug live, not by `pytest` (`main()`'s loop has no direct coverage — this is exactly the gap that lets this class of bug through): a regex substitution over-matched `app.theme_pairs` (`app_setup.AppContext`'s own field) into `app.loop_state.theme_pairs`, an `AttributeError` at startup, found on the first live launch and fixed immediately.
- **Phase 4 — the 6 top-level-only fields** (`pending_confirm`, `dismissed`, `last_focused_region_id`, `origin_region_id`, `expect_focus_reclaim`, `resolved_pid_cache`), batched together since none is touched by any closure — zero closure risk, purely mechanical top-level rewrites, despite the field count. One real collision risk found and avoided before it became a repeat of Phase 3's bug: `_resolve_visible_pids()` (a module-level function, not a `main()` closure) has its own unrelated parameter also named `resolved_pid_cache` — a blind text-wide substitution would have wrongly rewritten that function's own internal references too. Fixed by converting via an exact line-number-and-substring patch script instead of a pattern match.
- **Phase 5 (highest risk, landed as one atomic unit) — `active_module` + `selected_id` + `focus_id` together.** Couldn't be split further: `resolve_selection()` returns all three at 8+ call sites, and splitting them across phases would have forced ugly mixed-target unpacking for no benefit. Flattened the last remaining closures (`do_cycle_preset`, `do_apply_reselect`, `handle_launcher`, `handle_spawn_picker`, `handle_resize_editing`) and converted the entire bottom key-dispatch chain — the single largest, most mechanical piece of the whole migration, done via the same exact-line-number patch script Phase 4 introduced (one genuine mismatch caught immediately by the script's own check, a multi-line `old` string against a single-line target — fixed by hand, not a real bug). `do_apply_reselect`'s `ordered` param and `handle_launcher`'s `state`/`launcher`/`provider`/`moves` params are per-frame/stable-reference values passed explicitly, same pattern `handle_resize_editing` already used for `boxes`/`term_width`/`term_height` since Phase 1 — `MODE_HANDLERS`'s lambdas for these still close over `main()`'s own frame-local `state`/`boxes`/`term_width`/`term_height`, resolved at call time same as before, not at the dict's own one-time construction.

**This closes the whole `LoopState` migration.** Every one of `main()`'s 18 original closures either flattened to a plain module-level function (12 of them) or, for the 6 still nested (`do_save_layout`/`do_cycle_preset`/`do_new_preset`/`do_apply_reselect`/`handle_launcher`/`handle_spawn_picker`/`handle_resize_editing` — wait, those flattened too; the only closures left inside `main()` are `MODE_HANDLERS`/`HANDOFF_TARGETS`'s own forwarding lambdas), lost every `nonlocal` it ever needed. Candidate 3 (the per-frame update step, VISION.md's original third extraction target) is now genuinely unblocked — `loop_state` plus the same per-frame-transient-as-explicit-param pattern already proven here is enough to extract it normally, the way `app_setup.py`/`resize_mode.py` already were. Not attempted this session; a real next step, not infrastructure-building.

**Testability, a genuine bonus this migration unlocked incrementally, not just at the end:** field migration alone never made a closure testable — a nested `def` isn't importable regardless of `nonlocal`. Testability arrived at *flattening*, automatic at the end of whichever phase converted a closure's last remaining field — mirroring how `resize_mode.handle_editing_key` became unit-testable this same session once it stopped being a closure. Every flattened function stays in `main.py` (not moved into `modules/*.py` — the "no module imports config.py" boundary still applies; this is main-loop dispatch, not a UI module's own concern) — real unit tests for `do_apply_reselect`/`handle_launcher`/`do_cycle_preset`/`handle_spawn_picker` are a natural next step, not done this session.

## `weather.py`'s explicit location sources, no silent auto-detect {#weather-location-sources}

`rwb.py` (renamed from `clock.py` — VISION.md's R7 "real world box") shows a compact weather line plus a detailed preview, sourced from `weather.py`. Location resolution went through real values-driven back-and-forth before landing on its final shape, not just an implementation detail — worth preserving the reasoning, since it shaped the API more than the weather data itself did.

The starting idea (raw IP geolocation) was rejected first: ISP-registered IP blocks are often only accurate to "somewhere in the region," and on mobile/VPN/corporate networks can be off by a whole city or more — but the result *looks* exactly as confident as a correct one. That's a worse failure mode than a visible error: a wrong-but-plausible value is a **silent** failure precisely because nothing about it looks wrong. The fix isn't "pick a more accurate source" — it's "always show which location you're showing weather for," so a wrong resolution is at least self-evident on screen, not trusted blind. `rwb.py`'s preview always renders `weather.location_name`, regardless of which source produced it.

The more accurate alternative — GeoClue2 (D-Bus), WiFi-based positioning, the same mechanism Windows/macOS use for "how does it know exactly where I am" — was *also* rejected on a second, different ground: querying it silently, automatically, in the background, is exactly the "phone control center" pattern VISION.md section 1 explicitly disclaims ("phones hide and restrict; tuicc reveals and obeys"). The resolution wasn't "don't use GeoClue2" — precision was never the objection — it was "never do it invisibly." Once GeoClue2 became an **explicit, named, opt-in** config flag (`geoclue = true`) rather than an implicit default or an auto-detect fallback, it stopped being in tension with tuicc's own identity: the user is the one who chose it, in a file they can read.

This generalized into the actual shape shipped: `lat`+`lon` (most explicit), `geoclue` (D-Bus, precise), `ip_approx` (network-based, coarse) — each its own named, independent, opt-in config key, no single vague `auto_location` flag standing in for "guess somehow." Precedence (`lat`+`lon` > `geoclue` > `ip_approx`) and the "at least one must resolve once `[weather]` exists" validation live in `config.py`'s `_build_weather_config()`, modeled on `_build_control_toggles()`'s own `raise ValueError(...)` style (see this file's earlier sections) — fail loud at load time, never a silent partial config.

**Fourth source added later (GitHub issue #10): `location_file`.** A real gap in the three above: anyone who commits `config.toml` to a public dotfiles repo has to either drop the location entirely or publish their home coordinates — `lat`/`lon` were never separable from the rest of the file. `location_file` points at a second, standalone TOML file (flat, no `[weather]` header of its own — its only job is `lat`/`lon`) that the user keeps out of version control themselves; `_build_weather_config()` reads it the same way `load_config()` reads the main file. Same discipline as the original three: combining it with `lat`/`lon` set directly is rejected outright, not silently resolved one way — and a missing file or one lacking both `lat`/`lon` fails loud, the same as every other malformed-source case here.

`ip_approx`'s own mechanism (ip-api.com, a free, keyless, documented HTTP lookup) is deliberately its own named, visible function (`weather.resolve_from_ip()`) rather than leaning on some *other* service's undocumented internal IP-sniffing (e.g. wttr.in's own bare-URL auto-detect, considered and rejected specifically because its mechanism would be opaque from the outside) — the same "name the mechanism, don't hide it" principle applied one level down.

**Resolution is cached for the process's lifetime**, not re-run on `weather.py`'s own `StatusWorker` poll cadence (`resolve_location()`'s own docstring). This is a third, related but distinct decision: even an explicitly-opted-into source shouldn't be asked *repeatedly* in the background — a laptop doesn't move mid-session, and re-querying GeoClue2 or ip-api.com every 15 minutes would itself be the kind of ongoing background activity the whole discussion above was trying to avoid. Asking once, at startup, is categorically different from polling continuously — the weather *conditions* re-fetch on `app_setup.py`'s `poll_interval=900` (the codebase's first genuinely long `Domain` interval), the *location* does not.

## Wide-character (emoji) widths corrupt curses permanently, not just cosmetically {#rwb-wide-character-corruption}

`rwb.py`'s weather icons were the first strings in this codebase containing a genuinely wide Unicode character — an emoji, some carrying an explicit VS16 selector (U+FE0F) to force the colored emoji presentation over the thin text glyph. Found live, this broke every centering/clipping calculation that used `len(text)` as a stand-in for terminal column width (`render_utils.py`'s `centered_x()`, `_draw_centered_column()`'s `text[:col_w]` clipping, `draw_box_outline()`'s title-fit check, `draw_text_panel()`/`draw_status_line()`'s own clipping) — and the failure mode is worse than "looks a bit off": it read as **permanent** visual corruption, appearing the moment weather first rendered and never self-correcting on any later frame, even though `frame_update.py`'s `stdscr.erase()` genuinely does run unconditionally every single frame (confirmed, not assumed, before looking further). The actual mechanism: a width miscount doesn't produce a one-off glitch a later correct redraw fixes — it produces the *same wrong* centering/clipping calculation every frame, identically, so a genuinely fresh `erase()`+redraw reproduces the identical wrong result each time. "Nothing forces a redraw" (the user's own diagnosis) was the right instinct pointed at the wrong layer: the redraws were happening; the arithmetic feeding them was wrong on every single one.

Fixed with `display_width()`/`wc_truncate()` (`render_utils.py`), backed by the `wcwidth` package (this codebase's second real dependency, after `jeepney`) — not Python's stdlib `unicodedata.east_asian_width()`, which is a known-unreliable proxy specifically for emoji+variation-selector sequences, exactly the case that broke here. Confirmed live and load-bearing, not assumed: `wcwidth.wcwidth()` summed per-character (`wcwidth('☀')` = 1, `wcwidth('️')` = 0, sum = 1) **undercounts** a VS16 sequence's real rendered width — only `wcswidth()` called on the *whole sequence* correctly reports 2, matching real terminal behavior. `wc_truncate()` therefore treats a base character immediately followed by U+FE0F as one indivisible 2-column unit (never truncating between them, which would silently strand a base character without the selector that determines its presentation form) rather than summing individual `wcwidth()` calls per character.

Every `render_utils.py` primitive that previously sliced/measured text via `len()`/`text[:n]` was fixed uniformly, not just the two paths `rwb.py` happens to exercise today — `draw_box_outline()`'s title-fit math and `draw_text_panel()`/`draw_status_line()`'s own clipping included — since any *future* module introducing a wide character (another emoji, a CJK label) would hit the identical corruption otherwise, and `render_utils.py` is shared across the whole codebase specifically so a fix like this only has to happen once.

**This alone did NOT fix it — confirmed live, not assumed, on the user's own real kitty+ncurses, and worth recording precisely because it disproves the natural first guess.** `display_width()`/`wc_truncate()` compute the objectively correct Unicode column width, and STILL every fresh process, with only the corrected code ever having run, reproduced the identical corruption the moment weather first rendered. The reason: those functions only control what Python *decides* to draw and where — they say nothing about what `curses`/`ncurses` itself does *internally* once handed a string containing a wide/VS16 sequence in a single `addstr()` call. `addstr()` decodes the string and advances its own internal cursor position character-by-character using its OWN C-level width bookkeeping (used for `refresh()`'s screen-diffing) — and that bookkeeping can disagree with what the real terminal actually renders, for reasons entirely outside Python's reach (ncurses' bundled width tables predating widespread VS16/emoji-presentation support is the leading suspect, not independently confirmed). A **correct** Python-side width calculation doesn't help if the C library consuming that string still miscounts it internally — the two are unrelated computations that happen to often agree for plain text and diverge for exactly this class of sequence.

**Second attempt: dropping VS16 entirely**, falling back to each glyph's default (often plainer TEXT) presentation, as a way to sidestep the sequence mechanism rather than fix it. Genuinely stopped the corruption — but at a real cost: `🌫`/`🌧` (already `Emoji_Presentation=Yes` per Unicode even without VS16, so dropping it should have been a no-op for these two specifically) still rendered as missing/blank on the user's real font, reopening the *original* tofu-glyph complaint this whole icon saga started from. Rejected — traded one visible bug for a different one, not an acceptable end state.

**Third attempt: `draw_width_safe()`** (`render_utils.py`, still present in the codebase — see below for why it wasn't reverted) — isolates every wide (>1 column) unit into its OWN `addstr()` call, with every neighboring text segment's start column computed independently via `display_width()`, rather than one `addstr()` call spanning the whole line. The reasoning was sound (every draw call in this codebase already specifies `(row, col)` explicitly rather than relying on cursor continuity *across* separate calls — this was meant to extend the identical discipline *within* one line) and it looked live-confirmed working on a first pass. **It wasn't** — a longer, more deliberate repro (navigate directly to weather, confirm it renders cleanly, then step away exactly ONE Tab press and check immediately) still reproduced the identical stray-glyph corruption, now additionally observed bleeding into an *unrelated* module's own draw call (a stray character appearing inside the sidebar's own box-drawing border on a later frame) — meaning the corruption isn't scoped to the one write that introduced it, or even to the one box it was drawn in.

**Fourth attempt: unconditionally re-blanking the shared preview box with real space characters** every frame (`modules/preview.py`'s `draw()`, via `render_utils.draw_filled_box()`) before either of its two content branches (text preview vs. sparse workspace-tile drawing) runs — reasoning: `stdscr.erase()` might have a genuine blind spot for cells that previously held a wide character's continuation, and the sparse workspace-tile branch only draws where real window content exists, relying entirely on `erase()` to have cleared everything else. Also did not fix it, tested with the same one-Tab-away repro across 3 full navigate-away-and-back rounds.

**Fifth attempt failed the same way the first four did (plain ASCII text codes, `CLR`/`PCLD`/`OVC`/`FOG`/`RAIN`/`SNOW`/`TSTM`) — zero corruption, but it wasn't actually a fix, it was giving up on the goal.** Confirmed clean, but the user's own pushback was worth taking seriously rather than settling: "opustit je není design decision, ale defeat" (giving them up isn't a design decision, it's a defeat). That reframing led to the actual diagnostic breakthrough — a **minimal, tuicc-independent standalone curses script** (not tuicc's own code at all: one box, `erase()` every frame, alternating between multi-line wide-character content and a single differently-positioned line, exactly mirroring `draw_centered_lines()`'s own vertical-recentering behavior) reproduced the identical corruption in isolation. This pinpointed the trigger precisely, for the first time: **the width-2-to-width-1 CELL TRANSITION**, specifically when a box's vertical centering shifts a row's content between frames with different line counts (weather's 4 lines vs. some other selection's 1) — not "any wide character," not "this specific box," not anything in tuicc's own more complex rendering pipeline. Tested directly in that same minimal script: neither an explicit real-space fill nor `stdscr.touchwin()` (curses' own strongest tool — forces a complete non-differential repaint, bypassing any internal diff state entirely) fixed it there either, meaning the terminal itself (confirmed independently on both the user's real kitty session and, separately, tmux's own VT emulation layer hosting the isolated test) mishandles this specific transition even when handed objectively correct, freshly-resent content — genuinely below anything reachable from curses or Python.

**The actual, working resolution**: avoid the width-2-to-width-1 transition entirely by using only genuinely single-column (`wcwidth()==1`) glyphs — not a retreat to plain text, real icon-like symbols. The final set mixes classic pre-emoji dingbats from the U+2600 block (`☀`/`☁`/`❄`/`⛈` — the same base characters as the familiar sun/cloud/snowflake/storm emoji, just never forced into their wide color-emoji presentation, so they were never at risk) with two glyphs from the Geometric Shapes block (`◐`/`▥`) already proven to render well in this exact codebase (same family as the `●`/`○` status dots, `◀◀`/`▶`/`▶▶` transport controls, `▮`/`▯` signal bars) for the two categories the classic dingbat set doesn't cover well on its own. Explicitly avoids two *separate*, independently-confirmed risks that look similar but aren't the same bug: `⛅` (the original "partly cloudy" glyph) is width 2 even *without* a VS16 selector — easy to miss, since most of this same old block defaults to width 1; and the newer supplementary-plane pictographs (`🌤`/`🌫`/`🌦`/`🌨`) are width 1 but were independently confirmed to render as missing/tofu on this exact font — a font-coverage problem, unrelated to the width-corruption mechanism, that swapping to a *different* width-1 glyph set doesn't automatically fix unless the specific glyphs chosen also happen to have decent coverage. Live-verified clean across 3 full repro rounds in the real app, plus the isolated minimal script.

`display_width()`/`wc_truncate()`/`draw_width_safe()`/`draw_filled_box()`-in-`preview.py` were all left in place rather than reverted: each is independently correct and harmless (today's icon set never exercises the width-2 path they exist for), real tested infrastructure for the day this codebase genuinely needs a wide string (a CJK label, say), and the `preview.py` fill is legitimate hardening against shared-box content reuse in general, even though none of them turned out to be what actually fixed *this* bug.

The fifth attempt (single-width-only glyphs) shipped, got reported back to the user, and **the user rejected it anyway** — not on correctness grounds (they confirmed it worked) but because the resulting icons read as "annoyingly small" for actual glance-at-a-glance use, and pushed for one more round of investigation specifically questioning whether the bug really was unfixable below the application layer, or whether it was something fixable in this codebase's own `draw_centered_lines()`/`_draw_centered_column()`.

**Sixth attempt, and the actual, final fix: `stdscr.clearok(True)`, re-armed every single frame in `main.py`, right before its one `stdscr.refresh()` call.** The paragraph above's conclusion — "genuinely below anything reachable from curses or Python" — was **wrong**, and worth recording precisely *because* it was reasoned carefully and still wrong: `stdscr.touchwin()` (tested in the fifth attempt's isolated script) marks a window as needing refresh at all, but does NOT bypass `ncurses`' own per-line hash-based diffing within a refresh — it can still decide large parts of a "touched" line are unchanged from what it believes the physical terminal shows, and skip resending them. `clearok(True)` is a materially different, *stronger* tool never tried until this round: it forces `wrefresh()` to physically clear the terminal screen and repaint everything from scratch, unconditionally, bypassing the diff entirely rather than just invalidating its cache. The diagnostic that actually separated "curses' own model is wrong" from "the terminal mishandles correct bytes" — `stdscr.instr()`, read back right after the corrupted frame — proved curses' internal buffer was ALREADY fully correct (confirmed live: an `instr()` dump of the corrupted rows, immediately after the glitch was visible on screen, showed clean, fully-blanked content matching exactly what should have been drawn). That means the defect really is a terminal-side rendering bug in how it applies curses' own default *differential* refresh byte stream to that one cell — but "the terminal mishandles the diff" and "nothing can be done about it from curses" are different claims, and only the second one turned out false: forcing curses to stop sending a diff at all, every frame, sidesteps whatever specific escape-sequence pattern the terminal mishandles, without needing to know what that pattern actually is.

Confirmed with the same rigor the fifth attempt used, not a single successful check: the isolated minimal repro script held clean across 6+ repeated wide→narrow transition cycles with `clearok(True)` re-armed every frame (and confirmed via the SAME script that it's a genuine one-shot flag — consumed by the very next `refresh()`, silently reverting to differential mode after, so it has to be set every frame, not once at startup). Against the real app, on the user's own live sway session, with the FULL wide/VS16 icon set restored (`☀️`/`⛅`/`☁️`/`☂️`/`❄️`/`⛈️`, `▥` staying single-width — see below): the exact historically-corrupting repro (navigate to weather, confirm clean, step away exactly one Tab, check immediately) held clean across 4 full rounds, and a broader 25-step rapid-fire Tab stress sweep through many other modules' boxes found zero stray artifacts. `RAIN` uses `☂️` (U+2602 UMBRELLA + VS16, same classic U+2600-block family as the rest of the set) rather than the pictograph `🌧️` tried transiently during this investigation — deliberately avoiding the already-known tofu-risk category from the very first round of this saga, a font-coverage risk this fix does nothing to address (a separate axis from the width-corruption bug, see the fifth-attempt paragraph above).

**This shipped with one real, flagged-but-unmeasured open cost — and the flag turned out to matter.** `clearok(True)` armed every frame forces `ncurses` to do a full non-differential repaint on literally every frame, not just the ones that need it. The commit's own reasoning ("sub-millisecond, batched into one write, shouldn't be visible") was a plausible guess, explicitly NOT independently measured for flicker — and the user reported back, after actually living with it: **"ten flicker je opravdu hodně vidět... refreshovat takhle neustále celou obrazovku bude vypadat vždycky unpolished"** (the flicker is really visible; constantly refreshing the whole screen like this will always look unpolished). Visible, real-terminal flicker perception is simply not something this session's own tmux-capture-pane-based methodology can observe (it only ever samples settled end-state, never the transient repaint) — this is the first fix in this whole saga that needed the user's own eyes on the real thing to validate, not something a scripted repro could have caught first.

**Seventh attempt, before landing the actual fix: does a row-scoped alternative avoid the full-screen cost while still fixing the corruption?** Tested `stdscr.clrtoeol()` (a real terminal EL — erase-in-line — escape, structurally different from `addstr()`'s own diffed character rewrite) explicitly on each of the box's own rows, right before drawing new content, with NO `clearok()` call anywhere. **Failed** — the stray leftover glyph survived even a genuine erase-in-line escape covering that exact cell, a stronger and more surprising negative result than it first looks: it means the terminal's mishandling isn't specific to curses' own diffed-rewrite code path, it survives a completely different, dumber erase primitive too. This rules out "just erase the row a different way" as a category, not just the one technique tried. (Separately tested and also not pursued further: `curses.newwin()`-based subwindow with `clearok(True)` scoped to just that subwindow rather than `stdscr` — confirmed to still fix the corruption, but `clearok`'s own spec wording ("clear the screen completely... redraw the entire screen") gives no reason to expect it's actually spatially scoped to the subwindow's rectangle rather than the whole physical terminal regardless of which window's flag triggered it, and this session's capture-based methodology can't distinguish the two either — not disproven, just not worth the architectural cost of converting `preview.py`'s shared box to a real subwindow, across every module's `stdscr`-writing `draw()`, on an unconfirmed hunch.)

**The actual, final fix: frequency-gating, not spatial scoping.** `clearok(True)` stays exactly the mechanism (still the only one confirmed to work at all) — but it's now armed only on the ONE frame where the shared preview box's own line count actually changes from the previous frame (`main.py`'s `current_preview_line_count != loop_state.last_preview_line_count` check, right where `draw_all()` already runs, immediately before `refresh()`), not unconditionally every frame. `LoopState` gained `last_preview_line_count` for this — a real, deliberate exception to `main.py`'s own "nothing is cached per-frame" discipline (see this file's architecture notes), justified because the alternative (recomputing "did anything relevant change" from scratch with no memory of the last frame) is architecturally impossible for a frequency-based decision, by definition. Confirmed via the isolated repro script (rebuilt a fourth time, this round with a fire-counter): 8 alternating wide/narrow cycles fired `clearok` roughly once per actual transition, not once per frame, and content stayed clean throughout — then confirmed the gate itself works, not just "still armed from before," by repeating the SAME mode several times in a row and observing the fire counter barely move. Re-verified against the real app on the user's live sway session with the exact same standard as every prior round: the historically-corrupting repro clean across 5 full rounds, plus a 25-step rapid-fire Tab stress sweep with zero stray artifacts. The remaining cost is real but now bounded and specific, not blanket: a full-screen flash still happens on the actual frame a preview's line count changes (most visibly, navigating onto or away from weather) — this is the one moment curses truly has no cheaper correct option for on this terminal, not a residual laziness; whether that occasional, activity-tied flash itself reads as acceptable is, again, for the user to judge live, not something resolvable from this session's own tooling.

**The user pushed back a second time, harder: "ten flicker je opravdu hodně vidět... to zabíjí celý dojem"** (the flicker is really visible, it kills the whole feel) — even the frequency-gated version's occasional, activity-tied flash was rejected outright, not just the always-on version. Any visible flash, however rare, was ruled unacceptable.

**Eighth attempt, and the actual final fix: `stdscr.redrawln(beg, num)`.** `clearok(True)`'s own mechanism was the real problem, not just how often it fired: per its spec wording, it sends the terminal an actual clear-screen capability before redrawing — a genuinely different, more disruptive KIND of operation than a normal content update, which is very plausibly why it visibly flashed even scoped to one frame. `redrawln()` (Python's `window.redrawln(beg, num)`, wrapping ncurses' "these N lines starting at `beg` are corrupted, redraw them completely on the next refresh") is a materially different primitive: it marks specific lines' hashes as invalid so curses' normal refresh logic treats their FULL width as needing output — forcing a real, unconditional retransmission of those lines' bytes — WITHOUT ever sending a clear-screen command. Mechanically, it's the same *kind* of operation (cursor-positioned character writes) as any ordinary content update already uses without flicker; the only difference is it forces the full line width to be sent rather than trusting the diff.

Tested `touchline()` first (Python's more general "mark lines changed" draw-optimization call, the same underlying idea) — it did NOT fix the corruption, ruling out "any kind of dirty-marking" as sufficient. `redrawln()` specifically — a different, more targeted primitive ("these lines are *corrupted*", not just "changed") — did fix it, live-confirmed clean across 6 repeated wide/narrow cycles in the isolated script, then 5 full rounds of the historically-corrupting repro plus a 25-step rapid-fire stress sweep against the real app, zero stray artifacts either time. Landed exactly where `clearok(True)` used to sit in `main.py`: same `current_preview_line_count != loop_state.last_preview_line_count` gate (kept, even though `redrawln()` likely doesn't need frequency-gating to avoid a visible cost the way `clearok()` did — no reason to force even a cheap resend on frames where nothing preview-relevant changed), but scoped SPATIALLY too this time, to just `boxes["preview"]`'s own interior rows via `redrawln(preview_y + 1, preview_h - 2)` — not the whole terminal. This is the first attempt in the whole saga that's scoped on both axes (which frames, which rows) rather than trading one axis away for the other.

Whether this is genuinely, perceptibly flicker-free on the user's real kitty terminal is, like every visual-cost claim in this saga, for them to confirm live — this session's own tmux-capture methodology proves correctness (no stray glyphs) but has never been able to observe transient flicker either way, a limitation worth restating rather than glossing over now that it's mattered twice.

**Confirmed live by the user, restarting their real, daily-driven tuicc process (not this session's own tmux test copy): "I DONT SEE ANY FLICKER!!!"** Both halves of this whole investigation are now independently closed out — no corruption (`stdscr.instr()`-verified, adversarial-repro-verified) and no visible flicker (only ever verifiable by the user's own eyes on the real terminal, now done). The full wide/VS16 icon set (`☀️`/`⛅`/`☁️`/`☂️`/`❄️`/`⛈️`) ships as the final, working answer — not a downgrade, not a compromise, the actual thing the user asked for from the start of this saga.

**General lesson for the next Unicode-adjacent rendering bug in this codebase**: a fix that looks complete from the Python side, passes one live test, and is *reasoned correctly* about the mechanism it targets can still be wrong if the actual defect sits at a lower layer (here: inside `ncurses`'/the terminal's own handling of a specific cell-width transition) that Python-level code has no visibility into. "It works" needs a real, adversarial repro (navigate away, wait, try a different sequence) before being trusted — a single successful check right after a change is not enough evidence. Separately, and validated four times over by this same bug now: "it's technically correct" and "we're done" aren't the same claim — the fifth attempt was correct but still worth pushing back on (the user's call, not something to have assumed), the sixth attempt's own careful "this is below the reachable layer, full stop" conclusion turned out to have an untested tool one level further down that reversed it, that same sixth attempt's own "should be imperceptible" performance reasoning also turned out wrong once actually lived with, and the seventh attempt's own frequency-gating, while a real improvement, wasn't sufficient either — the disruptive PRIMITIVE itself (a clear-screen command) was the problem, not merely how often it ran. Two closely related but genuinely distinct things this bug needed measuring, not reasoning about, in the end: whether a fix eliminates the corruption (this session's own tmux-capture methodology *can* answer that, rigorously, via `stdscr.instr()` and repeated adversarial rounds) and whether a fix's own visual cost is acceptable (that one always needed the user's real eyes on the real terminal — no amount of careful reasoning about escape-sequence byte counts or operation "kind" substitutes for it, only narrows the guess). The actual, load-bearing diagnostic move for the correctness half was `stdscr.instr()` — reading back curses' own belief about screen contents, rather than only ever inspecting what the terminal visibly renders — since that's what turned "is this fixable at all" from a guess into a proven yes/no; the load-bearing move for the flicker half was simply taking "it kills the whole feel" at face value and going looking for a different primitive, rather than trying to make the existing one cheaper.

## Same pixel resolution, different terminal grid — auto-selecting a preset by size {#preset-auto-select-by-size}

Prompted by the user noticing tuicc "looks different" between two machines they both described as 1920x1080 — a genuinely good observation, not a mistake: pixel resolution and curses' own `getmaxyx()` cell grid are unrelated numbers. Font size (kitty's `font_size`), DPI/output scale (sway's per-output `scale`), and the font's own glyph metrics all factor into how many columns/rows a given pixel resolution actually produces — two machines can report the identical resolution and still hand tuicc completely different `term_width`/`term_height`. Since `compute_boxes()` computes every box as a ratio of that grid (see this file's own architecture notes on `layout_engine.py`), a preset tuned by eye on one grid can look visibly cramped, or leave odd extra space, on another.

Already-existing, explicitly-documented behavior (see `presets/1.toml`'s own header comment, predating this section): "if a box looks wrong on a terminal size very different from the one you set it up on, that's expected, not a bug — use F2." That answer stands — this section doesn't change what F2/preset design does, it only automates *picking which preset* applies, for anyone who maintains more than one.

**Rejected up front, in an earlier live discussion this session:** having tuicc itself dynamically rescale a SINGLE preset's own ratios based on terminal size (breakpoints within one preset, CSS-media-query style). This is effectively the `right_of`/`below`/`cols`/`rows` derivation system this codebase already tried once and deliberately removed for complexity (see `compute_boxes()`'s own "flat per-box loop, not a dependency resolver" note) — reintroducing an equivalent mechanism under a different name was judged not worth it unless a simpler approach couldn't cover the real cases. Chose the preset-selection route: `[[layout.box]]` ratios stay exactly as flat and independent as they already are; only *which preset* gets loaded becomes size-aware.

**Mechanism**: an optional `[preset]` table in a preset's own TOML file:

```toml
[preset]
min_cols = 200
min_rows = 50
```

Opt-in per preset — a preset with no `[preset]` table (every packaged preset, as shipped) never participates, so this changes nothing for anyone who hasn't set it up. `config.pick_preset_for_size(cols, rows)` scans every known preset (`available_preset_numbers()`'s own dual-dir precedence — user copy wins over packaged if both exist, matching `ensure_preset_exists()`) and picks the one with the largest `min_cols*min_rows` product among those that still actually fit (`cols >= min_cols and rows >= min_rows`) — "best fit that still fits," not the first one that technically fits (would under-use a screen a bigger preset was designed for) and not the closest by absolute difference (could pick one that doesn't actually fit at all). Read-only: unlike `ensure_preset_exists()`, this never materializes/copies a packaged preset just to probe its thresholds — `load_config()`'s own `ensure_all_packaged_presets_exist()` call already guarantees every packaged preset exists on disk before this ever runs.

**Deliberately session-only, never persisted.** `load_config()` gained an optional `preset_override` parameter — when `main.py` computes one via `pick_preset_for_size()` (using `stdscr.getmaxyx()`, only available once curses has actually initialized, hence why this can't live inside `load_config()`/`build_app()` themselves — see their own updated docstrings) and passes it through, it wins for that one load, but `config.toml`'s own `[layout] preset` line is never rewritten. This is a real, deliberate distinction from F4/F5 (`set_active_preset()`/`save_new_preset()`), which DO persist: an auto-selected preset reflects "what fits this machine's screen right now," not a standing preference — silently overwriting a manually-chosen preset number just because tuicc happened to launch on a different-sized grid this one time would be exactly the kind of hidden-default behavior this codebase's own principles (VISION.md section 6: "no hidden defaults") reject. F4 mid-session still works exactly as before, cycling from whatever preset is *currently* active (auto-selected or not) and persisting that choice like it always has.

**Scope, deliberately narrow for v1**: startup-only, not live on terminal resize. `compute_boxes()` already re-layouts every frame against the CURRENT grid regardless (nothing new needed there for a plain resize to look correct within one preset) — but re-running preset SELECTION mid-session, while the user is mid-interaction (`selected_id` pointing at a module/item that might not exist in a newly-selected preset), was judged a real source of surprise (the same class of bug the Sessions/empty-module `next_module_name` dead-end was) for a benefit (reacting to a resize that happens mid-session, not just at launch) that doesn't match the actual reported problem — two different MACHINES, not one terminal window being live-resized. Revisit only if that specific case is reported for real.

## Consolidating two parallel text-width implementations {#text-width-consolidation}

Found live while auditing modules for the same class of bug the RWB corruption saga above was ultimately about (a wide/CJK/emoji character measured by `len()`/plain slicing instead of real terminal columns) — `render_utils.py`'s `display_width()`/`wc_truncate()` (built this session, `wcwidth`-backed, correctly handles VS16 emoji sequences) and a SEPARATE, pre-existing `text_width.py` (`unicodedata.east_asian_width()`-based, built independently in an earlier session for a real, different bug — Spotify/browser track and window titles with CJK text overflowing `sidebar.py`/`media.py`) had ended up as two parallel implementations of the same concept, with a real functional gap between them: `unicodedata.east_asian_width()` correctly classifies East Asian Wide/Fullwidth characters, but has no concept of VS16 variation-selector sequences at all — meaning `text_width.py`'s own `display_width()` would have UNDERCOUNTED a VS16 emoji sequence exactly the same way the original, pre-fix `len()`-based code did (see this file's own `#rwb-wide-character-corruption` section for why that specific miscounting is dangerous, not just imprecise). Since `media.py` (one of `text_width.py`'s two consumers) draws real track titles — which absolutely can contain modern emoji with VS16 — this was a live, real gap, not a theoretical one.

Confirmed `render_utils.py`'s `wcwidth`-backed implementation is a strict superset before consolidating (not assumed): `wcswidth()` correctly classifies East Asian Wide/Fullwidth characters as 2 columns too, same as `unicodedata.east_asian_width()`'s Wide/Fullwidth classes — every one of `text_width.py`'s own CJK-specific test cases holds equally under `render_utils.wc_truncate()`/`display_width()` (ported into `test_render_utils.py` rather than just deleted, so that coverage isn't lost). `text_width.py` and `tests/test_text_width.py` were retired outright — not left as unused dead code — once both consumers (`sidebar.py`, `media.py`) were migrated onto `render_utils.py`'s versions; same "don't carry a redundant implementation forward" precedent as R3's own `ConnectivityWorker` retirement (VISION.md's R3 section: "found live it would've been... nothing of its own").

**Wider audit, same pass**: a grep for `addstr(...[...])`-style plain-slice truncation across every module turned up the same pattern in `launcher.py` (search query text — genuinely user-typed, can be non-Latin), `power_menu.py`/`quick_actions.py` (user-configured labels/icons — `quick_actions.py`'s `action["icon"]` field is *specifically* meant to hold emoji, the highest-risk site found), `sessions.py` (live-typed rename input, saved session names), `sysmon.py` (window labels via `_format_window_label`, the diagnostics summary line), and two real bugs in `connectivity.py`: a WiFi SSID's `str.ljust()`-based padding (pads by character count, not display width — a wide/emoji SSID, which real people genuinely set, would under-pad and throw the following signal-bars glyph out of position) and a Bluetooth device name truncated the same unsafe way. `preview.py`'s own per-window corner/center labels (built from real window titles via `condense_title()`) had the identical gap — the exact class of content (`sidebar.py`/`media.py`'s own titles) `text_width.py` was originally built for, just never extended to this file. All fixed the same way: `wc_truncate()`/`display_width()` from `render_utils.py`, now the one shared implementation. Live-verified against the real app afterward (WiFi rows, signal bar alignment, general smoke test) — no regressions, no crashes.

## R8's push-worker gate, resolved: pyudev over UPower, with a real runtime probe {#battery-push-pyudev}

R8's own closing section (`VISION.md`) named this the one real gate before v0.1.0: `battery.watch()`'s sysfs `select.poll()` attempt was confirmed empirically unreliable (never fired once across several real charger unplug/replug cycles), and the section committed to either making push work for real via a different event source, or deleting `push_worker.py`/`combined_status.py`/`battery.watch()` outright.

**Confirmed live, first, before writing any replacement code** (the section's own stated acceptance bar): `udevadm monitor --subsystem-match=power_supply`, run against several real charger plug/unplug cycles on the same machine the sysfs attempt failed on, reliably captured `change` events on `AC`, `BAT0`, `BAT1`, and the USB-C PD source device — every single cycle, no misses. This is a genuinely different code path than the sysfs `select.poll()`/`sysfs_notify()` mechanism that failed: `udevadm monitor` listens on the kernel's netlink uevent broadcast, which `udev`/`systemd-udevd` (or `eudev`) processes independently of whatever's wrong with `sysfs_notify()`'s wiring for this specific attribute on this kernel/driver combination. Chose `pyudev` (wraps this exact netlink mechanism) over UPower D-Bus — UPower itself is `near-universal but not guaranteed` (needs `upowerd` running, a real daemon dependency `pyudev` doesn't have), and this live confirmation already validated the udev/netlink layer directly, no need to add a second daemon dependency on top to reach the same underlying kernel signal.

**`battery.watch()` rewritten onto `pyudev.Monitor.from_netlink()`**, filtered to the `power_supply` subsystem, replacing the sysfs fd-polling entirely (not layered alongside it — the old mechanism is gone, not kept as a second fallback tier, since it's confirmed not to fire at all on real hardware). Same external generator contract as before (`stop_event` in, yields once per detected change or every `fallback_seconds` regardless) — a burst of near-simultaneous events (AC + BAT0 + BAT1 + the USB-C source all firing within milliseconds of the same physical plug/unplug, confirmed in the live `udevadm` capture) is drained with a non-blocking `poll(timeout=0)` loop before yielding once, rather than yielding once per device for what's really one physical event.

**A real, live-discovered wrinkle: `pyudev.Context()` isn't guaranteed to work just because the package imports.** `pyudev` lazily `dlopen()`s the real `libudev.so` via `ctypes.util.find_library()` — confirmed live, on this exact project's own NixOS dev environment, that a plain `pip install pyudev` into `.venv` imports the Python package fine but raises `ImportError("No library named udev")` the first time `Context()` is actually constructed, since NixOS doesn't populate the standard FHS library-search paths ctypes relies on (confirmed the mechanism itself is sound via `nix-shell -p 'python3.withPackages (ps: [ps.pyudev])'`, which links correctly). This directly mattered for the user's own explicit, stated design requirement — no per-user manual intervention — so `battery.PYUDEV_AVAILABLE` is a REAL runtime probe (constructs a throwaway `Context()`, catches any exception) rather than a bare `try: import pyudev`, checked once at import time so `app_setup.py`'s own push-vs-pull wiring decision is made correctly up front, not discovered only after a `PushWorker` thread is already running and failing. See `CLAUDE/NOTES/known-limitations.md#pyudev-libudev-nixos` for the current state of this specific gap on NixOS and what would actually fix it (an environment-level `LD_LIBRARY_PATH`/launch-Python change, not something the code itself can solve without replicating Nix's own library-wrapping logic).

**`app_setup.py`'s wiring**: `battery` becomes a `PushDomain` (via `PushWorker`) when `battery.PYUDEV_AVAILABLE` is true, or stays exactly the plain fast-poll `StatusWorker` `Domain` (`poll_interval=0.3`) it already was otherwise — both paths call the same new `battery.read_status()` (pulled out of the old inline lambda specifically so both wiring branches share one function, not two copies of the same `aggregate(get_packs(), get_ac_online())` call). `status_worker` (the field name stays, for now, matching every existing call site that already treats it as "the shared status object" without caring which mechanism backs any given domain) is now always a `CombinedStatus`, even in the all-poll fallback case — an empty `PushWorker` is a harmless, valid `CombinedStatus` too, so there's exactly one type to reason about regardless of which branch actually ran. `push_worker.py`'s `PushWorker` gained `get_action_error_for(domain_name, key)` as part of this — it existed on `StatusWorker` (needed by wifi/bluetooth's per-network/per-device action errors) but had no `PushWorker` equivalent, a real gap only surfaced once something actually tried routing `status_worker.*` calls through `CombinedStatus` for real instead of just having it exist, tested, unused.

This closes R8's own gate: `push_worker.py`/`combined_status.py` are no longer "built, tested, unused" — a real domain (`battery`) uses them in production, automatically, with a graceful, transparent fallback to the pre-existing polling behavior wherever the push mechanism can't actually engage.

## sidebar.py overflow: budget-based scrolling, not windowed_list.py's slot-count windowing {#sidebar-variable-height-windowing}

Reported live from a screenshot, during the sway/i3 behavioral-verification pass (`CLAUDE/GUIDE.md`'s own checklist): with enough real windows spread across `total_workspaces` slots, `sidebar.py`'s "Workspaces" box had no bound check at all — `draw()`/`nav_items()` both just walked every slot, advancing `item_y` unconditionally, with zero regard for the box's own `h`. Past a certain point this ran straight into whatever module sits below it in the layout (`Control`/`Power Menu` in the default preset), reading as visual corruption rather than an intentional "there's more than fits" state.

Genuinely different problem from every other windowed list in this codebase (`sysmon.py`'s window list, `media.py`'s Now Playing/Output sections): `windowed_list.py`'s existing `window_start()`/`section_rows()` machinery assumes every item occupies exactly one row, true for those two but not for a workspace slot, whose own height depends on how many windows it holds (`_slot_height()`). Reusing `windowed_list.py`'s API directly wasn't possible without either lying about item count (pretending N windows == N rows) or a real API change to that shared module for one caller's own variable-height need — instead, `sidebar.py` gained its own budget-based analogue, `_visible_slot_range(heights, selected_index, available_rows)`: the widest contiguous range of slots that fits within `available_rows` while keeping `selected_index` inside it, computed fresh every call (same "nothing cached per-frame" discipline the rest of this codebase already holds to).

**First version anchored the window on `selected_index` and extended FORWARD first, backfilling backward with leftover room — its own test suite caught this disagreeing with `window_start()`'s already-established bias**: `window_start()`'s own docstring is explicit that a selection newly scrolled past the visible window "shifts by exactly enough to make it the last visible slot" — i.e. a forward-scroll reveals the new selection at the BOTTOM of the window, matching ordinary list-navigation intuition (scrolling down reveals more below, not above). The forward-first version instead put a freshly-scrolled-to selection at the TOP of the window — not wrong on its own (selection stays visible either way), but a second, disagreeing windowing convention in the same codebase is worse than either choice alone. Rewritten to anchor `selected_index` as the LAST slot first (extend backward to fill budget), then extend forward with any budget still left over (covers the "selection is near index 0, more fits below it" case `window_start()`'s own `selected_index < visible_slots -> start at 0` branch handles) — every existing test needed re-deriving by hand against this corrected bias before the implementation was fixed to match, not the other way around.

Peek `NavItem`s for Tab to reach hidden slots reuse the same mechanism `sysmon.py`/`media.py` already established (`section_nav_indices`'s own "before"/"after" items) — a hidden slot just past either edge of the visible window gets a `NavItem` whose `rect` borrows the boundary VISIBLE slot's own rect (never drawn as itself), and landing on it via Tab updates `ctx.selected_id`, which `_visible_slot_range` recomputes around fresh next frame, pulling the window along.

Live-verified against the real app (a genuinely overflowing 10-workspace layout in a deliberately short terminal): the "Workspaces" box now keeps a clean bottom border regardless of content, no bleed into `Control` below it in any captured frame; stepping Tab through the list showed the window smoothly shift `[1,6] -> [2,7] -> [3,9] -> [4,10]` as selection moved down, reaching workspace 10 (the very last slot) exactly as designed, then resetting cleanly back to `[1,6]` the moment selection left the sidebar for a different module — matching the same reset-to-top behavior `sysmon.py`'s own peek windowing already has for the identical case.

`sidebar_compact.py` (the separate, deliberately-not-shared-code compact variant — see its own docstring for why it isn't a mode flag on `sidebar.py`) already had a bound check (`_slot_positions()`'s own `if row >= y + h - 1: break`) — no visual corruption there, but also no scrolling: hidden slots past that bound are simply unreachable via Tab, not windowed the way the fix above gives `sidebar.py`. Left as a known, smaller, separate gap — flagged rather than silently fixed in the same pass, since it's a genuinely different module with its own tradeoffs (uniform row height, unlike `sidebar.py`'s variable case), not an oversight in this fix.

## Shift+Tab into sidebar always lands on the TRUE last workspace, not whatever the default window contains {#sidebar-shift-tab-true-last}

Reported live right after the scrolling fix above shipped: Shift+Tab rolling backward from `Control` into `Workspaces` landed on workspace 9, not workspace 10 (the real last one) — a genuine, separate bug from the overflow fix itself, only exposed once sidebar actually had a scrollable window to get wrong.

Root cause: `navigation.py`'s `last_item_in_module(items, module_name)` only ever scans the SINGLE `items` list `collect_nav_items()` already computed for the current frame — built using whatever `ctx.selected_id` was active BEFORE this keypress (almost never sidebar's own, when rolling in from Control). With selection elsewhere, sidebar's own `nav_items()` windows itself around the default (top-anchored) position, and that returned list commonly doesn't contain workspace 10 at all — no amount of scanning finds an item that was never in the list to begin with. This is a structural gap shared by every `windowed_list.py`-based module (`sysmon.py`, `media.py` too), not something unique to sidebar's own new mechanism — just never noticed there, likely because those lists don't get rolled into backward from an adjacent module as constantly as sidebar (core, always-visible) does.

Fixed with a new, generic sentinel, `navigation.LAST_ITEM_QUERY` — a `ctx.selected_id` value no real `NavItem` id can ever collide with (every real id is `"module_name:something"`). `main.py`'s Shift+Tab dispatch gained a `sidebar`-specific branch, structurally mirroring the pre-existing `sessions` exception one case above it (Shift+Tab into `sessions` always lands on slot 1, never its last item — same file, same block): when `prev_item_across_modules()` picks a `sidebar` item out of the stale `ordered` list, `main.py` throws that away and re-queries `NAV_PROVIDERS["sidebar"]` DIRECTLY with a shallow-copied ctx (`dataclasses.replace(ctx, selected_id=LAST_ITEM_QUERY)`), taking THAT fresh call's own last item instead. `sidebar.py`'s `_selected_slot_index()` recognizes the sentinel and returns the true final index (`len(slots) - 1`) directly, which `_visible_slot_range()` then anchors on exactly like a real selection would — no changes needed to the windowing math itself.

Scoped to `sidebar` only for now, not retrofitted into `sysmon.py`/`media.py` even though they share the identical structural gap — neither has been reported hitting it in practice (their own lists are commonly short enough not to need scrolling, or aren't rolled into backward as routinely), and the shared `LAST_ITEM_QUERY` sentinel plus the `main.py`-side pattern are now proven and trivially copyable if that ever changes — not preemptively duplicated into two more modules on spec.

`Left`/`Right` (`module_next_keys`/`module_prev_keys`, vim-mode `h`/`l`) don't share this bug — both directions already use `first_item_in_module()` unconditionally (see that dispatch block), and "first" is always correct by construction: the default (no-selection) window is already top-anchored, so it naturally contains the true first item regardless of scrolling state. Only "roll in backward, land on the true LAST item" needed the fix.

Live-verified against the real app: positioned precisely on Control's first item (`Airplane Mode`, reached via `Right` — jumps by whole module, deterministic) rather than via error-prone repeated Tab/Shift+Tab counting, then a single Shift+Tab landed the sidebar's own window on `[8,10]` (workspace 10 visibly selected, its own two floating windows shown in the preview panel) with an `↑ +7 ws, +11 win` indicator above — confirming both this fix and the scrolling fix's own "hidden content" indicator (see below) together, in the one live sequence most likely to have exposed either regressing the other.

## "+N workspaces, +N windows" hidden-content indicator — a second, deliberately-later border redraw {#sidebar-hidden-content-indicator}

Requested alongside the scrolling fix above: when the workspace list is cut off top or bottom, show roughly how much is hidden, not just that it's scrollable — explicitly NOT at the cost of the box's own content space (the user's own call, after seeing a first attempt that reserved a content row for it and didn't like the tradeoff).

**First attempt: `render_utils.draw_box_outline()` gained a `bottom_label` parameter mirroring its existing `title`** — symmetric, looked reasonable, reverted almost immediately: live-tested and found the label silently overwritten every single frame. Root cause: this codebase's own tightly-packed presets commonly place two module boxes directly adjacent with ZERO gap between them, meaning one box's bottom border row and the next box's top border row are the literal SAME physical terminal row — confirmed exactly this way in the default preset's own numbers (`sidebar`'s `y + h` == `control`'s own `y`, precisely). Whichever module's `draw()` runs LATER in `MODULES`' own dict iteration order simply overwrites whatever the earlier one put on that shared row. The matching `title`-in-top-border case happened to work all along purely by coincidence of draw order (`sidebar` itself draws after whatever's above it in the normal pass) — not because top borders are inherently any safer than bottom ones.

**Second attempt: moved both indicators into real CONTENT rows inside the box's own interior instead of either border** — genuinely safe from the clobbering above, but rejected live by the user for a different, entirely valid reason: it costs the box a real row of actual workspace content just to show "there's more," a worse tradeoff than the problem it solves. Reverted a second time.

**Landed on: keep the border, but redraw it a SECOND time, deliberately LATER than every module's own normal `draw()` pass** — same underlying idiom this codebase already uses for resize mode's editing highlight and `help_mode`'s whole panel (see `CLAUDE/GUIDE.md`'s own architecture notes: drawn directly onto `stdscr`, after/instead of `draw_all()`, not through the normal per-module contract). `sidebar.draw_hidden_indicators(stdscr, box, ctx, module_name)` is a NEW, second entry point — not part of the module's regular `draw()`/`nav_items()` contract — that `main.py` calls once, unconditionally, immediately after `draw_all()` returns. Being the literal last thing drawn on sidebar's own top/bottom rows for the WHOLE frame is the entire point: it no longer matters which module happens to be adjacent or what order `MODULES` iterates them in, since nothing else draws after it. `draw()` itself still calls `draw_box_outline()` once, normally, with a plain `title="Workspaces"` — `draw_hidden_indicators()` simply calls it AGAIN on the exact same box, this time with the indicator folded in, an intentional, harmless redundant redraw of the same border rather than the two functions needing to coordinate who draws what.

A second bug surfaced live once this combined-string version shipped: `"Workspaces +7 ws, +11 win"` routinely doesn't fit a sidebar-width box, and `draw_box_outline`'s own existing fallback for a title that doesn't fit is BLANK dashes — no text at all, not even bare `"Workspaces"`. Fixed with `_fitting_title(base, indicator, w)`: tries `"base indicator"` combined, then `indicator` alone (dropping the now-redundant base name once scrolled), then bare `base` as the last resort.

**Requested next: right-align the indicator to the box's own right edge**, rather than wherever it happens to land embedded in a combined, left-anchored title string. Surfaced the SAME asymmetry between top and bottom rows a third time, in a new way: the TOP row is safe to fully redraw combined (`_fitting_title()` + `draw_box_outline()`, as above) because sidebar OWNS that title outright — whatever's above it (`sessions`, in the default preset) never puts real content on the shared row, only plain dashes. The BOTTOM row is NOT safe to redraw the same way: whatever's directly below (`control`) has its OWN real title drawn there, which a combined redraw would silently clobber — confirmed live, in exactly this form: `"Contr +5 ws, +11 win"`, the indicator chopping `"Control"`'s own name mid-word because the first right-alignment attempt assumed the bottom row was clear of any real content, the same wrong assumption the very first `bottom_label` attempt made in a different guise.

Landed on genuinely different treatment per edge, not a stylistic choice: `_fitting_title()` (full redraw, safe) for the top row; a narrower `_right_aligned_overlay_col()` (writes only its own cells, touches nothing else) for the bottom row, with a conservative left margin (`max(w // 2, 12)` columns) standing in for knowledge sidebar can't have about another module's real title width without violating "core never guesses a module's internal layout" in the other direction. A heuristic, not a proof — clears every real title in this codebase's own default preset (confirmed live against `"Control"` specifically), but a sufficiently long custom title on whatever sits below in a different preset could still collide; flagged in the function's own docstring rather than silently assumed solved.

`_hidden_summary(slots, indices)` — `"+N ws, +M win"` — counts both dimensions deliberately: workspace count alone can undersell it badly (`"+1 workspace"` reads as trivial when that one hidden workspace happens to hold a dozen windows), so the real window count across every hidden slot is summed too, omitted from the string entirely when it's zero.

Live-verified through every attempt, not just the final one: the content-row version confirmed working before being rejected on tradeoff grounds (not a bug); the combined-title version confirmed both for the common case and the narrow-box degradation; the final split top/bottom version confirmed independently on both edges — `┌─ +7 ws, +10 win ───────┐` at the top (right-aligned, "Workspaces" correctly dropped once the combined text stopped fitting) and `└─ +6 ws, +13 win ───────┘` at the bottom, with `"Control"` rendering completely intact directly below it once the collision fix landed. One unexplained, non-reproducing artifact (a single garbled `"ble1"` fragment where a workspace slot's own `"┌ 1"` label should have been) showed up once, immediately after this session's own tmux test harness crashed and had to be restarted — never reproduced across 20+ further deliberate navigation cycles afterward, including rapid back-to-back stress cycling with no delay between keypresses. Most likely a testing-environment artifact from the crash/restart itself rather than a genuine rendering bug, but not proven either way — worth a note if anyone ever sees something similar recur under normal use, rather than silently forgotten.

## `Provider.copy_to_clipboard()` — sysmon's diagnostics row, Enter-to-copy {#sysmon-diagnostics-copy-to-clipboard}

Requested live, right after the sidebar work above: pressing Enter on sysmon's diagnostics summary row (the "N issues" row backed by `diagnostics.py`'s `general_errors`/OOM/failed-units data) should copy its own hover-preview breakdown to the system clipboard, rather than being a pure no-op the way it is today.

**New optional `Provider` method, `copy_to_clipboard(text: str) -> bool`** — joins `mark_self`/`dismiss_self`/`focus_self`/`no_focus_next_window`/`resolve_pid`/`set_floating_geometry` as a non-abstract, default-no-op member of that family (see `CLAUDE/GUIDE.md`'s own "optional provider methods" note and `#optional-provider-methods` below it), default implementation just returns `False`. This is the FIRST provider method to shell out to a genuine external CLI tool rather than either WM IPC (`conn.command`, every other method on `SwayProvider`/`I3Provider`) or a direct library call (`Xlib`, `i3.py`'s own `resolve_pid()`) — sway.py uses `wl-copy` (wl-clipboard, the standard Wayland clipboard CLI — sway is always Wayland, so no backend choice to make); i3.py uses `xclip -selection clipboard` (the standard X11 equivalent — i3 is X11-only). Same "missing binary is not an error" tolerance as `brightness.py`/`cava`/lm-sensors elsewhere in this codebase: `subprocess.run(..., check=True)` wrapped in a bare `try/except (OSError, subprocess.CalledProcessError)`, both collapsing to a plain `False` return — no exception ever escapes to the caller.

One real, documented asymmetry between the two implementations, worth knowing if this is ever touched again: X11's clipboard model requires the OWNING process to stay alive to keep serving the selection on request, so `xclip` daemonizes itself in the background on a successful set — `subprocess.run()` returning in `i3.py`'s implementation only confirms the set succeeded, not that the (intentionally still-running) child has exited. Wayland's `wl-copy` hands the content off to the compositor instead, no daemonization needed — the subprocess really is done once `run()` returns. Neither behavior is a bug; it's the two protocols' own real semantic difference, not something tuicc's wrapper needs to paper over.

**`modules/sysmon.py` gained `handle_diagnostics(ctx, item, cfg)`**, registered into the module's existing `HANDLERS` dict as `"sysmon_diagnostics"` (already merged into `render.py`'s global `ACTION_HANDLERS` via `ACTION_HANDLERS.update(sysmon.HANDLERS)` — no new wiring needed there). Deliberately reuses `item.preview_text` — the SAME `(line, color)` tuples already built for the row's own hover-preview panel — rather than re-deriving or re-fetching raw diagnostics data a second time; joined with `"\n"` into one plain string. Mirrors `control.py`'s own established convention of splitting multi-line output into one `preview_text` entry per physical line (not one entry holding an embedded `"\n"` — see that module's own docstring for why an embedded newline escapes `draw_centered_lines`' positioning) — `handle_diagnostics` is exactly the inverse operation, re-joining those same per-line entries back into one real string for the clipboard, which needs actual newlines, not a UI-positioning workaround. Returns `(False, None)` always — this is a `Toggle`-shaped state action (see `VISION.md` section 1's four-category test), not a `Focus`/`Power` action, so it never dismisses tuicc; a no-op with nothing to copy (`item.preview_text is None` — the "no issues found" case has no preview) is likewise a silent, harmless no-op, not an error.

**Verification, honestly scoped**: full unit coverage for both new layers — `handle_diagnostics()`'s own logic (joins preview lines correctly, no-ops cleanly when there's nothing to copy) in `test_sysmon_module.py`, and each provider's `copy_to_clipboard()` subprocess wiring (correct command, correct `input=`, missing-binary and nonzero-exit both degrade to `False`) in `test_provider_commands.py`, via the same `monkeypatch.setattr(sway_module.subprocess, "run", ...)` pattern `test_control.py`'s own `probe_state` tests already established for this exact class of external-tool boundary. The REAL end-to-end mechanism was also verified live, directly against this session's actual running Wayland session (not through the UI, see below): calling `SwayProvider().copy_to_clipboard("hello from tuicc diagnostics test\nline 2 of the dump")` directly and reading it back with `wl-paste` round-tripped the exact multi-line text correctly, confirming the real `wl-copy` subprocess call — including the multi-line shape `handle_diagnostics()` actually produces — works end-to-end against a live compositor, not just against a mocked `subprocess.run`. **What was NOT separately verified**: the actual keypress → `dispatch_action()` → `handle_diagnostics()` chain through the live running app's own UI — blind `tmux` navigation to the diagnostics row repeatedly missed it (grep patterns guessed at the row's text before confirming, live, that the real summary reads `"N issues"`, plural, no leading "Diagnostics" label) and was abandoned in favor of the more reliable direct-Python verification above once every other layer (handler logic, provider subprocess wiring, real end-to-end clipboard mechanism) was independently confirmed. `dispatch_action()`'s own generic `ACTION_HANDLERS` lookup-and-call is itself long-proven, shared infrastructure — not re-verified per feature — so this gap is judged low-risk, not glossed over.

**Fast follow, same request thread ("haha ještě to musíme nějak dát vědět uživatelům, že Enter = copy to clipboard, a pak ideálně potvrzení že copied"): discoverability + confirmation, closing the gap the first pass's own docstring explicitly flagged as open** ("Provider.copy_to_clipboard()'s own success/failure isn't surfaced anywhere yet... a real, accepted gap").

*Discoverability* — first landed as a trailing hint line appended inside `_diagnostics_preview_text()` (the hover-preview panel), requiring `handle_diagnostics()` to strip it back off before copying via a `_DIAGNOSTICS_HINT_LINE_COUNT` slice. Corrected immediately, live, on direct user feedback ("ne já jsem myslel ať jen přidáš text k tomu 76 issues (Enter = cp clipboard)" — "no, I meant just add text to that '76 issues'"): the hint belongs directly on the row's own summary text in the box itself, visible without selecting the row first, not tucked into a hover panel nobody looks at until after they already know the action exists. Reverted `_diagnostics_preview_text()` back to its original plain form (no trailing lines, no slicing needed in the handler) and instead built the hint at `draw()`'s own diagnostics-row call site: `f"{summary} ({key_label(ctx.config.keybinds['confirm'])}=copy)"`, appended only once `diag is not None` (nothing to copy yet during the pre-poll "checking..." state). Same `key_label()` convention as before — a rebound confirm key still shows correctly — just relocated to where it's actually seen. `wc_truncate()` clips it gracefully on a narrow box like every other row text in this codebase; no special-casing needed for the common "doesn't quite fit" case.

*Confirmation* — reuses `LoopState`'s existing generic toast mechanism (`resize_message`/`resize_message_until`/`resize_message_urgent`, drawn via `render_utils.draw_status_line()`) rather than inventing a second one. That field's own docstring already anticipated this: "A generic transient toast — used by save/cycle-preset as much as by resize" (`loop_state.py`) — `frame_update.py`'s launcher/restore-spawn failure toast was already a second, non-resize consumer before this feature, so a third consumer here doesn't strain the existing (if now visibly stale) field name; a rename was considered but left alone as out of scope for this fast-follow, not because the staleness went unnoticed.

The real design problem this surfaced: `ACTION_HANDLERS`' handler contract (`actions.py`) only ever gives a handler an `ActionContext` — `.provider`/`.status`/`.restore_queue`/`.reselect_region_id`/`.reselect_item_id` — never `main.py`'s own `LoopState`, so `handle_diagnostics()` has no direct way to set a toast. Solved by extending `ActionContext` with two new output fields, `toast_message: str | None = None` / `toast_urgent: bool = False`, following the EXACT existing precedent `reselect_region_id`/`reselect_item_id` already established on the same dataclass: a handler writes to its own `ctx` as a side channel, and `main.py` drains it once, immediately after the dispatch call that may have set it, then resets it back to `None` — a single-use idiom, not a persistent subscription. `main.py` gained `do_apply_toast(loop_state, action_ctx)`, structurally identical to the pre-existing `do_apply_reselect()` right above it, called at all three of `do_apply_reselect()`'s own call sites (the two `dispatch_action()` sites — global shortcut and normal selection — and `handle_pending_confirm()`'s own site, for free, in case a future confirm-gated action ever wants a toast too, not because anything uses it there yet). `handle_diagnostics()` sets `toast_message = "Copied to clipboard"` on a successful `copy_to_clipboard()`, or `"⚠ Copy failed — clipboard tool unavailable?"` with `toast_urgent = True` on failure — the exact `False` return path the first pass's own tests already exercised (missing `wl-copy`/`xclip`, nonzero exit) now has a real, visible, in-app consequence instead of vanishing silently, closing the no-silent-failure gap the original docstring named.

Test updates, final shape: `_diagnostics_preview_text()`'s own tests and `nav_items()`'s diagnostics-row tests are unchanged from before this whole feature (`preview_text` is back to plain content, no hint lines to account for) — `draw()` itself stays untested by design (needs a real curses screen, same accepted gap as every other module). `handle_diagnostics()`'s own tests keep the toast coverage added in this same pass: `_FakeProvider(copy_succeeds=...)` parameterizes success vs failure, asserting the plain "Copied to clipboard" toast on success and the urgent "⚠ Copy failed" toast on failure, `preview_text` back to a plain two-line fixture with no hint lines to strip. 1293 tests passing.

## Module self-sufficiency vs. preview as enhancement {#module-self-sufficiency-vs-preview}

Reached in a long architectural discussion (including a 5-advisor LLM council session), triggered by connectivity.py's WiFi Device/Connection diagnostic tables landing as `preview_tables` content that exists ONLY inside the preview panel, nowhere in connectivity's own box.

**The problem, stated precisely:** `preview.py`'s own module docstring already says "the core never guesses a module's internal layout" — but `NavItem.preview_tables` (the bordered-table mechanism connectivity's Device/Connection tables use) was, at the time this was flagged, used by exactly 1 of the 6 modules that populate any preview field at all. `preview.py` had grown a whole rendering subsystem (table stacking, height math, `draw_table_box` orchestration) for a single consumer — the opposite of the principle its own header states. Separately, and more importantly: VISION.md declares "sidebar + preview + launcher are the identity of tuicc... any proposal that weakens them is rejected on sight" — but nothing in the code actually enforces that. `resize_mode.py`'s `confirm_delete_yes()` does `layout_boxes.remove(state.box)` with zero special-case for `preview`/`sidebar`/`launcher` — any of them is exactly as deletable as any other module box via the ordinary resize-mode delete flow. `main.py` already has to defensively guard `boxes.get("preview")` returning `None` in at least one place. So a module leaning on preview for functionally-required information was leaning on something the project claims is permanent but the code treats as fully optional.

**Decision, Rafi's own wording:** Modules are fully operable from their own box alone. All functionality, and every piece of information actually needed to make a decision or take an action, must be visible and controllable purely from the module's own box, regardless of whether preview exists in the current layout at all. Preview may add a richer/prettier secondary view when it's present, but it must never be the ONLY place a functionally-necessary piece of information exists. Explicitly scoped as "fully OPERATE", not "fully SEE in identical richness" — connectivity's connect/disconnect/forget/scan/hidden/power actions already don't depend on preview at all today; only the deeper live diagnostic readout (frequency, live-negotiated security, RSSI, bitrate, IP) is preview-exclusive, and that's the category this decision is actually about.

**Two follow-on mechanisms this motivates (not yet built, see the matching Plan Mode plan):**
1. A `preview_data: object` field + a `PREVIEW_RENDERERS: dict[module_name, Callable]` registry (mirroring the existing `ACTION_HANDLERS`/`MODULES`/`NAV_PROVIDERS` registry idiom already used elsewhere in this codebase) replaces the growing set of typed `preview_*` fields — `preview.py` stops needing to know the shape of any module's content; it just hands the module's own registered renderer the inner content rect. A raw `Callable` stored directly on `NavItem` was considered and rejected: it would be the first instance of behavior embedded in otherwise-pure data anywhere in this codebase, and (per the council's First Principles advisor) means render-time behavior would travel through a construction-time channel, before the render context even exists — a layering violation, not just a style preference.
2. A module can check `any(b.name == "preview" for b in ctx.config.layout.boxes)` (cheap, no new plumbing — `ctx.config.layout.boxes` is already a `list[ModuleBox]` available everywhere) and branch how much it draws in its OWN box accordingly — not a second copy of the module, one function with one more condition, the same way `connected`/`known`/`powered` already branch what connectivity shows today.

**Explicitly deferred, not decided against:** a "preview idle state" (what preview shows when nothing selected has any preview content AND the focused workspace itself has zero windows — genuinely blank today) — raised live as a real gap, with `rwb.py`'s own visualizer floated as a candidate future filler ("RWB krásná grafika by tam mohla přetéct"), but parked as a separate, later design question, not bundled into this decision or its implementation plan.

See `CLAUDE/GUIDE.md`'s "Adding a module" paragraph for the existing `MODULES`/`NAV_PROVIDERS`/`ACTION_HANDLERS` registry precedent this extends.

## Bluetooth adapter table: Powered + Pairable, both with real toggle actions {#bluetooth-adapter-table}

Follow-on to the preview_data/PREVIEW_RENDERERS registry above, and the very first real second consumer of it: connectivity.py's Bluetooth section had no adapter-level info at all, unlike WiFi's own "Device" table.

**Two candidate additions explored and rejected first**, applying VISION.md's own three-part test ("tells you something, calls for action, or is flex") live with Rafi: a friendly-name translation of a device's supported service UUIDs, and the live audio codec (SBC/AAC/aptX) for a connected BT audio device — the latter genuinely real and empirically confirmed (`pw-dump` against a real connected device showed `api.bluez5.codec: 'sbc'`), sourced from the `audio/` package (PipeWire), not bluez.py at all, since BlueZ itself has no codec concept. Both rejected: informational without a lever to pull, exactly the "filler" category Rafi named directly. The codec finding is left here as a documented, real, but explicitly out-of-scope idea for a future pass — it would need `AudioSink` extended with new fields and a MAC-address correlation between connectivity.py and the audio Domain, genuine cross-module work VISION.md's R5 already anticipated ("connect BT headphones, switch output") but didn't build.

**Read `bluetuith`'s actual source** (`ui/app/views/adapterview.go`/`deviceview.go`, from its own `bluetooth-classic` Go library's `AdapterData` struct) as the deciding reference, the same "read a comparable tool as protocol documentation" approach already used for impala (see VISION.md's R4 section). Its adapter view shows exactly Name/Powered/Discoverable/Pairable/Discovering, each with a real toggle action behind it — confirming the resolution: don't cut the info for being filler, add the lever that makes it not filler.

**Decided scope, Rafi's own call**: Powered + Pairable get real toggle keys (`bt_power_toggle`/`bt_pairable_toggle`, new — not reusing/renaming `wifi_power_toggle`, keeping the existing shipped key's meaning stable). Discovering reuses the existing shared `scan` key (already wired to `start_discovery()`) — no new key needed, just render it in the new table. Discoverable (bluetuith has it) is left out — no action was asked for it, so per the same "filler" reasoning it's inert info until one exists.

**Live-confirmed** (`busctl call org.bluez / … GetManagedObjects` against a real adapter, `/org/bluez/hci0`) that `org.bluez.Adapter1` exposes exactly the needed properties: `Name` (a broadcast name, e.g. "node1" — the machine's hostname, NOT an interface id), `Address`, `Powered`, `Discoverable`, `Pairable`, `Discovering`. `BluetoothAdapterInfo.name` is deliberately derived from the adapter's own D-Bus object path (`"hci0"`, the last path segment) rather than the `Name` property — mirrors WiFi's own `AdapterInfo.name` convention (an interface identifier, not iwd's separate friendly `Adapter.Name`) and matches what Rafi expected going in ("name: hci1 nebo co").

**`draw_preview()` needed zero changes** to support this — confirms the whole point of the preview registry refactor above: it was already generic (`[(title, rows)]` tuples, no module-specific logic), so a second, differently-shaped table source (Bluetooth's own `_bt_preview_tables()`) costs nothing in `preview.py` or the registry itself.

**`_power_progress_line()` and `_browsing_hint_footer()`'s own `powered=False` narrowing were generalized** (not duplicated) to take a `domain_name` param / cover both sections respectively — both functions' bodies were already parametric enough that this was a signature widening, not a rewrite. One real, live-confirmed asymmetry between the two sections: WiFi has no Pairable equivalent at all, so `_browsing_hint_footer`'s "radio on" hint line differs in content (Bluetooth's own line adds `[A] Pairable`) even though both sections now share the identical `[<key>] Power   [Esc] Back` shape for the "radio off" case.

Unlike WiFi (two backends, iwd + NetworkManager — everything doubled), Bluetooth has exactly one backend (`bluez.py`), so this landed with no duplication burden.

## Connectivity header Scan/Browse: level-1.5 expand, not a keybind, not simultaneous {#connectivity-header-expand}

Same session as the Bluetooth adapter table above, later on: Rafi's own report — the header's own preview (`_wifi_scan_preview_text`/`_bt_discover_preview_text`) shows the full "Available networks/devices" overview, genuinely useful for finding one entry among many, but there was no way to trigger a scan from level 1 (before browsing) without first committing to Enter (which replaces that same overview with the cramped windowed row list). This used to just work (Enter on the header directly triggered a scan, pre-level-2-browsing) — level-2 browsing repurposed Enter to mean "browse" instead, losing the level-1 scan trigger as a side effect nobody had actually decided to give up.

**A plain keybind (`s`, reusing browsing's own `scan` key) was tried and reverted the same session.** It works fine INSIDE browsing (a genuine mode_stack claim there — the whole reason that tier exists at all, per this module's own "level-2 browsing" docstring, is to make a dedicated key safe to bind without colliding with anything). At level 1 it's a different story: nothing claims input there, so VISION.md's "launcher owns unclaimed typing" identity commitment means ANY plain printable key belongs to the launcher's own ambient "start typing anywhere" claim — intercepting `s` specifically while the header is selected silently broke that promise for exactly that one key. Found live by Rafi, not theorized.

**Several non-printable-key alternatives were considered and rejected in turn**, each for a distinct, concrete reason, not just "felt wrong":
- **Ctrl+\<letter\>** — this codebase's existing convention reserves the whole namespace for `power_menu.action.shortcut`-style GLOBAL system actions (Lock/Logout/Reboot/Shutdown), and `Ctrl+S` specifically carries a real risk of freezing the WHOLE TERMINAL via XON/XOFF software flow control — `curses.wrapper()` only calls `cbreak()`/`noecho()`, neither of which touches the separate `IXON` termios flag flow control lives under, so nothing in this codebase's own curses setup guarantees `Ctrl+S` even reaches `getch()` rather than pausing the tty. Confirmed as a real mechanism, not assumed away.
- **F-keys** — already fully claimed (F1–F6 are help/resize/save_layout/cycle_preset/new_preset/spawn_box), and reaching for F7+ is "out of the way" for something as routine as refreshing a list — Rafi's own words.
- **Backspace/Insert/Home/End/PageUp/PageDown** — genuinely free, non-printable, no namespace conflict, but none of them carry any real "scan" semantics, and none felt right live either.
- **Enter-on-header-also-scans** (bundling a scan into the existing Enter-browse action) — rejected because it still LEAVES level 1 (commits to browsing) on the same keypress, which defeats the entire point: staying at level 1, watching the header's own full overview update live while a scan runs.
- **Auto-scan the instant the header is selected** — rejected live as "too forceful" (Rafi's own words): scanning is a real, not-free radio action; triggering it as a passive side effect of merely Tab-ing past a row (not a deliberate keypress) doesn't fit "the user has absolute authority over the machine" (VISION.md §1) as cleanly as an explicit action does.

**Two separate NavItems sharing the header's own row** ("Scan" and "Browse", Tab+Enter reachable, no new key of any kind) was the design that actually stuck — the same "second distinct action on the same list" pattern `media.py`'s own transport-glyph cluster and `sysmon`'s CLOSE/KILL already established elsewhere in this codebase. First attempt (both sections' Scan+Browse simultaneously reachable, positioned via a new `_header_action_slots()` geometry helper) shipped, then broke on the very next live test: Rafi reported the actual Tab order came out `BT Scan, WiFi Scan, WiFi Browse, BT Browse` — visibly wrong, and investigating why surfaced a real, deeper problem, not just a sizing bug.

**The deeper problem**: `navigation.tab_order()` is a single GLOBAL sort over every item from every module combined (`(x, y)` under the default `columns_first`, `(y, x)` under `rows_first`) — `next_item_in_module()`/`prev_item_in_module()` just filter that one pre-sorted list down to one module's own items, preserving whatever relative order the global sort gave them. Since Scan always sits left of Browse (by design, both right-aligned to the row's own edge), under `columns_first` (x primary) EVERY section's own Scan items sort together before ANY section's Browse items — `WiFi Scan, BT Scan, WiFi Browse, BT Browse` is the correct, deterministic, but NOT per-row-grouped result even once the immediate sizing bug (Bluetooth's `"Discovering…"` being 3 characters longer than WiFi's `"Scanning…"`, reserving a wider slot and shifting BT's own `scan_x` further left than WiFi's — the actual, distinct cause of the specific wrong order Rafi first saw) is fixed. No purely geometric (x, y) trick can produce genuinely row-grouped ordering across TWO simultaneously-reachable rows under `columns_first`'s strict x-primary lexicographic sort — confirmed by working through the sort key algebra directly with Rafi, not asserted.

**A real general fix — per-box `tab_order` override (config.toml's `[[layout.box]]` gaining an optional `tab_order` field, `navigation.tab_order()` gaining a `module_modes: dict` param, grouping items by module and sorting each group by ITS OWN resolved mode before concatenating, rather than ever comparing `(x, y)` tuples across two differently-scoped modes directly)** was designed in full with Rafi live, then explicitly deferred — "moc velký refaktor pro dnešek" (too big a refactor for today), not rejected on merits. `navigation.py` is shared by every module in the app; changing its core sort semantics deserves its own session, not a same-session bolt-on to a header-row bugfix. Revisit this design here if/when a similar per-module ordering need comes up again elsewhere — the algebra and the concrete plan (per-box config field, module-grouped sort, `frame_update.py` building the `module_modes` dict from `cfg.layout.boxes`, `main.py`'s own `module_position_key`/`module_names` cross-module ordering staying untouched since the override only ever affects ordering WITHIN one module) are already worked out, just not implemented.

**What actually shipped**: a level-1.5 expand, structurally identical to `sessions.py`'s own `_expanded_slot`/`media.py`'s `_expanded_bus_name` two-level-expand mechanism (a plain module-level global, NOT a `mode_stack` claim — normal Tab/Escape/module-switching keeps working unclaimed) — `connectivity._expanded_header` (`"wifi"`/`"bluetooth"`/`None`). Enter on a COLLAPSED header (`wifi_expand`/`bluetooth_expand` target_kinds, new) sets `_expanded_header` and reselects straight onto Scan (unconditionally — see the "always offered" revision below). Enter on Scan (`wifi_scan`/`bluetooth_discover`, unchanged from the first attempt) fires the scan/discovery and stays exactly there — level 1.5, not level 1 or level 2. Enter on Browse (`wifi_browse`/`bluetooth_browse`, same handlers as before, now ALSO clearing `_expanded_header` back to `None` since real level-2 browsing supersedes it) claims the real `mode_stack` tier exactly as before this whole feature ever started. This sidesteps the deeper `tab_order()` problem entirely rather than solving it: with only ONE section's own Scan+Browse pair ever present in `nav_items()`'s returned list at a time (the other section stays a single collapsed row, exactly like every OTHER slot in `sessions.py`'s own list stays collapsed while one is expanded), there is no second row's items to interleave with in the first place — correct regardless of `cfg.tab_order`'s mode, with zero changes to `navigation.py` itself.

`main.py`'s `handle_connectivity_browsing()` dispatch function (and its pre-existing `wifi_power_toggle` branch) has zero unit test coverage anywhere in this repo — a deliberate, pre-existing scope boundary (matches "main()'s loop has no direct coverage" elsewhere in this document), not something this change invented or was expected to fix; the two new Bluetooth branches follow the same convention rather than introducing new main.py test infrastructure unprompted.

**Follow-up, same session: Tab escaping the module while expanded.** First live test of the shipped design above surfaced a real gap Rafi caught immediately: Tab past Browse silently rolled into whatever module sits next ("utíká mi to pryč z modulu" — it escapes the module), instead of staying locked to just Scan/Browse until Escape or Enter-on-Browse. Net diff: one line in `any_two_level_module_expanded()`, nothing in `navigation.py`, no new `MODE_HANDLERS` entry, no `handle_wifi_header`/`handle_bt_header`/`handle_wifi_scan`/`handle_bt_scan` retirement after all — the mode_stack detour would have meant reinventing (worse, less-tested) `next_browsing_selection`-style hand-rolled dispatch for a problem this codebase already had a clean, shared answer for. Worth remembering next time a "second distinct action on a row" feature seems to need locked Tab behavior: check `any_two_level_module_expanded()` before reaching for `mode_stack`.

## Session restore's argv[0] resolution {#restore-argv0-resolution}

Found live testing session restore on Rafi's own real session (`~/.config/tuicc/sessions/1.toml`, saved on his NixOS/sway machine): Spotify failed to relaunch with `error while loading shared libraries: libayatana-appindicator3.so.1`, while the exact same app launches fine every time through the launcher module.

Root cause, confirmed by comparing the two spawn paths directly: `launcher.py` spawns a bare command name from `Exec=` (e.g. `"spotify"`), which `spawn_detached()` hands to `subprocess.Popen(["spotify"], ...)` unresolved — Python does its own `$PATH` lookup for an argv0 with no `/` in it, landing on `/nix/store/.../spotify.../bin/spotify`, a `makeWrapper`-generated shell script that sets `LD_LIBRARY_PATH` (among other things) before `exec`ing into the real binary. `session.py`'s `capture_window()` instead reads the LIVE process's real `/proc/<pid>/cmdline` — by the time tuicc gets to read it, that wrapper script has already `exec`'d into the unwrapped binary (`.../share/spotify/.spotify-wrapped`), so the wrapper itself never appears in the captured argv at all. Restoring that captured argv[0] literally therefore always skips the wrapper's own env setup — confirmed this isn't Spotify-specific by checking Discord's and Obsidian's own nix-generated wrapper scripts, both structured the same way (`exec "<real-binary>" <args...>`).

(A separate, unrelated corruption was found in the same saved session at the same time: Discord's and Obsidian's captured `cmdline` arrays each held ONE array element with an embedded space — `".../electron /path/app.asar"` — instead of two, most likely from the Electron process rewriting its own `process.title` in place, which overwrites the NUL separator between argv slots on Linux when there's spare contiguous space to grow into. Not fixed here — `spawn_detached()` never re-splits a list's own elements today, deliberately, since it can't distinguish "this got corrupted" from "this argument genuinely contains a space" — flagged for Rafi, not treated as the same bug as the wrapper-skipping one above.)

**Fix**: `session.resolve_restore_argv(cmdline, app_id, desktop_apps)` — a pure function, swaps ONLY `cmdline[0]` for the matching `.desktop` entry's own `Exec=` command (matched by `app_id_hint.lower() == app_id.lower()`, since a captured `window.app_id` and a `StartupWMClass=` commonly differ only in case — confirmed live against Rafi's own real `.desktop` files: `"Spotify"` vs `"spotify"`, `"Discord"` vs `"discord"`), keeping every argument after it exactly as captured — those can carry real restore-worthy state (an open file/vault/project path) a bare `Exec=` line could never reproduce, which is the whole reason `session.py` captures real argv in the first place rather than just replaying `Exec=` (considered and rejected as the general design — see the question this answers: "couldn't sessions just be an automated launcher script?").

Only swaps when the resolved command is actually runnable right now (`shutil.which()`) — a defensive guard against a `.desktop` entry whose `Exec=` only makes sense inside its own sandbox/container and doesn't exist on the bare host. Wired at the one real spawn site, `pending_moves.promote_restore_queue()`, called with `desktop_apps=launcher_mode.get_apps()` from `frame_update.py` (already imports `launcher_mode` for an unrelated reason) — `desktop_apps` defaults to `()` for every other/older caller, same "no match found → unchanged" fallback as an app with no `.desktop` entry at all.

**Correction, found running this against Rafi's own real session right after writing the paragraph above**: the guard's ONLYOFFICE example was wrong. There ARE two different `onlyoffice-desktopeditors.desktop` files on this machine — an FHS-sandbox-internal one (`Exec=/usr/bin/onlyoffice-desktopeditors`, genuinely unresolvable on the bare host, confirmed via `shutil.which()` returning `None` for it) and a SEPARATE one actually linked into Rafi's profile (`Exec=/nix/store/.../onlyoffice-desktopeditors-9.1.0/bin/onlyoffice-desktopeditors`, an absolute nix-store path to a real, executable `buildFHSEnv`-generated bubblewrap launcher script) — `launcher.py`'s own `scan_desktop_apps()` picks up the SECOND one, which DOES resolve. So `resolve_restore_argv()` now swaps ONLYOFFICE's argv[0] too, same as every other app in this session — not the "stays untouched" example originally claimed. This is very likely a GOOD outcome, not a regression: it means session restore now launches ONLYOFFICE through the exact same sandboxed entry point the launcher module already uses for a fresh launch, rather than the raw unsandboxed `DesktopEditors` binary session.py happened to capture — but it's an unverified behavior change for this specific app (today's raw-binary restore does already work, confirmed live), flagged here rather than silently assumed identical. Worth a live restore-and-watch on ONLYOFFICE specifically next time Rafi tests this.

## winrestore: capturing app_id instead of cmdline/env {#winrestore-app-id-capture}

Same live-testing session as the `argv[0]` fix above, continued: even with that fix landed, TWO more real restore failures turned up on Rafi's own real saved session (`~/.config/tuicc/sessions/1.toml`) — Discord's and Obsidian's captured `cmdline` arrays each held ONE array element with an embedded space (`".../electron /path/app.asar"`) instead of two separate argv entries, most likely from the Electron process rewriting its own `process.title` in place (which overwrites the NUL byte separating argv slots on Linux, when there's spare contiguous memory to grow into) — genuinely corrupted data by the time `/proc/<pid>/cmdline` could be read, not a tuicc parsing bug. Comparing against `tileroot` (a dedicated C++ sway/i3/Hyprland session-restore tool, github.com/Hinikaa/tileroot) confirmed this whole "capture exact argv, replay it verbatim" approach is fragile in a way that isn't specific to tuicc's own implementation — `tileroot`'s own `matcher.cpp` has the identical `argv[0]`-bypasses-wrapper-scripts bug, unaddressed, just not yet reported (its userbase skews Arch/AUR, where wrapper-script-then-exec packaging like nix's is much rarer).

**Rafi's own call, live**: give up the "exactly what was open" promise entirely — a saved layout doesn't need to reopen the same file/vault/tab, just the same app in the same place, tiled/stacked/floating correctly. This is a strictly smaller, strictly more reliable feature, not a compromise held in tension with reliability — the two goals were pulling in the same direction the whole time. Renamed `session.py`/`modules/sessions.py` to `winrestore.py`/`modules/winrestore.py` to match (see below) — "session" oversold a promise the feature no longer makes, and a rename also sidesteps a real collision: `layout`/`layout.py`/`layout_engine.py`/`cfg.layout` already means tuicc's own sidebar/preview box grid, a name a WM-window-arrangement module could never share without constant confusion.

**What changed, concretely:**
- `capture_window()`/`capture_session()` (winrestore.py) now record only `{app_id, target_region, floating, x/y/w/h if floating}` — no `/proc/<pid>/cmdline` or `/proc/<pid>/environ` read at all, so there's nothing left to corrupt or to skip a wrapper script on. `capture_window()` also stopped needing a `provider` param (no more pid resolution) and can no longer fail (every open window is capturable now — no more silent per-window skip on an unreadable `/proc`).
- Relaunch goes through `resolve_launch_argv(app_id, desktop_apps)` — the SAME app_id-hint-matched `.desktop` `Exec=` lookup `resolve_restore_argv()` used as its argv[0]-swap fallback above, now the PRIMARY and ONLY mechanism, not a swap-in-place patch over a captured cmdline that no longer exists. `resolve_restore_argv()` itself, along with `read_cmdline()`/`read_environ()`/`_parse_cmdline()`/`_parse_environ()`, is deleted outright — nothing left to call it for.
- **Matching got simpler too, reusing existing code rather than needing a new matcher**: the original plan (discussed with Rafi before implementation) was a from-scratch `tileroot`-style FIFO+claimed-set matcher, to structurally avoid `pending_moves.py`'s pid-tier tracking — the same tracking that made the (separately already-fixed) fork/exec pid-mismatch bug possible in the first place (`CLAUDE/NOTES/known-limitations.md#fork-exec-pid-mismatch`). Turned out unnecessary: `pending_moves.resolve_pending_move()` already has a pure app_id-tier (case-insensitive, exactly the matching rule wanted) that fires whenever an entry's `pid` is `None` — `queue_restore_entry()` already took a `pid` param, so `promote_restore_queue()` now simply passes `None` for it on purpose (the REAL pid `spawn_detached()` returned is still used for `no_focus_next_window()`, just never threaded into the matching entry) instead of the genuinely-spawned pid. Reuses `process()`'s entire existing, already-tested plumbing for free — focus reclaim, `MOVE_TIMEOUT_SECONDS`, `wm_config` target-region resolution, fullscreen reassert — rather than reimplementing any of it. `queue_launcher_spawn()` (plain typed launches) is completely unaffected — still passes a real pid, still gets pid-tier matching, since an ordinary launcher spawn has no reason to give that up.
- Whole `session.py`/`modules/sessions.py` family renamed to `winrestore.py`/`modules/winrestore.py` — `SESSIONS_DIR` → `WINRESTORE_DIR` (`~/.config/tuicc/sessions/` → `~/.config/tuicc/winrestore/`, NOT migrated — old saved files at the old path are simply invisible now, acceptable since this landed pre-`v0.1.0`, no tag ever shipped with the old format), `[sessions]` config section → `[winrestore]`, `Config.session_names`/`SESSION_SLOT_COUNT`/`set_session_name()` → `winrestore_names`/`WINRESTORE_SLOT_COUNT`/`set_winrestore_name()`, `RenderContext.session_preview` → `winrestore_preview`, `"sessions_naming"` mode_stack tier → `"winrestore_naming"`, `target_kind`s `"session_row"`/`"session_action"` → `"winrestore_row"`/`"winrestore_action"`, module registry key `"sessions"` → `"winrestore"` (`render.py`'s `MODULES`/`NAV_PROVIDERS`/`AUTO_FH_PROVIDERS`/`ACTION_HANDLERS`, preset TOML `[[box]] name = "winrestore"`). The box's own on-screen title stays "Sessions" — a UI label, independent of the underlying module/file name, not part of this rename.

**Explicitly deferred, not part of this pass**: `append_layout` (sway/i3's native placeholder/swallow mechanism for reconstructing the real split/stacked/tabbed tree, not just flat per-region placement) was investigated in the same session (reading `tileroot`'s own `ipc_i3.cpp`/`matcher.cpp` against the real i3 docs at build.i3wm.org/docs/layout-saving.html) and confirmed real and usable — `workspace "<target>"` immediately followed by `append_layout <path-to-json>`, `swallows` criteria matched on `app_id`/`class`/`instance`/`title`/`window_role`, all case-sensitive PCRE. Deferred because it needs its own new capture-side mechanism first: `WMState`/`Region`/`Window` (`model.py`) doesn't retain the real tree at all — `Region.windows` is a flat list, `preview.py` infers visual layout from each window's own `rect` at render time — so tree capture needs a NEW, sway/i3-specific raw-IPC-tree walk (mirroring `attach_cmdlines`/`node_to_layout` in `tileroot`'s `ipc_i3.cpp`), exposed as a second new optional `Provider` method on the capture side, alongside a restore-side one. Worth doing better than `tileroot` itself when this does land: its own `node_to_layout` collapses any non-`splitv` container to `splith`, silently losing `stacked`/`tabbed` groups — tuicc already tracks that distinction via `Window.tab_group_layout` (see `model.py`'s own docstring, GitHub issue #8) and should carry it through here too.

## append_layout tiled/stacked/tabbed restore {#append-layout-tiled-restore}

The deferred work above, actually built the same day, once phases 0-2 were live-confirmed working on Rafi's own machine ("tohle při rychlém testu funguje... musíme teď dotlačit ty tabbed stacked floating layouty skrze appendlayout"). Full design grounded in a real facts-gathering pass over `providers/base.py`/`sway.py`/`i3.py`/`model.py` (read in full, not skimmed) plus **live empirical testing against Rafi's own real sway session** for the one genuinely uncertain piece — not assumed from docs, confirmed by actually doing it.

**New shared pure module, `tiled_tree.py`** (peer to `tab_groups.py` — same "one shared function both providers import" shape, since sway/i3 share the identical i3ipc `Con` wire shape and there's nothing provider-specific about walking it): `capture_tiled_tree(con)` walks a workspace `Con`'s own `.nodes` (never `.floating_nodes` — floating stays on the flat/per-window path entirely) into a plain nested dict, carrying `con.layout` through verbatim (`splith`/`splitv`/`stacked`/`tabbed`) rather than collapsing stacked/tabbed to splith the way `tileroot`'s own `node_to_layout` does — `Window.tab_group_layout` already proves tuicc tracks this distinction elsewhere (GitHub issue #8), no reason to lose it here. `layout_to_append_json(tree, swallow_key)` converts that saved tree into the real `append_layout` JSON, `swallow_key` passed in by the caller (`"app_id"` for sway, `"class"` for i3 — mirrors `mark_self()`'s own existing `app_id=`/`class=` asymmetry) rather than hardcoded, so one function serves both providers. `flatten_leaves(tree)` turns a tree back into a plain app_id list for the actual spawn step (placeholders alone don't launch anything).

**Three new optional `Provider` methods** (same no-op-default template every one of the existing 10 already follows): `get_tiled_tree(region_id)` (capture, default `None`), `prepare_tiled_tree(tree, region_id)` (restore — `workspace number <region_id>` then a temp-file `append_layout <path>`, returns whether BOTH commands reported success; default `False`), `set_self_sticky(sticky)` (see below; default no-op). Implemented identically in `sway.py`/`i3.py`, differing only in the swallow key and (already-existing) mark criteria keyword.

**The one real open question, resolved by testing it live rather than guessing**: `append_layout` has no "target workspace" parameter of its own — it always inserts into whatever's currently focused, confirmed both by the i3 docs and by `tileroot`'s own implementation needing the identical `workspace` focus step first. Restoring across several regions therefore means several real WM workspace switches in a row, before anything spawns — naively, a visible flicker through each target workspace on tuicc's own fullscreen screen. Rafi's own question in response, live: "co když se tuicc bude hýbat jako překrývající appka nad workspaces?" (what if tuicc moved as an overlay above the workspaces?). Tested directly against a real floating window on Rafi's own sway session (spawned a throwaway `kitty --app-id=tuicc_sticky_test`, `[con_id=X] floating enable, sticky enable, fullscreen enable`): `sticky: true` and `fullscreen_mode: 1` hold simultaneously with no conflict (the `sticky` command's own man-page wording is ambiguous on this combo, but real behavior isn't), and switching real workspace focus afterward re-parents the sticky window into the newly-focused workspace's own subtree every time, `visible: true`, full-output rect. So: `set_self_sticky(True)` right before the batch of `prepare_tiled_tree()` calls, `set_self_sticky(False)` right after, both only when the batch actually has at least one tree to place — the whole workspace-switching dance happens completely invisibly, tuicc's own fullscreen surface never stops covering the screen. Scoped and temporary — R1's scratchpad/fullscreen lifecycle model is otherwise completely untouched, this is not a permanent behavior change.

**`winrestore.py` schema changed again, from flat-per-window to per-region** (a second break from the still-fresh app_id-only shape landed hours earlier the same session — acceptable, still pre-`v0.1.0`, no tag): `capture_region()` tries `provider.get_tiled_tree(region.id)` first (only when the region actually has tiled windows — no reason to make the call otherwise), falls back to a flat `"tiled_flat"` list (today's app_id-only shape, unstructured) when that comes back `None` — a WM without tree support, or just an empty tiled area on this one region specifically. Floating windows are always flat, under their own `"floating"` key, regardless — `append_layout` never touches them. `save_session`'s own TOML top-level key changed `"window"` → `"region"` to match.

**Restore ordering — the part that needed real care, not just wiring**: the `append_layout` IPC calls (real workspace switches, no way to undo them cleanly) must never fire before a "load? (overwrites your layout)" confirm dialog's own y/n answer, but `actions.handle_pending_confirm()` (the SHARED confirm-resolution code, also used by `power_menu.py`/`quick_actions.py`, with zero winrestore-specific knowledge) can't be taught to defer an IPC side effect conditionally. Solved with a new `ActionContext.pending_layout_regions` field, separate from `restore_queue`: `modules/winrestore.py`'s "load" action (both the no-confirm-needed path and, via the unchanged generic `"restore_entries"` dict shape, the confirm_yes path) only ever appends RAW per-region entries here — never touches a provider. `frame_update.py` absorbs this once per frame into the sequential driver described in the "Phase 3 correction" below — by construction, that driver's own first real IPC call only ever happens on the frame AFTER a load decision has already been made, whichever path made it.

**Matching**: a flattened tiled leaf gets tagged `placed_by_wm=<whether prepare_tiled_tree() succeeded for its whole region>` — `append_layout` is all-or-nothing per sway/i3's own semantics, so a `False` here applies to every leaf in that region, not just the ones that look likely to fail. `pending_moves.queue_restore_entry()` threads this straight onto the queued entry; `process()`'s match-success branch gained exactly one new conditional (skip `move_window_to_region()`/`set_floating_geometry()` when `placed_by_wm` is set — the WM's own swallow already placed it) and nothing else changes — focus reclaim, `SETTLE_SECONDS` linger, quick-exit detection all still run identically either way. Same "one flag, reuse the entire existing tested pipeline" shape the `pid=None` trick from the app_id-capture redesign already used a few hours earlier — no second matcher needed here either.

### Phase 3 correction: strictly sequential, one region at a time {#append-layout-sequential-correction}

**What the first version above actually did on Rafi's first real test, next session**: no tree structure came back at all, and every duplicated app_id in his real saved layout (`kitty` in 3 places, `firefox` in 2) piled onto a single workspace instead of their own targets — "žádný stacked tabbed floating se neprojevil a všechny kitties skončily na hromadě." Diagnosed live, not guessed: `swaymsg -t get_tree`, dumping the real post-restore tree per workspace (this repo's own established diagnostic technique — `GUIDE.md`'s checklist intro). Confirmed a clean, consistent pattern: every genuinely UNIQUE app_id in the batch (ONLYOFFICE, Obsidian) landed on its correct region; every app_id that repeated ANYWHERE in the batch got swallowed into whichever region's placeholder tree was built EARLIEST (region 1's own 2-kitty tiled split absorbed all 4 real kitty spawns in the batch, including the one meant for region 3's tabbed group and the one meant to float; region 2's firefox placeholder absorbed both real firefox spawns).

**Root cause**: `append_layout`'s `swallows` matching has no concept of "which of tuicc's own spawns this window came from" — the WM grabs the first unsatisfied placeholder ANYWHERE in the whole tree matching the criteria, the instant a window maps, regardless of which region "should" get it. Building every region's placeholders up front, THEN spawning everything through the existing staggered queue (the design above), leaves multiple placeholders with identical criteria open on different regions simultaneously — nothing prevents them racing for the same real window. Not a rare edge case: the same app appearing more than once in a restore (multiple terminals, multiple browser windows) is the ordinary case, not a corner case — confirmed by it firing on the very first real layout tested.

**Fix: make the whole restore strictly sequential, one region at a time — not just the `prepare_tiled_tree()` calls, every spawn.** Only ONE region's own windows are ever "in flight" (spawned, not yet matched) at once, so there is never a second open placeholder anywhere in the tree for a WM-side swallow to steal a window into. Within one region, its own tiled leaves go first, as their own sub-phase, fully waited out, before that region's own `tiled_flat`/floating entries spawn — a same-region floating window sharing an app_id with that region's own still-open tiled placeholders has the identical mis-swallow risk otherwise (a floating-intended window could get tiled-swallowed instead, landing in the right region but the wrong shape).

`winrestore.prepare_restore_entries()` (the single-shot batch function above) is gone, replaced by:
- **`TiledRestoreState`** — plain per-loop state (`ResizeState`/`LauncherState`'s own shape): `queued_regions` (raw region entries not yet started), `active_region_id`/`active_phase` (`"tiled"`|`"flat"`|`None`), `pending_flat` (the active region's own tiled_flat+floating batch, held back until its tiled phase clears), `sticky_on`.
- **`advance_tiled_restore(state, moves, provider, restore_queue, now)`** — called every frame from `frame_update.py` (a cheap no-op when nothing's queued/active), same "drive a small queue incrementally, one step per frame" idiom `pending_moves.py` itself already uses. Each call does at most one thing: notices the active region/phase has cleared and either releases `pending_flat` (tiled phase done) or finishes the region outright (flat phase, or a tree-less region's only phase, done); or, with nothing active, pops the next queued region and starts it; or, once everything's drained, turns `set_self_sticky(False)` back off if it was ever turned on.
- **"In flight" check** — deliberately NOT a new matching mechanism, just a read over state `pending_moves.py` already maintains: an entry counts as in-flight while still sitting unpopped in `restore_queue`, OR present in `moves.entries` with no `last_matched_at` yet. `process()`'s own existing match-then-linger-then-`MOVE_TIMEOUT_SECONDS`-give-up lifecycle already guarantees this resolves on its own — no separate timeout needed for the sequential driver itself. Filtered to `entry.get("target_region") == active_region_id` and `"placed_by_wm" in entry` — that key is a marker only `queue_restore_entry()` (winrestore's own path) ever sets, never `queue_launcher_spawn()` (a plain typed launch), so an unrelated launcher spawn happening to target the same workspace mid-restore can't be mistaken for part of the batch. Deliberately does NOT wait out `SETTLE_SECONDS`'s post-match linger tail — that tail exists for fork/exec-descendant detection (`#fork-exec-pid-mismatch`), which structurally can't apply to a `pid=None` winrestore entry in the first place; waiting for it here would tax every single region with an unnecessary ~6s minimum for nothing.

`main.py` gained one more per-loop local, `tiled_restore = winrestore.TiledRestoreState()`, threaded through `update_frame()` the same way `moves = pending_moves.PendingMovesQueue()` already is. `frame_update.py`'s own drain block now just absorbs `action_ctx.pending_layout_regions` into `tiled_restore.queued_regions` and calls `advance_tiled_restore()` once — `ActionContext.pending_layout_regions`'s own contract (still deferred past the confirm dialog) is completely unchanged, only what consumes it downstream is.

**Accepted cost**: a multi-region restore is no longer instant/parallel-staggered — it's now genuinely sequential, each region waiting for its own windows to actually map before the next one's placeholders even get built. Slower in wall-clock terms for a big restore, but the batch-everything-up-front version was never actually correct for the common case (any repeated app_id) — a fast, wrong restore isn't a real tradeoff against a slower, right one.

### A second live-found bug, same fix session: `prepare_tiled_tree()` never resolved custom-named workspaces {#append-layout-workspace-resolution}

Reported immediately after the sequential fix above, on the very next real test: "když jsou custom named WS, tak to posílá okna na plain 2 ws a ne na 2:II" (with custom-named workspaces, it sends windows to plain "2", not "2:II"). Root cause: `advance_tiled_restore()` was calling `provider.prepare_tiled_tree(tree, target_region)` with `target_region` straight from the saved entry — always the BARE workspace number, by the same long-standing convention every winrestore/launcher entry uses (see `pending_moves.py`'s own docstrings). `pending_moves.process()` already resolves this bare number against `wm_config.workspace_names` (`resolve_workspace_target()`, `wm_config_parser.py`) immediately before every `move_window_to_region()` call — this exact resolution was simply never wired into the NEW `prepare_tiled_tree()` call path at all, flagged as an explicit open risk in the original Phase 3 plan ("get this right... not re-deriving it in the provider") and then genuinely missed during implementation.

Fixed by threading `workspace_names` (`wm_config.workspace_names`, from `frame_update.py`'s own already-in-scope `app.wm_config`) into `advance_tiled_restore()` as a new optional param, and resolving `target_region` through `resolve_workspace_target()` right before (and ONLY for) the `prepare_tiled_tree()` call — the entries themselves (`tiled_entries`/`flat_entries`, pushed into `restore_queue`) keep their bare `target_region` unchanged, same as every other winrestore entry; `process()` still resolves it again itself at match time for its own bookkeeping (`resolved_target_regions`, the `force_relayout` comparison), exactly as before this fix. `None` (no `wm_config`) leaves `target_region` bare, matching `resolve_workspace_target()`'s own no-candidates degradation.

## `append_layout` doesn't exist on sway — replaced with manual con_id tree reconstruction {#append-layout-doesnt-exist-on-sway}

**The entire mechanism documented in the two sections above is dead — not a bug in tuicc's own code, a permanent upstream decision.** Found live, next real test after the workspace-resolution fix above ("floating okno nedokáže doletět na svoje místo a neobnoví to tabbed stacked", with a screenshot): `swaymsg "append_layout ..."` and `i3ipc.Connection().command("append_layout ...")` both return `{"success": false, "parse_error": true, "error": "Unknown/invalid command 'append_layout'"}` on Rafi's real sway 1.12.0 — confirmed via `gh api` against the actual GitHub issue text (more reliable than WebFetch's AI-summarized fetch for an exact quote), not a paraphrase: sway's own maintainer, ddevault/SirCmpwn, closed swaywm/sway#1005 with "I've decided that we are just not going to support this i3 feature, ever." `Provider.prepare_tiled_tree()` had been returning `False` unconditionally on sway this entire time — every restore silently fell back to flat placement, which is exactly what produced the bug report.

Presented three options (simplify to flat permanently / keep the mechanism as i3-only dead code / find an alternative) via `AskUserQuestion` — Rafi picked none of them, instead proposing his own alternative: fly tuicc itself through each target workspace during restore (staying sticky+fullscreen, invisible the whole time — reusing the exact sticky trick built for the flicker problem above) and build each region's structure with ordinary `move`/`layout` commands while actually focused there.

**Verified live, before writing anything — the one lesson actually taken from getting burned by `append_layout` itself:** spawned 3 real `kitty` windows, drove them by hand via `swaymsg`. Two findings, both surprising relative to Rafi's own proposal:
1. `[con_id=X] move container to workspace number N` and `[con_id=X] layout stacking|tabbed|splitv|splith` (note: **`stacking`, not `stacked`** — that's only the READ value `get_tree()` reports; `layout stacked` is a hard parse error, `"Expected 'layout default|tabbed|stacking|splitv|splith'..."`) both work addressed purely by criteria, with **no need for real WM focus on the target workspace at all** — real focus (confirmed via `get_workspaces()`'s own `focused` field, unchanged before/after every test command) never moves. This makes the whole sticky-flying idea unnecessary: nothing in the replacement mechanism ever calls `workspace <n>`, so there's no flicker to hide in the first place. `Provider.set_self_sticky()` is retired along with `prepare_tiled_tree()`.
2. `layout <type>` addressed at a con wraps **ALL of that con's current siblings** (everything else under the same immediate parent) into a brand-new container — confirmed live (2 windows, both direct workspace children, `layout stacking` on either wrapped both into a new con). This is the same interactive behavior real i3/sway users already rely on (focus several windows, hit the layout keybind) — nothing tuicc-specific. The problem: if a whole region's tree were built directly on the real target workspace, an EARLIER sibling (already placed, not yet grouped with anything) sits there as a "loose" top-level con by the time a LATER, unrelated nested group tries to form — and gets swept into that group by mistake, since `layout` can't be scoped to "only these children". Confirmed by trying it: moving 3 windows onto one workspace, grouping 2 of them, then moving a 3rd on top **auto-joined the existing group** rather than staying separate (sway inserts a new arrival at whatever's already established on that workspace) — informative on its own (see point 3 below) but exactly the failure mode that rules out building nested structure directly on the real workspace.

**Fix: build each subtree in isolation on a small reserved pool of scratch workspaces (`9000`+, one per nesting depth — `SCRATCH_WORKSPACE_BASE`/`MAX_TREE_BUILD_DEPTH`, `winrestore.py`), and only transplant a subtree onto its parent's own workspace once it's already a single, fully-formed container.** Picked far outside any plausible real workspace numbering — same "reserved namespace, not configurable" precedent `MARK_PREFIX` already sets for marks — rather than low numbers, specifically so collision with a user's real workspace is not just unlikely but essentially impossible. A tree nested deeper than the reserved pool (`MAX_TREE_BUILD_DEPTH`, generously 8) degrades its remaining structure to a flat leaf list instead of crashing — an exceedingly rare case in practice, documented not engineered around further.

3. A THIRD live test, once the scratch-workspace design was already settled on: does moving an existing multi-member GROUP (not a leaf) onto a workspace that already holds a DIFFERENT group correctly nest both as opaque units, or does it flatten their members together? Built two independent 2-member groups on two clean scratch workspaces, then moved one group's own wrapper con id onto the other's workspace — the result nested correctly (`tabbed[a, b, stacked[c, d]]`), the second group's own internal layout fully intact, not flattened. This is what makes "move the whole finished subtree up as one unit" (point 2's escape hatch) actually safe. Separately confirmed: addressing a MEMBER's own id (not the wrapper's) with `move` extracts JUST that member out of its group, leaving the rest behind — confirming `set_container_layout()` must return and the caller must retain the WRAPPER's own con id as the durable "handle" for a group, never a member's.

**Algorithm** (`TreeBuildState`/`advance_tree_build()`/`_BuildFrame`, `winrestore.py`) — an explicit, iterative stack machine (real Python recursion can't pause mid-subtree for however many frames a real window spawn takes): one `_BuildFrame` per split node currently being folded, `remaining` children not yet started, `accumulated_id` the running fold result, `has_wrapper` whether it's already a real multi-member group. Each tick does AT MOST one of: notice a queued leaf's tag resolved and fold it in; notice the current frame is fully folded (no `remaining` left) and pop it, handing its single result up to the parent frame (or, if the stack is now empty, doing the ONE real move onto the actual `target_region`, resolved via `resolve_workspace_target()` once at `start_tree_build()` time — same convention as every other move in this codebase); or dispatch the next child (a `"window"` queues one tagged restore entry targeting `_scratch_workspace(depth)`, a `"split"` pushes a new frame one depth deeper).

**Folding a child**: first child of a frame — just take its id, nothing to group with yet (matches the live-confirmed "2 loose leaves on a workspace do NOT auto-merge" baseline). Second child — `Provider.set_container_layout()` (the `append_layout`-mechanism's replacement, `tiled_tree.set_container_layout()` underneath, shared by both providers since addressing by con_id needs no `app_id=`/`class=` translation the way marks do) groups them, and `accumulated_id` becomes the returned WRAPPER id, `has_wrapper` flips true. Third-and-later children — **no further `set_container_layout()` call at all**, relying on the live-confirmed auto-join behavior (point 2 above) instead: since the frame's own scratch workspace already holds nothing but the established group by that point (this frame's own accumulator, not some unrelated one — guaranteed by the scratch-workspace isolation), a new arrival always joins it directly, adopting its layout. This sidesteps an entirely separate untested question (whether re-issuing `layout X` on an already-correctly-parented member is a safe no-op or creates redundant nesting) by simply never needing to ask it.

**Failure recovery**: `Provider.set_container_layout()` returning `None` (live-verified reliable, so expected rare — most likely the window vanished mid-restore) sets `TreeBuildState.failed`; the child that directly triggered the failure is force-moved to the real `target_region` immediately (it's already resolved, right there); every subsequent tick then sweeps every frame still on the stack the same way, so nothing already accumulated is left stranded on a hidden scratch workspace forever. The one acknowledged, documented gap: a sibling leaf whose spawn was still in flight (queued, not yet matched) at the exact moment a DIFFERENT sibling's fold failed has no way to be recovered — it will still eventually spawn, land on its own scratch workspace, and then never be moved further. Accepted as rare and documented, not engineered around further, same tolerance this codebase already extends to comparable edge cases (`mark_self()`'s own focus-race fallback, etc).

**`pending_moves.py`**: one small, backward-compatible addition rather than a second matcher — an entry may carry an optional `"tag"` (only `winrestore.py`'s tree-builder ever sets one, and only ever one at a time, by construction), and `PendingMovesQueue` gained `resolved_tags: dict` (tag → matched window id), populated by `process()`'s existing match branch and popped by `advance_tree_build()` on a LATER frame (the tree-builder runs before `process()` each frame, so a tag resolved this frame is only visible next frame — the same one-frame lag every other "drive a queue one step per frame" mechanism in this codebase already has). Every other field/behavior of `process()` — focus reclaim, `SETTLE_SECONDS`, timeout, failure messages — applies to a tagged entry exactly the same as any other; `placed_by_wm` is now genuinely dead weight (nothing sets it `True` any more, since nothing needs to skip the ordinary placement move any more) but left in place as a harmless, already-tested no-op rather than torn out along with the batch-marker role it separately still plays in `_batch_in_flight()`.

**`tiled_tree.py`**: `layout_to_append_json()`/`_regex_escape()` deleted outright (dead — nothing builds `append_layout` JSON any more). `capture_tiled_tree()`/`flatten_leaves()`/`get_tiled_tree()` are completely unaffected — capture never depended on `append_layout` in the first place, only the restore side did. New `set_container_layout(conn, window_id, layout)` — issues `[con_id={window_id}] layout {keyword}` (translating the one `stacked`→`stacking` read/set spelling asymmetry) then re-queries `get_tree()` and returns `window_id`'s own current parent id — a single shared free function, not per-provider, since addressing by con_id needs zero translation between sway/i3 (unlike `mark_self()`'s `app_id=`/`class=` split).

## Launcher placement-mode picker; tree-reconstruction restore disabled {#launcher-placement-mode}

Live-tested the scratch-workspace tree builder above on a real multi-region, repeated-app_id layout and it didn't work — Rafi's own read: "teď pro jistotu restore nefunguje vůbec... tohle je strašně komplikovaná věc, chainovat restorace oken přes všechny workspaces." His alternative, stated directly: make launching ONE window into a chosen shape (tiled/stacked/tabbed/floating) cheap and reliable first, as a launcher feature — the exact real-world idiom of `mod4+S` on a focused window turning it into a stack, further spawns explicitly aimed at it, windows already elsewhere on the workspace never retroactively joining. Session restore, if it returns at all, becomes a later replay of that same primitive — not attempted here.

**Two more primitives verified live before designing, same discipline as the append_layout mistake above**: `layout stacking` on a LONE window (no sibling at all) still creates a real, addressable single-member group — exactly `mod4+S` on one focused window. And `move window to mark <mark>` precisely targets ONE SPECIFIC existing container by mark, regardless of how many other groups exist on the same workspace, with zero focus disturbance (confirmed: real WM focus never moved) — the missing piece the scratch-workspace design never had: it could only ever address "whatever's on this workspace right now", never "S1 specifically, not T1".

**The feature**: the launcher gets a placement-mode picker, cycled with **Tab/Shift+Tab** — Left/Right and Up/Down were already claimed (app-result cycling and target-workspace shifting respectively, both inside `handle_typing_key()`/`handle_launcher()`), but Tab/Shift+Tab are inert during launcher typing, free real estate. Shown live in the sidebar's own `" {id} - launching here "` label as `" {id} - launching here (into S1) "` etc. (`sidebar.py`, via `launcher_mode.placement_mode_display()`). Options, in order, cycled circularly: `tiled → stack_new → tab_new → «one entry per existing top-level group on the target region» → floating` (`launcher_mode.placement_mode_options()`). Default: the target region's own first existing group if it has one, else `tiled` (`launcher_mode.default_placement_mode()`) — recomputed fresh every time the target region changes (Up/Down during typing, and once right after typing starts, past `_apply_launcher_routing_default()` so a routing-rule redirect is accounted for), via `main.py`'s `_reset_placement_mode_default()` — never sticky across a workspace change, since a group label only means something on the workspace it came from.

**New shared primitives, `tiled_tree.py`** (peer to `set_container_layout()`, same "one function serves both providers, con_id addressing needs no app_id=/class= translation" reasoning): `list_container_groups(workspace)` walks the TOP-LEVEL `.nodes` only (deliberately not recursive, unlike `capture_tiled_tree()` — a group nested deeper just isn't offered as a target, a documented scoping limitation matching the real common case, not a crash), labeling each stacked/tabbed child `S1`/`S2`/`T1`/... in on-screen order. `move_window_to_group(conn, window_id, container_id)` marks `container_id` with a fresh, disposable, pid+counter-unique temp mark (same uniqueness reasoning `MARK_PREFIX` already established for `mark_self()`), `move window to mark <mark>`, unmarks again. `Provider.list_container_groups()`/`move_window_to_group()` (both optional, default `[]`/`False`) are thin per-provider delegates, identical between sway/i3. `set_container_layout()` (already built) is reused as-is for `stack_new`/`tab_new` — it groups a freshly-placed window with whatever's ALREADY on the target workspace, real `mod4+S` semantics (if other loose windows already sit there, they join too — correct, matches real WM behavior, not a bug).

**Wiring reuses the tag/resolved_tags plumbing built for the tree-builder above, not a new mechanism**: `queue_launcher_spawn()` gained the same optional `tag` param `queue_restore_entry()` already had (an ordinary `tiled` launch never sets one — zero overhead on the overwhelmingly common path). New `pending_moves.PlacementQueue` (`pending: dict[tag, PendingPlacement]`) + `advance_placements(state, moves, provider)` — same "cheap no-op most frames" driver shape as `advance_tiled_restore()`, but a plain dict rather than a single-slot state machine, since — unlike the tree-builder's one-tag-at-a-time guarantee — several launcher spawns can genuinely be in flight simultaneously (GUIDE.md's own verification checklist already covers this case for plain spawns). Runs right after `process()` each frame (`frame_update.py`), not one frame later like the tree-builder's own tag consumption — no sequencing invariant here needs that lag, so acting the same frame is simply more responsive. `main.py`'s `handle_launcher()` resolves the picked mode against a FRESH `list_container_groups()` call at CONFIRM time, not whenever it was originally picked — a stale label (that group closed since) quietly degrades to plain `tiled`, never errors.

**Restore ("load") disabled outright, not fixed**: `modules/winrestore.py` gained a module-level `RESTORE_DISABLED = True` flag, checked first thing in the `"load"` action — short-circuits straight to a toast ("Session restore is temporarily disabled — see README") before touching `pending_layout_regions` or anything else. `"save"` is untouched (still just a plain TOML write, no IPC side effects, forward-compatible with whatever eventually replaces this). `TreeBuildState`/`advance_tree_build()`/`set_container_layout()` are NOT deleted — `set_container_layout()` in particular gets a real second caller in this very feature (`stack_new`/`tab_new` above), so it's not even dead code; only the "load" action's own call path is switched off, a one-line revert once restore is rebuilt for real as a replay of these same launcher primitives. `README.md` updated to say this plainly rather than let the feature silently look broken with no explanation.

### Live-found bug, same feature: `floating` (and any existing-group) placement silently no-op'd on a named-workspace setup {#bare-workspace-id-fix}

Reported immediately: "floating spawn nefunguje." Root cause wasn't the new `floating` code path itself — it was a pre-existing, latent inconsistency this feature was the first thing to actually expose. `loop_state.focus_id` (`main.py`) is **not always bare** the way `Region.id`/a saved entry's own `target_region` always are: `pending_moves.process()` sets it to `result.resolved_target_regions[-1]` once a spawn resolves (`frame_update.py`), and that value can ALREADY be a resolved `"N:Name"` (`resolve_workspace_target()`'s own job). `handle_launcher()`'s confirm branch reads `loop_state.focus_id` straight into `target_region`, then into `PendingPlacement.region_id` for a `floating` pick, and into `provider.list_container_groups(target_region)` for an existing-group pick — both of which, unlike `move_window_to_region()`'s own `workspace number <target>` IPC command (tolerant of either form via sway/i3's own leading-digit prefix matching), looked up the target workspace with an EXACT `str(workspace.num) == region_id` comparison. Passed an already-resolved `"3:III"`, that comparison never matches anything, the lookup returns `None`, and the method just `return`s having done nothing at all — no error, no toast, just silent no-op. On a plain-numbered-workstation setup this never surfaces; on Rafi's own real setup (named workspaces throughout this whole session) it was reachable on essentially every use.

Fixed at the root, not by patching the two call sites: new `wm_config_parser.bare_workspace_id(region_id)` (`_leading_number()`'s own existing regex, exposed as a public function since it's now needed cross-module) strips a resolved name back to its bare leading number, no-op on an already-bare id. Applied inside `providers/sway.py`'s and `providers/i3.py`'s THREE workspace-lookup-by-exact-number sites — `set_floating_geometry()`, `get_tiled_tree()`, `list_container_groups()` — not just the two the bug report touched, since all three share the identical fragile comparison and the fix is free. `get_tiled_tree()`'s own callers (winrestore's "save" branch) only ever pass an already-bare `Region.id`, so it was never actually reachable there in practice — hardened anyway, consistency over chasing only the proven-reachable half. No behavior change for a genuinely bare id (`bare_workspace_id("8") == "8"`) — the whole fix is additive tolerance, not a new requirement.

Also exposed, same root cause, not yet independently reported: `list_container_groups()` being unreachable this way meant the launcher's Tab-cycle picker would never offer an existing `S1`/`T1` as a choice either, silently falling back to only `tiled`/`stack_new`/`tab_new`/`floating`, whenever `loop_state.focus_id` was already resolved — same fix covers it, no separate work needed.

`set_floating_geometry()` had **no direct test coverage at all** before this fix — a real gap that let the bug ship in the first place; added both a normal-case test and the exact resolved-id regression for both providers, plus the same regression for `get_tiled_tree()`/`list_container_groups()`.

### Live-found bug, same feature: `floating enable` re-homes onto whatever's currently focused {#floating-enable-workspace-reparenting}

Reported right after the fix above: "teď se opravdu spawne floating, ale neposune se na targeted ws, zůstane na tuicc ws" (floating now genuinely happens, but the window doesn't move to the target workspace — stays on tuicc's own). Root-caused live, not guessed, same diagnostic technique as every other bug this session (`swaymsg -t get_tree`, one step at a time, real windows): a container correctly moved to a target workspace via `move container to workspace number N` (confirmed on the right workspace), then converted with `[con_id=X] floating enable, resize set ..., move position ...` — the SAME single command chain `set_floating_geometry()` has always sent — ends up back on whatever workspace is **currently focused**, not the one it was just moved to. Confirmed this is specifically `floating enable`'s own doing (not the resize/move actions, not a comma-chaining artifact): reversing the two steps — `floating enable`/`resize`/`move position` FIRST (while the container is still wherever it originally mapped), THEN `move container to workspace number N` — lands it correctly on the target and KEEPS it there, real WM focus completely undisturbed throughout. A floating container's own geometry and floating-ness survive a subsequent workspace move perfectly (verified live: `rect` unchanged, still floating, after the second move).

This bug predates the launcher placement-mode feature — `pending_moves.process()`'s own winrestore-floating branch has always called `move_window_to_region()` THEN `set_floating_geometry()`, the exact broken order, since the very first floating-restore code landed. It was very likely the true root cause of the earlier, separately-reported "floating okno nedokáže doletět na svoje místo" bug from the append_layout era — misattributed at the time to the tree-reconstruction mechanism being investigated in that same session, never actually isolated since the evidence (the user's own test windows) got accidentally cleaned up before it could be checked directly. Not restestable now either (restore's own "load" path is disabled — see `#launcher-placement-mode`), but the fix below applies to that code path too, for whenever it comes back.

**Fix, two call sites, same underlying reorder:**
- `pending_moves.process()`'s winrestore-floating branch: swapped to call `set_floating_geometry()` BEFORE `move_window_to_region()` (both already sit right next to each other in one `if not entry.get("placed_by_wm"):` block — a straight reorder, no new call needed).
- `pending_moves.advance_placements()`'s `"floating"` branch (the launcher's own placement-mode picker): can't reorder the same way — by the time this runs, `process()` has ALREADY moved the window to its target region once, unconditionally, as part of matching (launcher entries have no `"floating"` key on them the way winrestore entries do, so `process()` never knows to skip or defer that move). Fixed by calling `provider.move_window_to_region(window_id, placement.region_id)` a SECOND time, immediately after `set_floating_geometry()` — cheap (one extra IPC call, only for the `floating` mode specifically, not the common `tiled` path), and correct per the same "a floating container survives being moved again" behavior confirmed live above.

**One fix, not two**: immediately after this landed, a second symptom was reported — "sway neakceptuje tvůj resize a nutí tam system default" (sway won't accept your resize, forces some system default there instead), which looked at first like a genuinely separate bug (maybe the same swayfx comma-chaining quirk `install.sh`'s own `for_window` rules already work around — see this file's own note on that a few sections up). A manual live replay of the exact chained `floating enable, resize set, move position` command, in isolation, worked perfectly, which argued against that theory. Confirmed once the reorder fix above actually took effect live: it was the SAME bug, not a second one — the window landing on the WRONG (currently-focused) workspace was likely also picking up whatever default sizing applies there (a fresh floating window with no size hint gets the WM's own default, not necessarily related to us at all), which looked like "my resize got ignored" but was really just "the resize applied to a window that then got reparented, and the version that stuck was never the one I was looking at." No separate fix was needed.

New test coverage locks in the ORDER, not just the calls: `_FakeProvider.call_order` (tests/test_pending_moves.py) is a single interleaved log across `move_window_to_region()`/`set_floating_geometry()` — the pre-existing `.moved`/`.floated` lists alone can't express "which happened first," which is exactly what this bug was.

### `preview.py` drawing outside its own box {#preview-window-screen-rect-clamping}

Separate, genuinely independent bug spotted in the same round of screenshots (not a symptom of the floating bug above, though it likely got exercised BY it): a floating window's own preview rectangle rendered straight through `preview.py`'s own box border into the sidebar's "Workspaces" box next door. Root cause: `_window_screen_rect()` (the pure function converting a window's real WM-reported `rect`, normalized 0..1 relative to its own workspace, into this module's own terminal-cell coordinates) trusted that normalization to actually stay within 0..1 and did no clamping of its own — a real floating window whose on-screen geometry ends up larger than or offset outside its own workspace (exactly what a resize landing on the wrong, about-to-be-reparented window, per the bug above, could produce) yields `rx`/`ry`/`rw`/`rh` outside that range, and the computed screen box just draws wherever that arithmetic says, with nothing stopping it from leaving this module's own assigned area. Fixed by clamping the computed `win_x`/`win_y`/`win_w`/`win_h` to the box's own inner area (inside its 1-cell border) as a final step — `nav_items()` shares this same function for its own floating-window tab targets, so the fix keeps "what's drawn" and "what Tab actually selects" in agreement, same invariant the function's own docstring already commits to. New tests cover a rect extending past the region, one entirely beyond it, and one inside a non-origin box (a real module box never starts at screen (0,0)).

**Follow-up, confirmed clean live, then requested as a UX refinement**: "ořezává a to je správně, ale dokázali bychom třeba ty rohy co pokračují mimo obrazovku udělat šrafovaně?" (clips correctly now, but could the corners that continue past the screen be hatched?) — a visual cue that a floating window's real edge genuinely extends beyond what this box can show, distinct from a window that just happens to end exactly at that cell. New `_clamped_edges(window, x, y, w, h)` re-derives (top, bottom, left, right) clamp flags from the same pre-clamp math `_window_screen_rect()` already computes internally — a separate function rather than changing that one's own return shape, since most of its callers (`nav_items()`'s hit-testing) only need the plain coordinates, and every existing test already asserts that exact 4-tuple. New `_draw_clamped_outline()` (peer to the existing `_draw_dashed_outline()` placeholder-box helper) draws a DENSE `╱` hatch (every cell, not a sparse tick) along any edge whose flag is set, corners included whenever EITHER of their two edges is clamped — `_draw_window()` gained an optional `clamp` param (default all-`False`, so its one other call site — tiled windows, never clamped by construction) picks the plain `draw_box_outline()` path unchanged.

### Placement-mode hint also shown in the Launcher box itself, not just the sidebar

Asked live: "když spouštím aplikaci, objevuje se teď přímo v laucher boxu info o tom jak se spawne?" — it didn't; the sidebar's own `" {id} - launching here ({mode}) "` label (`#launcher-placement-mode`) was the only place it showed, a different box than the one actually being looked at while typing. Added the same info to `modules/launcher.py`'s own `draw()`, on the query row itself (`"> search text"`), right-aligned against the box's own edge as `"[mode]"` — costs no extra row, always visible once typing starts, regardless of box height (unlike the routing-rule hint below it, which needs a spare row and only shows for apps with a matching rule). New `_placement_hint_position(box_x, box_w, query_width, mode_width)` — pure position math, returns `None` (skip drawing entirely, not truncate into illegibility) when a long in-progress search would collide with it; the query always wins that fight. Both the sidebar's and the launcher's own hints stay — deliberately not a "replace one with the other" — each is useful in its own moment (sidebar when eyeing the target workspace, launcher box when eyeing what's being typed).

Two immediate follow-ups from there, both live requests: sidebar label got `↑↓` added right after "launching here" (naming the keys that move which region shows it) and `(mode)` switched to `[mode]` to match the launcher box's own bracket style, no behavior change either way — just text.

Then a bigger one: "teď v launcheru by neměla být vidět jen jedna option ale takový ten výčet jako v connectivity [O Tiled] [O Stacked] .... a tak čtyři, svítí ta co je vybraná" — replace the single right-aligned `[mode]` hint with a full condensed row, all 4 fixed categories always visible, the active one lit — mirroring `modules/connectivity.py`'s own `●`/`○` "is this the current state" convention (`"[P]WR ● [S]CAN ○"`) rather than inventing a new visual language. New `PLACEMENT_CATEGORIES` (tiled/stack_new/tab_new/floating, in that fixed order) and `placement_category(mode)` — collapses an existing group's own specific label (`"S1"`/`"S2"`/...) onto the SAME "Stacked" entry `"stack_new"` itself lights, a `"T1"`/`"T2"`/... label onto "Tabbed": both mean "aimed at a stack/tab group" at this coarse, 4-button level, the sidebar's own more detailed `"into S2"` text is still there for the precise answer. Tab/Shift+Tab still cycle through every REAL option one at a time (including a specific existing group, per `placement_mode_options()`, unchanged) — this only changes how the condensed row lights up, never what's actually selectable. `_draw_placement_row()` draws `"[Tab] [● Tiled] [○ Stacked] [○ Tabbed] [○ Floating]"` piece by piece (curses can't mix colors within one `addstr` string), stopping cleanly at the box's own inner right edge rather than overflowing into whatever's next door — `"[Tab]"` uses `key_label(cfg.keybinds["tab"])`, the actual configured key, not a hardcoded name (same discipline `power_menu.py`/`connectivity.py`'s own hint text already follows). Gets its own dedicated row right under the query line whenever the box is tall enough to spare one (`h > 4`) — items_row shifts down accordingly, same `h > 3` degrade shape that row's own fallback already used — a too-short box falls back to the old single right-aligned `[mode]` hint on the query row instead of just disappearing.

**Immediate follow-up, same live round, three passes before it actually landed right**: adding the new row pushed the pre-existing routing-rule hint (GitHub issue #9's own follow-on — "Routing rule detected — spawning at ws ...") down onto what used to be a 4th content row below the results, which a box sized for the ORIGINAL 3-line budget (query/mode/results) may no longer have room for at all.

2. Second attempt: grew the row budget by one row ONLY on frames a rule is actually active (`extra_rows = 1 if routing_hint else 0`), giving the rule its own dedicated row above the placement row. Also wrong, caught live the moment it rendered: the box was already comfortably WIDE, and the "extra row" this reserved sat almost entirely empty apart from the rule text at its very left edge ("teď počkej druhý řádek je uplně prázdný, to mi říkáš že se na ten druhý řádek nevejde obojí vedle sebe?" — wait, that second row is completely empty, are you saying both won't fit side by side on it?). There never was a real HEIGHT problem — only a habit of reaching for another row before checking whether the row already in hand had spare WIDTH instead.
3. Actual fix: `_draw_placement_row()` gained an optional `prefix` param — the routing hint, when active, is drawn first, immediately followed by "[Tab] [● Tiled]..." on the SAME row the placement row already had, using its own leftover width. No second row, ever — `show_mode_row = h > 4` reverted to exactly what it was before the rule even entered the picture. The tiny-box fallback (no room for a dedicated row at all) keeps its own "the rule wins the one squeezed-onto-the-query-row slot when active, the plain `[mode]` text otherwise" priority — the one piece of the second attempt that was already correct and stayed unchanged.

Required moving `results`/`sel`/`sel_app_id`/the routing lookup earlier in `draw()` either way (the row content decision needs to know whether a rule is active before drawing that row, not after) — the old, separate `hint_row = items_row + 1` block at the very end of the function is gone outright, folded into this same row.

**One more round, same feature**: "taky by se v tom seznamu měl objevovat into S1, T1 cokoliv if applicable" — the condensed row's 4 fixed categories (`PLACEMENT_CATEGORIES`/`placement_category()`, both deleted outright now — no longer used anywhere) collapsed a real existing group's own label onto a generic "Stacked"/"Tabbed" bucket; the ask was for the ACTUAL reachable options to show up as their own entries, same list `placement_mode_options()` already builds for Tab-cycling in `main.py`. `RenderContext` gained `launcher_placement_options: list` — computed in `frame_update.py` (`launcher_mode.placement_mode_options(provider.list_container_groups(target_region))`), ONLY while `launcher.typing_mode` is true (an IPC round trip every frame otherwise, for a row nobody's looking at — same restraint the status-worker-fed fields on this same context already apply). `modules/launcher.py`'s `_draw_placement_row()` now iterates this live list directly instead of the fixed 4-tuple; new `_row_label()` gives the 4 base modes their existing short capitalized words and reuses `placement_mode_display()` verbatim (`"into S1"`) for anything else — one function, no more separate category-collapsing step needed at all.
